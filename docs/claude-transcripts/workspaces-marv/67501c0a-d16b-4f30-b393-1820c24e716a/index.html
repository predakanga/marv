Good questions — let me address each one, then update the documents.

Architecture:

  1. DI container ownership: You're right. The app should call into core to do the heavy lifting. The app owns the IHostBuilder and top-level config, but core should expose a method like AddMarv(IServiceCollection, MarvConfig) that handles plugin discovery, loading, dependency sorting, and service registration. The app just calls that.

  2. Single IrcMessage for inbound/outbound: Yes, I think so. The structure is identical — tags, command, parameters. The only difference is the source (inbound has one, outbound doesn't). Making it a single type keeps the parser/serializer unified and avoids conversion between types when plugins want to echo or transform messages.

  3. PING/PONG layering: Fair point. PING/PONG is a protocol-level concern, not a transport concern. The connection layer should just shuttle raw messages. I'll move PING/PONG handling into the message processor (core layer), alongside CAP negotiation and state tracking.

  4. Per-plugin tasks: This is feasible. Each plugin gets its own Channel<MarvEvent> and a dedicated task that drains it. The message processor fans out events to all plugin channels after state tracking updates. This means plugins run concurrently with each other but each plugin's handlers still run sequentially within its own task. State stores (IChannelStore, IUserStore) would need to be thread-safe for reads, but since only the message processor writes to them (before fanning out events), we can use a reader-writer pattern — the processor updates state, then publishes events, and plugins read state during handling. Plugins can safely read state because the stores use immutable snapshots or concurrent-safe reads.

  5. Automatic ProvidesService/ConsumesService: Yes. We can scan the plugin's ConfigureServices registrations to see what service types it registers (provides), and scan its constructor parameters to see what it requires (consumes). The attributes become unnecessary for the common case. We'd still need an attribute for optional dependencies (to distinguish "nullable because optional" from "nullable for other reasons"), but we could make that [OptionalService] on the constructor parameter instead.

  6. Automatic config registration: Yes. The base class can use a generic: MarvPlugin<TConfig> where TConfig is the configuration type. The plugin loader detects the generic argument, binds it to Plugins:{PluginName} automatically, and injects IOptions<TConfig>. No ConfigureServices needed for the config-only case.

Platform abstraction:

  1. IChannelMember: Agreed. We can fold prefixes and join time into IChannel directly — e.g., IChannel.GetPrefixes(string nick) and IChannel.GetJoinTime(string nick). The members collection just returns IUser references.

  2. Combining Channel/Private events: Yes, a MessageEvent with an IsDirect flag (and Channel being null for DMs) works well. Same for notices and actions. This cuts the event count in half and simplifies handler registration.

  3. BatchEvent: Good concern. Instead of delivering a separate BatchEvent and suppressing individual events, we can do the opposite: always deliver individual typed events, but tag each one with a BatchId property. Plugins that care about batching can collect events by BatchId. Plugins that don't care just process events normally. No special BatchEvent type needed.

Plugin API:

  1. GetChannel vs Channels: I'll drop GetChannel and keep Channels as an IReadOnlyDictionary<string, IChannel> (keyed by case-mapped name) so lookup by name is still O(1) via the indexer.

  2. Users: Same treatment — IBot.Users as IReadOnlyDictionary<string, IUser>. Drop GetUser.

  3. SendAndAwaitAsync: It sends an IRC command and waits for the server's response, using labeled-response to correlate them. For example, sending a WHO command and getting back the WHO reply lines as a batch. I'll add a clearer description.

  4. OnRegex: Good addition. [OnRegex(@"pattern")] with a RegexMatchContext that includes the Match object. I'll add it.

  5. Handlers in separate classes: The idea would be a [HandlerGroup] attribute on a class that the plugin declares. The plugin loader scans the plugin's assembly for handler groups and wires them up with DI. Something like:

[HandlerGroup(typeof(MyPlugin))]
public class MyAdminHandlers
{
    public MyAdminHandlers(IBot bot, IAuthorizationService auth) { ... }

    [OnCommand("kick")]
    public async Task HandleKick(CommandContext ctx, CancellationToken ct) { ... }
}

#52026-05-30T10:35:45.810Z

Could you explain how scanning ConfigureServices registrations would work? My idea was just to scan assemblies for implementations of the consumed types, but I can see how that could be flawed.

Good question — let me think through both approaches honestly.

Scanning ConfigureServices (my proposal): The idea is to call each plugin's ConfigureServices on a throwaway ServiceCollection during the discovery phase. IServiceCollection is just IList<ServiceDescriptor>, and each ServiceDescriptor has a ServiceType property. So after calling it, you inspect the descriptors, filter out known framework types (IOptions<>, ILogger<>, etc.), and the remaining ServiceType entries are what that plugin provides.

This works because ConfigureServices is static and only adds registrations — it doesn't resolve anything, so there are no ordering concerns during discovery. You'd call it a second time for real during the actual DI build phase.

The downsides: you're running the method twice (minor), and if it has side effects beyond adding descriptors that's a problem (but that would be a plugin bug). It also feels like an odd trick.

Assembly scanning (your idea): Scan plugin assemblies for types implementing the consumed interface. If Plugin B needs IAuthorizationService, find which assembly contains a class implementing it, and infer that assembly's plugin provides it.

The flaw you're probably sensing: a class implementing an interface doesn't mean the plugin intends to provide it as a service. Internal helpers, test doubles, or alternative implementations that aren't registered would all be false positives. And if two assemblies contain implementations, it's ambiguous.

A third option worth considering: Just keep a lightweight attribute on the providing side only. Something like [ProvidesService(typeof(IAuthorizationService))]. The rationale: providing a service is the uncommon case — most plugins just consume. A single attribute on the rare plugin that provides a service is much less burdensome than the original design where both sides needed attributes. The consuming side stays automatic (constructor parameter inspection).

That third option is probably the most honest design — it's explicit, zero-magic, and the cost falls only on plugins that do something unusual (providing services to other plugins).

What's your preference?
