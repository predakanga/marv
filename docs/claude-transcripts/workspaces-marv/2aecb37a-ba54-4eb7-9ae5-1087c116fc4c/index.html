Good point — if there's a maintained package that drops in as an IConfigurationSource, there's no reason to reimplement the flattening logic ourselves. The spec's Option A was motivated by avoiding a dependency, but System.Text.Json's permissive mode only covers comments and trailing commas anyway — if we're pulling in a package, we might as well get full JSON5 support.

Let me check what's actually available.

It doesn't look like a Json5.Configuration package exists on NuGet. The closest things are:

  • Json5Core — a JSON5 parser, but not an IConfigurationSource integration
  • Retyped.json5 — a Bridge.NET binding, not relevant

There's no drop-in AddJson5File extension method available. So the options are really:

  1. Custom provider using System.Text.Json (the current spec) — covers comments and trailing commas with zero dependencies, which are the practical pain points
  2. Custom provider using Json5Core — adds a dependency for full JSON5 support, but we'd still need to write the IConfigurationSource/IConfigurationProvider wrapper and the key flattener ourselves

Given that comments and trailing commas are the only real ask, and System.Text.Json handles both natively, I think the current spec (Option A) is the right call. No point pulling in a dependency just to get unquoted keys and single-quoted strings that nobody will use in a config file.

Want me to update the spec to note this, or leave it as-is and move to implementation?
