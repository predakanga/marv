# CS-016: Extract BatchChannels to Utility Class

**Source:** `TODO.md` item 6
**Scope:** Marv.Core
**Complexity:** Trivial
**Breaking changes:** None (method is `internal`)

---

## Problem

`IrcBot.BatchChannels` is an `internal static` method that splits a list
of channel names into batches fitting the 512-byte IRC line length limit.
This logic is useful to any plugin that needs to send batched IRC commands
(e.g., joining many channels, sending MODE for multiple targets). Since
it's `internal` to `IrcBot`, plugins cannot use it.

## Decisions

- Move the method to a new `public static` utility class
  `IrcUtils` in `Marv.Core.Utils`.
- Keep the method named `BatchChannels` — it operates on channel name
  lists specifically, and generalizing to arbitrary comma-separated
  parameters risks missing protocol-specific quirks (e.g., channels with
  keys use a different format than plain comma-separated lists).
- The `maxPayloadLength` parameter is required (no default). The correct
  value depends on the IRC command being constructed, and encoding a
  default would bake in assumptions about which command the caller is
  building. `IrcBot.JoinMultipleAsync` passes the value it computes for
  JOIN; other callers compute theirs for their command.
- Remove `IrcBot.BatchChannels` entirely and update `JoinMultipleAsync`
  to call `IrcUtils.BatchChannels` directly.

## Changes

### 1. Create `IrcUtils` class

```csharp
namespace Marv.Core.Utils;

/// <summary>
/// Utility methods for working with IRC protocol constraints.
/// </summary>
public static class IrcUtils
{
    /// <summary>
    /// Splits a list of channel names into batches where each batch's
    /// comma-separated representation fits within
    /// <paramref name="maxPayloadLength"/> bytes. Useful for batching
    /// JOIN, MODE, and other channel-list commands within the 512-byte
    /// IRC line limit.
    /// </summary>
    /// <param name="channels">The channel names to batch.</param>
    /// <param name="maxPayloadLength">
    /// Maximum byte length for the comma-separated channel list.
    /// The caller must account for the command prefix and CRLF when
    /// computing this value (e.g., 512 - len("JOIN ") - len("\r\n")).
    /// </param>
    public static IEnumerable<List<string>> BatchChannels(
        IReadOnlyList<string> channels, int maxPayloadLength)
    {
        // Implementation moved from IrcBot.BatchChannels
    }
}
```

### 2. Update `IrcBot`

Remove the `BatchChannels` method from `IrcBot`. Update
`JoinMultipleAsync` to call `IrcUtils.BatchChannels` directly, passing
the computed max payload length (currently 505):

```csharp
foreach (var batch in IrcUtils.BatchChannels(channelNames, maxPayloadLength: 505))
{
    var joinList = string.Join(",", batch);
    await SendRawAsync(new IrcMessage("JOIN", [joinList]), ct);
}
```

### 3. Move existing tests

Update existing tests for `IrcBot.BatchChannels` to test
`IrcUtils.BatchChannels` instead. Since the parameter no longer has a
default, all test call sites must pass `maxPayloadLength` explicitly.

## Impact

- **Plugin API:** Adds `IrcUtils.BatchChannels` as a new public utility
  in `Marv.Core.Utils`. Non-breaking.
- **Existing code:** `IrcBot.JoinMultipleAsync` behavior is unchanged.
  `IrcBot.BatchChannels` is removed (was `internal`, no external impact).
- **Tests:** Existing batch tests move to the new class. No behavior
  change.

1	# CS-015: Regex Options for OnRegex Attribute
2	
3	**Source:** `TODO.md` item 4
4	**Scope:** Marv.Core.Plugin
5	**Complexity:** Small
6	**Breaking changes:** None
7	
8	---
9	
10	## Problem
11	
12	The `[OnRegex]` attribute compiles patterns with only `RegexOptions.Compiled`.
13	Plugin authors cannot specify additional regex options such as
14	`RegexOptions.IgnoreCase`, `RegexOptions.Singleline`, or
15	`RegexOptions.IgnorePatternWhitespace`. This forces authors to embed
16	inline flags in the pattern itself (e.g., `(?i)hello`) or to use
17	`[OnRawMessage]` with manual regex handling.
18	
19	The `OnCommandAttribute` already supports several optional properties
20	(`ChannelOnly`, `DirectOnly`, `Channel`, `Prefix`). Adding `Options` to
21	`OnRegexAttribute` follows the same pattern.
22	
23	## Decisions
24	
25	- Add an `Options` property to `OnRegexAttribute` of type
26	  `RegexOptions`.
27	- Default value is `RegexOptions.None` — the framework always adds
28	  `RegexOptions.Compiled` internally, so the author only specifies
29	  behavioral options.
30	- The property uses `init` style, consistent with other optional
31	  properties on the attribute.
32	
33	## Changes
34	
35	### 1. Add `Options` property to `OnRegexAttribute`
36	
37	```csharp
38	[AttributeUsage(AttributeTargets.Method, AllowMultiple = true, Inherited = false)]
39	public sealed class OnRegexAttribute(string pattern) : Attribute
40	{
41	    /// <summary>The regular expression pattern to match against message text.</summary>
42	    public string Pattern { get; } = pattern;
43	
44	    /// <summary>
45	    /// Additional <see cref="RegexOptions"/> applied when compiling the pattern.
46	    /// <see cref="RegexOptions.Compiled"/> is always added by the framework.
47	    /// Defaults to <see cref="RegexOptions.None"/>.
48	    /// </summary>
49	    public RegexOptions Options { get; init; } = RegexOptions.None;
50	
51	    /// <summary>If true, handler only fires for channel messages (skips DMs).</summary>
52	    public bool ChannelOnly { get; init; }
53	
54	    /// <summary>If true, handler only fires for direct/private messages (skips channels).</summary>
55	    public bool DirectOnly { get; init; }
56	
57	    /// <summary>
58	    /// If set, handler only fires when the message is in this channel.
59	    /// Compared case-insensitively.
60	    /// </summary>
61	    public string? Channel { get; init; }
62	}
63	```
64	
65	### 2. Update regex compilation in `MarvPlugin.DiscoverHandlers`
66	
67	In the handler discovery loop, combine the author-specified options with
68	`RegexOptions.Compiled`:
69	
70	```csharp
71	// [OnRegex] handlers
72	foreach (var regexAttr in method.GetCustomAttributes<OnRegexAttribute>())
73	{
74	    WarnOnConflictingFilters(regexAttr.ChannelOnly, regexAttr.DirectOnly, regexAttr.Channel,
75	        target.GetType().Name, method.Name, "OnRegex");
76	    _regexHandlers.Add(new RegexRegistration(
77	        target, method,
78	        new Regex(regexAttr.Pattern, RegexOptions.Compiled | regexAttr.Options),
79	        regexAttr.ChannelOnly, regexAttr.DirectOnly, regexAttr.Channel));
80	}
81	```
82	
83	### 3. Update `docs/PLUGIN_API.md`
84	
85	Document the new `Options` property with examples.
86	
87	## Usage examples
88	
89	```csharp
90	// Case-insensitive matching
91	[OnRegex(@"hello\s+(\w+)", Options = RegexOptions.IgnoreCase)]
92	public async Task HandleHello(RegexMatchContext ctx, CancellationToken ct)
93	{
94	    await ctx.ReplyAsync($"Hi {ctx.Match.Groups[1].Value}!", ct);
95	}
96	
97	// Verbose pattern with comments
98	[OnRegex(@"
99	    ^!roll\s+          # command prefix
100	    (\d+)d(\d+)        # NdM dice notation
101	    (?:\+(\d+))?       # optional modifier
102	    $",
103	    Options = RegexOptions.IgnorePatternWhitespace)]
104	public async Task HandleRoll(RegexMatchContext ctx, CancellationToken ct) { ... }
105	```
106	
107	## Impact
108	
109	- **Plugin API:** Adds one optional property to `OnRegexAttribute`
110	  (additive, non-breaking). Default `RegexOptions.None` preserves current
111	  behavior — existing plugins compile unchanged.
112	- **Performance:** No change. The `Compiled` flag is always present.
113	  Additional options like `IgnoreCase` have negligible runtime impact.
114	- **Tests:** Add tests for: default options (Compiled only),
115	  IgnoreCase matching, combined options, IgnorePatternWhitespace.

11

14	This logic is useful to any plugin that needs to send batched IRC commands

1	# CS-017: Common HandlerContext Base Class
2	
3	**Source:** `TODO.md` item 7
4	**Scope:** Marv.Core.Plugin

6	**Breaking changes:** Source-compatible, binary-breaking (see Impact)
7	
8	---
9	
10	## Problem
11	
12	`CommandContext` and `RegexMatchContext` share five identical properties
13	(`Channel`, `Sender`, `IsDirect`, `RawMessage`, `Bot`) and an identical
14	`ReplyAsync` method. This duplication means:
15	
16	- Filter evaluators that need the sender or channel must cast
17	  `HandlerInvocation.Context` to each type separately (see the
18	  `FilterHandlerAsync` advanced example in CS-005, which switches on
19	  `CommandContext` vs `RegexMatchContext`).
20	- Any future context type (e.g., for a webhook or scheduled-message
21	  handler) must copy the same properties.
22	- The `Marv.Testing` builders (`CommandContextBuilder`,
23	  `RegexMatchContextBuilder`) duplicate the same fluent methods.
24	
25	## Decisions
26	
27	- Introduce an abstract `HandlerContext` base class with the shared
28	  properties and `ReplyAsync`.
29	- `CommandContext` and `RegexMatchContext` inherit from `HandlerContext`.
30	- `HandlerContext` is not sealed — downstream projects can subclass it for
31	  custom handler types.
32	- The `HandlerInvocation.Context` property type remains `object?` (not
33	  `HandlerContext?`) because interval and raw-message handlers do not
34	  receive a context with sender/channel. Filter evaluators that want
35	  the common properties can pattern-match on `HandlerContext` instead
36	  of switching on each concrete type.
37	
38	## Changes

40	### 1. Create `HandlerContext` base class

46	/// Base class for handler contexts that carry sender, channel, and message
47	/// information. Shared by <see cref="CommandContext"/> and
48	/// <see cref="RegexMatchContext"/>.
49	/// </summary>
50	public abstract class HandlerContext
51	{
52	    /// <summary>The channel the message was sent in, or null for DMs.</summary>
53	    public IChannel? Channel { get; init; }
54	
55	    /// <summary>The user who sent the message.</summary>
56	    public required IUser Sender { get; init; }
57	
58	    /// <summary>True if this is a direct (private) message to the bot.</summary>
59	    public bool IsDirect => Channel is null;
60	
61	    /// <summary>The underlying IRC message.</summary>
62	    public required IrcMessage RawMessage { get; init; }
63	
64	    /// <summary>The bot instance, used for sending replies.</summary>
65	    public required IBot Bot { get; init; }

68	    /// Sends a reply in context — to the channel if the message was in a
69	    /// channel, or directly to the sender if it was a private message.
70	    /// </summary>
71	    public Task ReplyAsync(string text, CancellationToken ct = default)

140	## Design decisions

143	method contains logic (choosing between channel and DM targets). An
144	interface would require each implementer to duplicate this logic or use a
145	default interface method, which is less discoverable in C#. A base class
146	also enables `is HandlerContext` pattern matching.
147	
148	**Why not change `HandlerInvocation.Context` to `HandlerContext?`?**
149	Interval handlers have no sender/channel context, and raw message handlers
150	receive an `IrcMessage` directly. Changing the type would require either
151	wrapping these in a `HandlerContext` subclass (adding unnecessary
152	ceremony) or making the property nullable with a different semantic. The
153	current `object?` type is accurate — filter evaluators pattern-match on
154	what they need.
155	
156	**Why not include `ReplyAsync` only on concrete types?** Every context
157	that has a sender and channel should support replying. Putting `ReplyAsync`
158	on the base class means any future context type (webhook events, scheduled
159	messages) gets reply support automatically. The reply logic is
160	deterministic from the channel/sender state, so there's no reason for
161	subtypes to override it.
162

169	  the old types need recompilation. Since Marv is pre-1.0 and plugins are
170	  compiled from source, this is acceptable.
171	- **Filter evaluators:** Can simplify sender/channel extraction to a
172	  single `HandlerContext` cast instead of switching on each type.
173	- **Tests:** Existing tests compile unchanged. Add tests that verify
174	  `HandlerContext` properties are accessible from both context types.

1	# CS-018: Remove PluginType from HandlerGroupAttribute
2	
3	**Source:** `TODO.md` item 8
4	**Scope:** Marv.Core.Plugin
5	**Complexity:** Small
6	**Breaking changes:** Yes (attribute constructor signature change)
7	
8	---
9	
10	## Problem
11	
12	`HandlerGroupAttribute` requires a `Type pluginType` constructor argument
13	that specifies which plugin owns the handler group:
14	
15	```csharp
16	[HandlerGroup(typeof(ModerationPlugin))]
17	public class ModerationAdminCommands { ... }
18	```
19	
20	This has several issues:
21	
22	1. **Redundancy:** Handler groups are discovered by scanning the plugin's
23	   own assembly. `DiscoverHandlerGroups` already filters by
24	   `attr.PluginType == pluginType` — but since the scan starts from the
25	   plugin's assembly, a handler group in that assembly can only belong to
26	   a plugin in the same assembly. The `PluginType` property duplicates
27	   information that the framework already knows.
28	
29	2. **Coupling:** The handler group must reference the concrete plugin
30	   class, creating a circular type dependency if the plugin also
31	   references the handler group. More practically, it means handler groups
32	   in a separate assembly (a possible future pattern) would need a
33	   project reference back to the plugin assembly just for the attribute.
34	
35	3. **Boilerplate:** Every handler group requires importing and specifying
36	   the plugin type, which is ceremony without value since there's only
37	   one plugin per assembly in practice.
38	
39	## Decisions
40	
41	- Remove the `Type pluginType` constructor parameter from
42	  `HandlerGroupAttribute`.
43	- `HandlerGroupAttribute` becomes a simple marker attribute with no
44	  required arguments.
45	- `DiscoverHandlerGroups` scans the plugin's assembly for any class
46	  marked with `[HandlerGroup]` and treats them all as belonging to the
47	  current plugin.
48	- If an assembly contains multiple plugins (an unusual but valid
49	  configuration), handler groups are associated with all plugins in the
50	  same assembly. This is acceptable — the scenario is rare and the
51	  handler group's handlers execute in the context of each plugin's
52	  dispatch loop. If more precise ownership is needed later, an optional
53	  `PluginType` property can be reintroduced.
54

55	## 3. Handler Attributes
56	
57	### `[OnCommand("name")]` → `Task Handler(CommandContext ctx, CancellationToken ct)`
58	
59	Fires when a message starts with `[prefix][command]`. Command matching is
60	case-insensitive. AllowMultiple — same method can handle multiple commands.
61	
62	| Property | Type | Default | Effect |
63	|---|---|---|---|
64	| `Prefix` | `string?` | bot's `CommandPrefix` | Override the command prefix |
65	| `ChannelOnly` | `bool` | `false` | Skip DMs |
66	| `DirectOnly` | `bool` | `false` | Skip channel messages |
67	| `Channel` | `string?` | `null` | Only fire in this channel (case-insensitive) |
68	
69	### `[OnRegex("pattern")]` → `Task Handler(RegexMatchContext ctx, CancellationToken ct)`
70	
71	Fires when message text (IRC formatting stripped) matches the pattern. Same
72	filter properties as `[OnCommand]` minus `Prefix`.
73	
74	### `[OnEvent]` → `Task Handler(TEvent evt, CancellationToken ct)`
75	
76	Event type is inferred from the first parameter (must extend `MarvEvent`).
77	
78	### `[OnRawMessage("COMMAND")]` → `Task Handler(IrcMessage msg, CancellationToken ct)`
79	
80	Fires for raw IRC messages with matching command. Use for protocol-level
81	handling not covered by typed events. VERSION, PING, TIME are handled
82	internally.
83	
84	### `[OnInterval(Seconds = 30)]` or `[OnInterval(Minutes = 5)]`
85	
86	→ `Task Handler(CancellationToken ct)`
87	
88	Fires on a timer while connected. Defaults to 1 minute if neither is set.
89	
90	> **Note:** All handler methods may omit the `CancellationToken` parameter.

namespace Marv.Core;

/// <summary>
/// Utility methods for working with IRC protocol constraints.
/// </summary>
public static class IrcUtils
{
    /// <summary>
    /// Splits a list of channel names into batches where each batch's
    /// comma-separated representation fits within
    /// <paramref name="maxPayloadLength"/> bytes. Useful for batching
    /// JOIN, MODE, and other channel-list commands within the 512-byte
    /// IRC line limit.
    /// </summary>
    /// <param name="channels">The channel names to batch.</param>
    /// <param name="maxPayloadLength">
    /// Maximum byte length for the comma-separated channel list.
    /// The caller must account for the command prefix and CRLF when
    /// computing this value (e.g., 512 - len("JOIN ") - len("\r\n")).
    /// </param>
    public static IEnumerable<List<string>> BatchChannels(
        IReadOnlyList<string> channels, int maxPayloadLength)
    {
        var batch = new List<string>();
        var currentLength = 0;

        foreach (var channel in channels)
        {
            var addedLength = batch.Count == 0
                ? channel.Length
                : channel.Length + 1; // +1 for comma separator

            if (currentLength + addedLength > maxPayloadLength && batch.Count > 0)
            {
                yield return batch;
                batch = [];
                currentLength = 0;
                addedLength = channel.Length;
            }

            batch.Add(channel);
            currentLength += addedLength;
        }

        if (batch.Count > 0)
            yield return batch;
    }
}

## Design decisions

**Why `Json5.Configuration` instead of a custom provider?** The package
provides exactly what we need — `AddJson5File` as a drop-in `AddJsonFile`
replacement with full JSON5 support (comments, trailing commas, unquoted
keys, single-quoted strings, etc.). Implementing our own provider would
duplicate work that's already been done and tested. The package is from
[devlooped](https://github.com/devlooped/json5), a reputable open-source
maintainer, targets .NET 8+ and is compatible with .NET 10.

**Why not just recommend YAML?** YAML is already supported and handles
comments natively. However, JSON is the default format, the example config
is JSON, and many operators prefer JSON's explicit syntax. Telling users
"switch to YAML for comments" is a workaround, not a solution.

**Why support `.json5` as an extension?** Some users may prefer to use the
`.json5` extension to signal that the file uses JSON5 features, and some
editors provide better syntax highlighting for `.json5` files. Supporting
both costs nothing since the parser handles both.
