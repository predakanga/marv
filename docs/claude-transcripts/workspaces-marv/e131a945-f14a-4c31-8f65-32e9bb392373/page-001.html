1	# CS-019: JSON5 Configuration Parser — COMPLETED
2	
3	**Source:** `TODO.md` item 9
4	**Scope:** Marv (host application)
5	**Complexity:** Trivial
6	**Breaking changes:** None
7	**Status:** Completed
8	
9	---
10	
11	## Problem
12	
13	The JSON configuration parser uses `Microsoft.Extensions.Configuration`'s
14	built-in `AddJsonFile`, which only supports strict JSON (RFC 8259). This
15	means configuration files cannot contain:
16	
17	- Comments (single-line `//` or block `/* */`)
18	- Trailing commas after the last element in arrays/objects
19	- Unquoted keys
20	- Single-quoted strings
21	- Multiline strings
22	
23	Comments are the most impactful limitation. Operators commonly want to
24	annotate their configuration files with explanations, comment out
25	sections for debugging, or leave notes about non-obvious settings. YAML
26	configuration already supports comments, but JSON is the default format
27	(the example config is `marv.example.json` and the default is
28	`marv.json`).
29	
30	## Decisions
31	
32	- Use the [`Json5.Configuration`](https://www.nuget.org/packages/Json5.Configuration)
33	  NuGet package, which provides `AddJson5File` — a drop-in replacement
34	  for `AddJsonFile` with full JSON5 support.
35	- Handle both `.json` and `.json5` extensions via `AddJson5File`, since
36	  JSON5 is a strict superset of JSON. Existing valid JSON files continue
37	  to work unchanged.
38	- The default configuration filename remains `marv.json`.
39	
40	## Changes

105	## Design decisions
106	
107	**Why `Json5.Configuration` instead of a custom provider?** The package
108	provides exactly what we need — `AddJson5File` as a drop-in `AddJsonFile`
109	replacement with full JSON5 support (comments, trailing commas, unquoted
110	keys, single-quoted strings, etc.). Implementing our own provider would
111	duplicate work that's already been done and tested. The package is from
112	[devlooped](https://github.com/devlooped/json5), a reputable open-source
113	maintainer, targets .NET 8+ and is compatible with .NET 10.
114	
115	**Why not just recommend YAML?** YAML is already supported and handles
116	comments natively. However, JSON is the default format, the example config
117	is JSON, and many operators prefer JSON's explicit syntax. Telling users
118	"switch to YAML for comments" is a workaround, not a solution.
119	
120	**Why support `.json5` as an extension?** Some users may prefer to use the
121	`.json5` extension to signal that the file uses JSON5 features, and some
122	editors provide better syntax highlighting for `.json5` files. Supporting
123	both costs nothing since the parser handles both.

2	
3	**Source:** GitHub issue #4
4	**Scope:** Host

10	
11	## Problem
12	
13	The host application (`Program.cs`) calls `builder.Configuration.Sources.Clear()`
14	and rebuilds the configuration stack from scratch, discarding the default .NET
15	providers (`appsettings.json`, `appsettings.{Environment}.json`, etc.). This is
16	surprising for users familiar with .NET conventions. Additionally,
17	`ConfigurationOptions` serves two purposes — generating CLI option definitions
18	and extracting overrides via `GetOverrides` — when it should only do the former.
19	
20	## Changes
21	
22	### 1. Preserve the default configuration stack
23	
24	Stop calling `builder.Configuration.Sources.Clear()`. Instead, walk the existing
25	`IConfigurationBuilder.Sources` and replace any `JsonConfigurationSource`
26	instances with JSON5 equivalents so that `appsettings.json` gains JSON5 comment
27	support for free.
28	
29	### 2. Add `marv.json` as a higher-priority source
30	
31	After the default stack is preserved, add `marv.json` (and any `--config`
32	override) as a JSON5 source layered on top, so Marv-specific settings take
33	precedence over `appsettings.json` defaults.
34	
35	### 3. Use the host builder's environment variable prefix
36	
37	Remove the manual `builder.Configuration.AddEnvironmentVariables("MARV_")` call.
38	Instead, configure the host builder's default environment variable provider with
39	the `MARV_` prefix via `builder.Configuration.AddEnvironmentVariables("MARV_")`
40	— or, if the default host builder already provides a way to set the prefix,
41	use that.
42	
43	> **Note:** The default `Host.CreateApplicationBuilder()` adds an unprefixed
44	> env var provider. If there is no built-in way to configure its prefix, keep
45	> the explicit `AddEnvironmentVariables("MARV_")` call but do not clear the
46	> default provider — let both coexist so that standard .NET env vars (e.g.
47	> `ASPNETCORE_ENVIRONMENT`) still work.
48	
49	### 4. Create a `CommandLineConfigurationProvider`
50	
51	Replace `ConfigurationOptions.GetOverrides()` and the `AddInMemoryCollection`
52	approach with a custom `IConfigurationProvider` that wraps the
53	`System.CommandLine.ParseResult`. This provider will:
54	
55	- Iterate the `Entry` list and extract explicitly-set CLI values.
56	- Present them as configuration keys, maintaining the same precedence (CLI
57	  overrides everything).
58	
59	This simplifies `ConfigurationOptions` to a single responsibility: generating
60	`Option<T>` definitions from `MarvConfiguration` properties.
61	
62	### 5. Remove `GetOverrides` and entry `Apply` methods
63	
64	Once the `CommandLineConfigurationProvider` is in place, remove:
65	
66	- `ConfigurationOptions.GetOverrides(ParseResult)`
67	- The `Apply` method on `Entry` and its subclasses (`ScalarEntry`, `BoolEntry`,
68	  `CollectionEntry`)
69	- The `AddInMemoryCollection` call in `Program.cs`
70	
71	`ConfigurationOptions` retains `Build()`, `All`, and the entry records (for
72	option metadata) but the records no longer need `Apply`.
73	
74	## Design decisions
75	
76	- **Preserve `marv.json` as the default config filename** rather than switching
77	  to `appsettings.json`. The owner confirmed this in issue discussion.
78	- **Layer order** (lowest to highest priority):
79	  1. Default .NET stack (`appsettings.json`, `appsettings.{Environment}.json`)
80	  2. `marv.json` (Marv-specific settings override appsettings defaults)
81	  3. Environment variables (`MARV_` prefix)
82	  4. CLI arguments (via `CommandLineConfigurationProvider`)
83	- **Custom provider over in-memory collection**: the `GetOverrides` +
84	  `AddInMemoryCollection` approach works but gives `ConfigurationOptions` two
85	  responsibilities. A dedicated provider is more idiomatic and single-purpose.
86

103	- **Risk:** Low. The configuration stack order is well-defined and testable.
104	  Existing users who only use `marv.json` + CLI args see no difference.

using Microsoft.Extensions.Configuration;
using Xunit;

namespace Marv.Core.Tests;

/// <summary>
/// Verifies that the built-in JSON configuration provider supports comments
/// and trailing commas — the features we rely on after removing Json5.Configuration.
/// </summary>
public class JsonConfigCommentTests : IDisposable
{
    private readonly string _tempFile = Path.GetTempFileName();

    public void Dispose() => File.Delete(_tempFile);

    [Fact]
    public void AddJsonFile_Supports_LineComments_And_TrailingCommas()
    {
        File.WriteAllText(_tempFile, """
            {
                // Line comment
                "Server": "irc.example.com",
                "Channels": [
                    "#general",
                    "#dev",
                ],
            }
            """);

        var config = new ConfigurationBuilder()
            .AddJsonFile(_tempFile, optional: false)
            .Build();

        Assert.Equal("irc.example.com", config["Server"]);
        Assert.Equal("#general", config["Channels:0"]);
        Assert.Equal("#dev", config["Channels:1"]);
    }

    [Fact]
    public void AddJsonFile_Supports_BlockComments()
    {
        File.WriteAllText(_tempFile, """
            {
                /* Block comment */
                "Nick": "Marv",
                "Port": 6697
            }
            """);

        var config = new ConfigurationBuilder()
            .AddJsonFile(_tempFile, optional: false)
            .Build();

        Assert.Equal("Marv", config["Nick"]);
        Assert.Equal("6697", config["Port"]);
    }
}
