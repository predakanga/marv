1	# CS-029: NuGet Packages for Marv.Core and Marv.Testing
2	
3	**Source:** GitHub issue #5
4	**Scope:** CI/CD + Core
5	**Complexity:** Small-Medium
6	**Breaking changes:** None
7	**Status:** Pending
8	
9	---
10	
11	## Problem
12	
13	Downstream plugin projects that depend on Marv.Core via `ProjectReference`
14	produce unversioned assemblies. When those plugins are loaded against the
15	versioned assemblies in published container images or binary releases
16	(e.g. Marv.Core v0.6.0), .NET throws assembly version mismatch errors.
17	
18	Publishing Marv.Core and Marv.Testing as NuGet packages allows downstream
19	projects to consume them via `PackageReference`, which resolves the version
20	correctly.
21	
22	## Changes
23	
24	### 1. Add NuGet package metadata to Marv.Core
25	
26	Add standard NuGet metadata properties to `src/Marv.Core/Marv.Core.csproj`:
27	
28	- `PackageId` (defaults to project name, but set explicitly for clarity)
29	- `Authors`
30	- `Description`
31	- `PackageLicenseExpression`
32	- `RepositoryUrl`
33	- `PackageReadmeFile` (optional — a short README for the NuGet listing)
34	
35	The `Version` is already set in `Directory.Build.props` and will be inherited.
36	
37	### 2. Add NuGet package metadata to Marv.Testing
38	
39	Add the same metadata properties to `src/Marv.Testing/Marv.Testing.csproj`.
40	Marv.Testing already has a `<Description>` element. NSubstitute remains a
41	dependency — it is required by `MockBot`, `MockUser`, and `MockChannel`
42	which return NSubstitute proxies.
43	
44	### 3. Mark non-packable projects
45	
46	Add `<IsPackable>false</IsPackable>` to `Directory.Build.props` as the
47	default, then override it to `true` in the two packable projects. This
48	prevents the host app, example plugins, and test projects from being
49	accidentally packed.
50	
51	### 4. Add a `publish-nuget` job to the release workflow
52	
53	Add a new job to `.github/workflows/release.yml` that runs alongside the
54	existing `publish-binaries` and `docker` jobs (after `wait-for-ci` and
55	`version`):
56	
57	```yaml
58	publish-nuget:
59	  runs-on: ubuntu-latest
60	  needs: [wait-for-ci, version]
61	  steps:
62	    - uses: actions/checkout@v4
63	    - uses: actions/setup-dotnet@v4
64	      with:
65	        dotnet-version: 10.0.x
66	    - run: |
67	        VERSION=${{ needs.version.outputs.version }}
68	        dotnet pack src/Marv.Core/Marv.Core.csproj -c Release -p:Version="$VERSION" -o packages/
69	        dotnet pack src/Marv.Testing/Marv.Testing.csproj -c Release -p:Version="$VERSION" -o packages/
70	    - run: |
71	        dotnet nuget push packages/*.nupkg \
72	          --source "https://nuget.pkg.github.com/predakanga/index.json" \
73	          --api-key ${{ secrets.GITHUB_TOKEN }}
74	```
75	
76	Packages are published to **GitHub Packages only** (not nuget.org).
77	Publishing occurs only on tagged releases (the workflow already triggers
78	on `v*` tags).
79	
80	### 5. Update the `github-release` job dependency
81	
82	Add `publish-nuget` to the `needs` list of the `github-release` job so
83	that the GitHub release is only created after all artifacts (binaries,
84	Docker image, and NuGet packages) are published successfully.
85	
86	## Design decisions
87	
88	- **GitHub Packages only:** The project already uses GitHub Container
89	  Registry for Docker images. GitHub Packages provides a consistent
90	  experience and avoids the nuget.org API key management overhead.
91	  Publishing to nuget.org can be added later if there is demand.
92	- **Default `IsPackable=false`:** Safer than marking individual projects
93	  as non-packable — new projects are non-packable by default, reducing
94	  the risk of accidental publishing.
95	- **Tagged releases only:** No pre-release packages from CI. This keeps
96	  the feed clean and avoids version confusion for downstream consumers.
97	
98	## Testing
99	
100	- Run `dotnet pack` locally for both projects and verify `.nupkg` files
101	  are produced with correct metadata (`dotnet nuget inspect` or extract
102	  the `.nuspec` from the package).
103	- Verify that non-packable projects (host, plugins, tests) produce a
104	  build warning or error when `dotnet pack` is attempted.
105	- After a tagged release, verify packages appear in the GitHub Packages
106	  feed at `https://github.com/predakanga/marv/packages`.
107	- Test downstream consumption: create a test project that uses
108	  `PackageReference` for Marv.Core, build a plugin DLL, and load it
109	  against the published Marv binary.
110	
111	## Impact
112	
113	- **Plugin API:** No changes to the plugin API surface.
114	- **DX:** Downstream plugin authors can consume Marv.Core and
115	  Marv.Testing via standard NuGet tooling instead of git submodules or
116	  ProjectReference workarounds.
117	- **Risk:** Low — this adds a publishing step without changing any
118	  existing code or behaviour. The only risk is misconfigured NuGet
119	  metadata, which would result in a failed publish (caught by CI).

1	# CS-029: NuGet Packages for Marv.Core and Marv.Testing
2	
3	**Source:** GitHub issue #5
4	**Scope:** CI/CD + Core
5	**Complexity:** Small-Medium
6	**Breaking changes:** None
7	**Status:** Pending
8	
9	---
10	
11	## Problem
12	
13	Downstream plugin projects that depend on Marv.Core via `ProjectReference`
14	produce unversioned assemblies. When those plugins are loaded against the
15	versioned assemblies in published container images or binary releases
16	(e.g. Marv.Core v0.6.0), .NET throws assembly version mismatch errors.
17	
18	Publishing Marv.Core and Marv.Testing as NuGet packages allows downstream
19	projects to consume them via `PackageReference`, which resolves the version
20	correctly.
21	
22	## Changes
23	
24	### 1. Add NuGet package metadata to Marv.Core
25	
26	Add standard NuGet metadata properties to `src/Marv.Core/Marv.Core.csproj`:
27	
28	- `PackageId` (defaults to project name, but set explicitly for clarity)
29	- `Authors`
30	- `Description`
31	- `PackageLicenseExpression`
32	- `RepositoryUrl`
33	- `PackageReadmeFile` (optional — a short README for the NuGet listing)
34	
35	The `Version` is already set in `Directory.Build.props` and will be inherited.
36	
37	### 2. Add NuGet package metadata to Marv.Testing
38	
39	Add the same metadata properties to `src/Marv.Testing/Marv.Testing.csproj`.
40	Marv.Testing already has a `<Description>` element. NSubstitute remains a
41	dependency — it is required by `MockBot`, `MockUser`, and `MockChannel`
42	which return NSubstitute proxies.
43	
44	### 3. Mark non-packable projects
45	
46	Add `<IsPackable>false</IsPackable>` to `Directory.Build.props` as the
47	default, then override it to `true` in the two packable projects. This
48	prevents the host app, example plugins, and test projects from being
49	accidentally packed.
50	
51	### 4. Add a `publish-nuget` job to the release workflow
52	
53	Add a new job to `.github/workflows/release.yml` that runs alongside the
54	existing `publish-binaries` and `docker` jobs (after `wait-for-ci` and
55	`version`):
56	
57	```yaml
58	publish-nuget:
59	  runs-on: ubuntu-latest
60	  needs: [wait-for-ci, version]
61	  steps:
62	    - uses: actions/checkout@v4
63	    - uses: actions/setup-dotnet@v4
64	      with:
65	        dotnet-version: 10.0.x
66	    - run: |
67	        VERSION=${{ needs.version.outputs.version }}
68	        dotnet pack src/Marv.Core/Marv.Core.csproj -c Release -p:Version="$VERSION" -o packages/
69	        dotnet pack src/Marv.Testing/Marv.Testing.csproj -c Release -p:Version="$VERSION" -o packages/
70	    - run: |
71	        dotnet nuget push packages/*.nupkg \
72	          --source "https://nuget.pkg.github.com/predakanga/index.json" \
73	          --api-key ${{ secrets.GITHUB_TOKEN }}
74	```
75	
76	Packages are published to **GitHub Packages only** (not nuget.org).
77	Publishing occurs only on tagged releases (the workflow already triggers
78	on `v*` tags).
79	
80	### 5. Simplify release binary artifacts
81	
82	Now that Marv.Core and Marv.Testing are available as NuGet packages,
83	the release artifact for each platform is just the Marv executable — no
84	plugins directory or other files are needed. Replace the tar.gz archive
85	with the bare executable: remove the `mkdir -p plugins` step, the
86	`Archive` step, and upload the executable directly as the release
87	artifact. Update the `github-release` job's `files` glob accordingly.
88	
89	### 6. Update the `github-release` job dependency
90	
91	Add `publish-nuget` to the `needs` list of the `github-release` job so
92	that the GitHub release is only created after all artifacts (binaries,
93	Docker image, and NuGet packages) are published successfully.
94	
95	## Design decisions
96	
97	- **GitHub Packages only:** The project already uses GitHub Container
98	  Registry for Docker images. GitHub Packages provides a consistent
99	  experience and avoids the nuget.org API key management overhead.
100	  Publishing to nuget.org can be added later if there is demand.
101	- **Default `IsPackable=false`:** Safer than marking individual projects
102	  as non-packable — new projects are non-packable by default, reducing
103	  the risk of accidental publishing.
104	- **Tagged releases only:** No pre-release packages from CI. This keeps
105	  the feed clean and avoids version confusion for downstream consumers.
106	- **Bare executable, no archive:** With NuGet packages available, the
107	  release artifact is just the executable per platform — no archive
108	  wrapping needed. Simpler to download and deploy.
109	
110	## Testing
111	
112	- Run `dotnet pack` locally for both projects and verify `.nupkg` files
113	  are produced with correct metadata (`dotnet nuget inspect` or extract
114	  the `.nuspec` from the package).
115	- Verify that non-packable projects (host, plugins, tests) produce a
116	  build warning or error when `dotnet pack` is attempted.
117	- After a tagged release, verify packages appear in the GitHub Packages
118	  feed at `https://github.com/predakanga/marv/packages`.
119	- Test downstream consumption: create a test project that uses
120	  `PackageReference` for Marv.Core, build a plugin DLL, and load it
121	  against the published Marv binary.
122	- Verify the per-platform executable uploads correctly as a GitHub
123	  release asset and is directly downloadable.
124	
125	## Impact
126	
127	- **Plugin API:** No changes to the plugin API surface.
128	- **DX:** Downstream plugin authors can consume Marv.Core and
129	  Marv.Testing via standard NuGet tooling instead of git submodules or
130	  ProjectReference workarounds.
131	- **Risk:** Low — this adds a publishing step without changing any
132	  existing code or behaviour. The only risk is misconfigured NuGet
133	  metadata, which would result in a failed publish (caught by CI).
