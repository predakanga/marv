1	# Upstream Authorization for Marv — Design Options
2	
3	Analysis of how Marv could support declarative authorization for plugin
4	handlers, examining six approaches: attribute-based `[RequireAuth]`,
5	a virtual `FilterHandler` override, a hybrid, a middleware pipeline,
6	self-evaluating filter attributes, and `[RequireAuth]` with a dynamic
7	policy object.
8	
9	---
10	
11	## Background: Current State
12	
13	### Marv's Existing Auth Surface
14	
15	Marv ships a minimal `IAuthorizationService` in `Marv.Plugins.Auth`:
16	
17	```csharp
18	public interface IAuthorizationService
19	{
20	    Task<bool> IsAuthorizedAsync(IUser user, string permission, CancellationToken ct);
21	}
22	```
23	
24	The bundled implementation (`AccountBasedAuthService`) checks IRC
25	services account names against a configured admin list — a single
26	binary check with no permission hierarchy.
27	
28	### How We Use Authorization
29	
30	We do not use Marv's `IAuthorizationService` at all. We have our
31	own `IUserAuthService` which returns an `AuthResult` containing
32	`UserId`, `Username`, `UserClass`, and `IsAdmin`. Authorization
33	decisions are made through four distinct patterns:
34	
35	| Pattern | Description | Used by |
36	|---|---|---|
37	| **A — Admin flag** | `auth.IsAdmin` (derived from hostmask class) | BanManagement, GeoIp, Gline, UserMod, Lookup, Twitter |
38	| **B — Hostmask class** | `HostmaskParser.IsAdminClass(class)` without full auth | StaffAccess, BotCommandHandlers |
39	| **C — Permission level** | DB query for `permissions.Level >= N` | Gline (≥700), Search (≥100), Calc (≥100), UserInfo |
40	| **D — Nick list** | `BotAdmins` config list | BotCommandHandlers (join/part/say/die) |
41	| **E — Staff channel** | Allow if message is in the staff channel | Combined with A in 6 plugins |
42	
43	Most handlers combine patterns — the typical guard is "admin OR in
44	staff channel" (A+E), and Gline requires both admin status (A) and a
45	minimum permission level (C) for staff protection checks.
46	
47	### Key Observation
48	
49	Our authorization is fundamentally different from Marv's bundled auth.
50	Any upstream mechanism must accommodate both — and unknown future
51	projects with their own models.

55	## Approach 1: Attribute-Based `[RequireAuth]`
56	
57	### Design
58	
59	Add an attribute that declares authorization requirements on handler
60	methods. The `MarvPlugin` dispatch loop checks this attribute before
61	invoking the handler:
62	
63	```csharp
64	[AttributeUsage(AttributeTargets.Method, AllowMultiple = true)]
65	public sealed class RequireAuthAttribute(string permission) : Attribute
66	{
67	    public string Permission { get; } = permission;
68	}
69	```
70	
71	Usage in a handler:
72	
73	```csharp
74	[OnCommand("ban")]
75	[RequireAuth("admin")]
76	public async Task HandleBan(CommandContext ctx, CancellationToken ct) { ... }
77	```
78	
79	The dispatch loop in `MarvPlugin.InvokeHandlerSafe` would check for
80	`[RequireAuth]` attributes and call `IAuthorizationService` before
81	invoking the handler. If authorization fails, the handler is skipped
82	(or a configurable denial message is sent).
83	
84	### Strengths
85	
86	- **Declarative and discoverable.** Authorization requirements are
87	  visible at the method signature, not buried in the first 10 lines
88	  of the method body.
89	- **Zero boilerplate per handler.** No manual auth check code needed.
90	- **Familiar pattern.** Matches ASP.NET `[Authorize]`, Discord.NET
91	  `[RequireUserPermission]`, DSharpPlus `[RequirePermissions]`.
92	- **Framework-enforced.** Can't forget to check — the attribute
93	  prevents the handler from running at all.
94	
95	### Weaknesses
96	
97	#### 1. The Permission String Problem
98	
99	The attribute takes a `string permission`, but what does that string
100	mean? In Marv's bundled auth, it's ignored entirely —
101	`AccountBasedAuthService.IsAuthorizedAsync` returns true for admins
102	regardless of the permission string.
103	
104	For us, the natural permissions would be:
105	
106	```csharp
107	[RequireAuth("admin")]              // Pattern A: IsAdmin check
108	[RequireAuth("level:100")]          // Pattern C: permission level ≥ 100
109	[RequireAuth("level:700")]          // Pattern C: permission level ≥ 700
110	[RequireAuth("bot-admin")]          // Pattern D: nick in BotAdmins list
111	```
112	
113	But this embeds authorization model semantics into string conventions.
114	A project using RBAC would want `[RequireAuth("moderator")]`. A
115	project using OAuth scopes would want `[RequireAuth("channels:manage")]`.
116	The attribute is universal, but the permission strings are
117	project-specific — there's no way for the framework to validate them.
118	
119	#### 2. Compound Conditions Don't Fit
120	
121	Our most common pattern is "admin OR staff channel" — a disjunction
122	of two different checks. This doesn't map cleanly to a single attribute:
123	
124	```csharp
125	// Option A: Two attributes = AND (both required)? Or OR?
126	[RequireAuth("admin")]
127	[RequireAuth("staff-channel")]
128	
129	// Option B: Special syntax in the string?
130	[RequireAuth("admin|staff-channel")]
131	
132	// Option C: A separate attribute?
133	[RequireAuthAny("admin", "staff-channel")]
134	```
135	
136	All of these are awkward. The fundamental issue is that authorization
137	policies are often more complex than "does the user have permission X?"
138	— they involve context (which channel?), combinations (admin OR
139	channel), and cascading checks (admin, then also check level for
140	certain operations).
141	
142	#### 3. Context-Dependent Authorization
143	
144	Some of our authorization depends on the handler's arguments or the
145	command context:
146	
147	- Gline checks if the **target** user has a higher permission level
148	  than the **invoker** — this requires running the handler's argument
149	  parsing first.
150	- UserInfo returns different amounts of information based on the
151	  invoker's permission level — authorization isn't binary.
152	- BotCommandHandlers checks the nick list only for specific
153	  sub-commands (join, part, say, die, restart).
154	
155	`[RequireAuth]` can only express "can this user invoke this method at
156	all?" — not "can this user invoke this method with these arguments?"
157	
158	#### 4. Denial Response Customization
159	
160	When authorization fails, what happens? Options:
161	
162	1. **Silent skip** — handler doesn't run, no response. Bad UX.
163	2. **Generic "Permission denied"** — acceptable but impersonal.
164	3. **Custom denial** — "You need to be at least Power User (level
165	   100) to use this command." Requires the auth service to provide
166	   the denial reason, which couples the framework to the auth model.
167	
168	We currently send custom denial messages from within handlers.
169	An attribute-based system would need a way to customize this — perhaps
170	a `DenialMessage` property on the attribute, or a
171	`FormatDenialAsync` method on `IAuthorizationService`.
172	
173	### Verdict
174	
175	**Good for simple, universal authorization (admin-or-not).** Becomes
176	increasingly awkward as authorization models grow more complex. Works
177	well as a complement to other approaches (handle the simple cases
178	declaratively, handle complex cases in code).
179

182	## Approach 2: Virtual `FilterHandler` on MarvPlugin
183	
184	### Design
185	
186	Add a virtual method to `MarvPlugin` that is called before every
187	handler invocation:
188	
189	```csharp
190	public abstract class MarvPlugin
191	{
192	    /// <summary>
193	    /// Called before each handler invocation. Return false to prevent the
194	    /// handler from running. The implementation may send its own response
195	    /// (e.g. a "permission denied" message).
196	    /// </summary>
197	    protected virtual ValueTask<bool> FilterHandlerAsync(
198	        HandlerInvocation invocation, CancellationToken ct)
199	    {
200	        return ValueTask.FromResult(true);
201	    }
202	}
203	```
204	
205	Where `HandlerInvocation` provides the handler metadata and context:
206	
207	```csharp
208	public readonly struct HandlerInvocation
209	{
210	    /// <summary>The handler method that will be invoked.</summary>
211	    public MethodInfo Method { get; init; }
212	
213	    /// <summary>The target object (plugin or handler group instance).</summary>
214	    public object Target { get; init; }
215	
216	    /// <summary>The handler type (Command, Regex, Event, RawMessage, Interval).</summary>
217	    public HandlerType Type { get; init; }
218	
219	    /// <summary>
220	    /// The context object that will be passed to the handler.
221	    /// Cast to CommandContext, RegexMatchContext, or the event type as needed.
222	    /// </summary>
223	    public object Context { get; init; }
224	
225	    /// <summary>
226	    /// All custom attributes on the handler method.
227	    /// Useful for reading project-specific attributes (e.g. [RequireLevel(100)]).
228	    /// </summary>
229	    public IReadOnlyList<Attribute> Attributes { get; init; }
230	}
231	```
232	
233	A project like ours would create a base class:
234	
235	```csharp
236	public abstract class SamplePlugin : MarvPlugin
237	{
238	    private readonly IUserAuthService _auth;
239	
240	    protected SamplePlugin(IBot bot, IPluginActivator activator,
241	        ILoggerFactory loggerFactory, IUserAuthService auth)
242	        : base(bot, activator, loggerFactory)
243	    {
244	        _auth = auth;
245	    }
246	
247	    protected override async ValueTask<bool> FilterHandlerAsync(
248	        HandlerInvocation invocation, CancellationToken ct)
249	    {
250	        // Read project-specific attributes
251	        var requireLevel = invocation.Attributes
252	            .OfType<RequireLevelAttribute>()
253	            .FirstOrDefault();
254	
255	        if (requireLevel == null)
256	            return true; // No auth required
257	
258	        // Get the sender from whichever context type
259	        var sender = invocation.Context switch
260	        {
261	            CommandContext cmd => cmd.Sender,
262	            RegexMatchContext regex => regex.Sender,
263	            _ => null
264	        };
265	
266	        if (sender == null)
267	            return true;
268	
269	        var auth = await _auth.AuthenticateAsync(sender, ct);
270	        if (auth.IsAdmin)
271	            return true;
272	
273	        // Check permission level
274	        // ... query DB for level, compare to requireLevel.MinLevel
275	
276	        // Send denial
277	        if (invocation.Context is CommandContext ctx)
278	            await ctx.ReplyAsync("Permission denied.");
279	
280	        return false;
281	    }
282	}
283	```
284	
285	We would then define our own attributes:
286	
287	```csharp
288	[AttributeUsage(AttributeTargets.Method)]
289	public sealed class RequireLevelAttribute(int minLevel) : Attribute
290	{
291	    public int MinLevel { get; } = minLevel;
292	}
293	
294	[AttributeUsage(AttributeTargets.Method)]
295	public sealed class RequireAdminAttribute : Attribute;
296	
297	[AttributeUsage(AttributeTargets.Method)]
298	public sealed class StaffChannelBypassAttribute : Attribute;
299	```
300	
301	And use them on handlers:
302	
303	```csharp
304	[OnCommand("ban")]
305	[RequireAdmin]
306	[StaffChannelBypass]
307	public async Task HandleBan(CommandContext ctx, CancellationToken ct) { ... }
308	
309	[OnCommand("gline")]
310	[RequireLevel(700)]
311	public async Task HandleGline(CommandContext ctx, CancellationToken ct) { ... }
312	```
313	
314	### Strengths
315	
316	#### 1. Fully Flexible Authorization Model
317	
318	The plugin project defines its own attributes and its own
319	`FilterHandlerAsync` logic. RBAC, integer levels, capability flags,
320	OAuth scopes — any model works. The framework doesn't need to
321	understand the semantics.
322	
323	#### 2. Context-Aware Filtering
324	
325	`FilterHandlerAsync` receives the full invocation context, so it can
326	inspect the channel, the sender, the arguments — anything needed for
327	the authorization decision.
328	
329	#### 3. Not Just Authorization
330	
331	The same mechanism supports other cross-cutting concerns:
332	- **Channel filtering:** Skip handlers that should only run in
333	  specific channels (replaces the ubiquitous
334	  `if (ctx.IsDirect) return;` guard).
335	- **Rate limiting:** Track invocation frequency per user.
336	- **Logging/auditing:** Log all command invocations centrally.
337	- **Cooldowns:** Prevent command spam.
338	
339	#### 4. Single Override Point
340	
341	One method in the base class handles all filtering. Plugin authors
342	write handlers that focus on business logic — the authorization is
343	handled uniformly by the base class.
344	
345	#### 5. Incremental Adoption
346	
347	Projects that don't need filtering just don't override the method.
348	Existing plugins continue to work unchanged.
349	
350	### Weaknesses
351	
352	#### 1. Boilerplate for Plugin Authors
353	
354	The primary concern. To use this pattern, a plugin project must:
355	
356	1. Create a base class (`ExplorationPlugin : MarvPlugin`)
357	2. Override `FilterHandlerAsync` with the project's auth logic
358	3. Define custom attributes
359	4. Update all plugin constructors to inject auth services and pass
360	   them to the base class
361	5. Update all handler group constructors if they need to participate
362	
363	This is a significant amount of infrastructure code. For a project
364	with 2-3 plugins, it's arguably not worth it — you'd write more
365	framework code than you save in handler guards.
366	
367	**Mitigation:** This is a one-time cost per project, and it pays
368	off as the number of plugins and handlers grows. We have 16 plugins
369	with ~30 authorized handlers — the base class approach saves
370	~5 lines per handler at the cost of ~50 lines of base class setup.
371	The break-even point is around 10 authorized handlers.
372	
373	#### 2. Handler Groups Complicate the Picture
374	
375	Handler groups are instantiated by `IPluginActivator` and their
376	handlers are dispatched by the owning plugin. `FilterHandlerAsync`
377	would naturally apply to handler group methods too — but the handler
378	group might need its own authorization logic.
379	
380	The `HandlerInvocation.Target` field distinguishes the plugin from
381	its handler groups, so the filter can branch on this. But it means
382	the base class must understand the handler group's authorization
383	needs, which could get complicated.
384	
385	**Mitigation:** Handler groups could define their own attributes and
386	the base class reads them the same way. Since `invocation.Attributes`
387	contains the method's attributes regardless of which class defines
388	the method, this works naturally.
389	
390	#### 3. Authorization Happens Before Argument Parsing
391	
392	Some handlers need to parse arguments before making authorization
393	decisions (e.g. Gline checks the target user's level).
394	`FilterHandlerAsync` runs before the handler, so it doesn't have
395	access to parsed arguments.
396	
397	This is inherent to any pre-handler filter. Handlers with
398	argument-dependent authorization would still need inline checks.
399	
400	**Mitigation:** Document this as a known limitation. In practice,
401	this affects only Gline's staff protection check — the primary "can
402	the user invoke this at all?" check still works in the filter.
403	
404	#### 4. Reflection-Based Attribute Reading
405	
406	Reading `invocation.Attributes` on every handler call involves
407	attribute reflection. This is cheap (attributes are cached by the
408	CLR after first read), but it's a pattern that some developers find
409	surprising in hot paths.
410	
411	**Mitigation:** Pre-read attributes during handler discovery and
412	store them in the handler registration. The `HandlerInvocation` then
413	carries the pre-computed list.
414	
415	#### 5. Virtual Method on Every Dispatch
416	
417	Every handler invocation — including regex handlers that fire on
418	every message — would call `FilterHandlerAsync`. The base
419	implementation returns `true` immediately, but the virtual call
420	dispatch still has a cost.
421	
422	**Mitigation:** The cost is negligible. A virtual method call is
423	~2ns. IRC bots process maybe 100 messages/second at peak.
424	
425	### Implementation in MarvPlugin
426	
427	The change to `MarvPlugin` is small. In `InvokeHandlerSafe`:
428	
429	```csharp
430	private async Task InvokeHandlerSafe(
431	    object target, MethodInfo method, object arg, CancellationToken ct)
432	{
433	    try
434	    {
435	        var invocation = new HandlerInvocation
436	        {
437	            Method = method,
438	            Target = target,
439	            Type = /* determined from registration */,
440	            Context = arg,
441	            Attributes = _attributeCache.GetOrAdd(method,
442	                m => m.GetCustomAttributes(true).Cast<Attribute>().ToList())
443	        };
444	
445	        if (!await FilterHandlerAsync(invocation, ct))
446	            return;
447	
448	        await InvokeHandler(target, method, arg, ct);
449	    }
450	    catch ...
451	}
452	```
453	
454	This is roughly 10 lines of framework code plus the
455	`HandlerInvocation` struct (~20 lines) and the `HandlerType` enum
456	(~5 lines). Minimal framework surface change.
457	
458	### Verdict
459	
460	**The most flexible approach.** Accommodates any authorization model
461	without the framework needing to understand it. The cost is
462	up-front boilerplate for plugin projects — worth it for projects
463	with many handlers, potentially not for small projects.
464

467	## Approach 3: Hybrid — Framework Attribute + Virtual Filter
468	
469	### Design
470	
471	Provide *both* mechanisms:
472	
473	1. A simple `[RequireAuth("permission")]` attribute in Marv.Core that
474	   uses `IAuthorizationService` for the common case.
475	2. A virtual `FilterHandlerAsync` for projects that need custom
476	   authorization logic.
477	
478	The dispatch order:
479	
480	```
481	1. FilterHandlerAsync (custom project logic)
482	2. [RequireAuth] check via IAuthorizationService (framework logic)
483	3. Handler invocation
484	```
485	
486	Or reversed — `FilterHandlerAsync` could run *after* the framework
487	check, acting as an additional layer. The order depends on whether
488	project-specific filters should be able to override the framework
489	check (allow even if `[RequireAuth]` would deny) or only restrict
490	further (deny even if `[RequireAuth]` would allow).
491	
492	### The Problem: Two Systems to Learn
493	
494	This combines the weaknesses of both approaches:
495	
496	- Plugin authors must understand both `[RequireAuth]` and
497	  `FilterHandlerAsync` to know which to use.
498	- The interaction between them (ordering, override semantics) adds
499	  cognitive load.
500	- A project like ours would likely ignore `[RequireAuth]`
501	  entirely and use only `FilterHandlerAsync`, making the attribute
502	  dead weight.
503	- A project using only `[RequireAuth]` would never touch
504	  `FilterHandlerAsync`, making the virtual method dead weight.
505	
506	### When It Works
507	
508	The hybrid shines if Marv establishes a standard permission model
509	that most projects use, while `FilterHandlerAsync` serves as an
510	escape hatch. If Marv's `IAuthorizationService` evolves to support
511	permission hierarchies and the `[RequireAuth]` attribute covers 80%
512	of use cases, the filter handles the remaining 20%.
513	
514	But that's a bet on the future shape of Marv's auth — and the
515	exploration experience suggests that projects will bring their own
516	authorization models.
517	
518	### Verdict
519	
520	**Not recommended as a starting point.** If `[RequireAuth]` proves
521	sufficient for most projects, `FilterHandlerAsync` can always be
522	added later. If `FilterHandlerAsync` is needed from the start,
523	`[RequireAuth]` adds complexity without pulling its weight. Pick one
524	and add the other only if a concrete need emerges.
525

528	## Approach 4 (Bonus): Middleware Pipeline
529	
530	### Design
531	
532	Instead of a single virtual method, implement a middleware pipeline
533	similar to ASP.NET Core:
534	
535	```csharp
536	public abstract class MarvPlugin
537	{
538	    protected void UseMiddleware<T>() where T : IHandlerMiddleware;
539	}
540	
541	public interface IHandlerMiddleware
542	{
543	    Task InvokeAsync(HandlerInvocation invocation,
544	        Func<Task> next, CancellationToken ct);
545	}
546	```
547	
548	Projects compose middleware:
549	
550	```csharp
551	public class AuthMiddleware(IUserAuthService auth) : IHandlerMiddleware
552	{
553	    public async Task InvokeAsync(HandlerInvocation invocation,
554	        Func<Task> next, CancellationToken ct)
555	    {
556	        if (!await Authorize(invocation, ct))
557	            return;
558	        await next();
559	    }
560	}
561	```
562	
563	### Why Not
564	
565	This is overengineered for an IRC bot framework. The middleware
566	pipeline pattern is valuable when you have many independent
567	cross-cutting concerns that compose arbitrarily (ASP.NET: auth,
568	CORS, routing, compression, logging). An IRC bot plugin typically
569	has one cross-cutting concern: authorization. Building a pipeline
570	infrastructure for one middleware is a poor trade-off.
571	
572	If a second cross-cutting concern emerges (rate limiting, auditing),
573	`FilterHandlerAsync` can still handle it — it's just one virtual
574	method, not a single-concern system.
575	
576	### Verdict
577	
578	**Over-engineered.** Revisit if three or more independent
579	cross-cutting concerns emerge.

583	## Approach 5: Self-Evaluating Filter Attributes
584	
585	### Design
586	
587	Each filter attribute carries a `Type` reference to its own evaluator
588	class. The framework discovers `IFilteringAttribute` on handler methods,
589	resolves the evaluator from the DI container, and calls it. No base
590	class override needed — the framework handles all plumbing.
591	
592	```csharp
593	// Framework-provided interfaces
594	public interface IFilterEvaluator
595	{
596	    ValueTask<bool> FilterAsync(IFilteringAttribute attr,
597	        HandlerInvocation invocation, CancellationToken ct);
598	}
599	
600	public interface IFilteringAttribute
601	{
602	    Type Evaluator { get; }
603	}
604	```
605	
606	A project defines attribute + evaluator pairs:
607	
608	```csharp
609	// Attribute — declares the requirement
610	[AttributeUsage(AttributeTargets.Method)]
611	public sealed class RequireLevelAttribute(int level)
612	    : Attribute, IFilteringAttribute
613	{
614	    public int Level { get; } = level;
615	    public Type Evaluator => typeof(RequireLevelFilter);
616	}
617	
618	// Evaluator — implements the check, resolved from DI
619	public class RequireLevelFilter(IUserLevelService svc) : IFilterEvaluator
620	{
621	    public async ValueTask<bool> FilterAsync(
622	        IFilteringAttribute attr, HandlerInvocation invocation,
623	        CancellationToken ct)
624	    {
625	        if (attr is not RequireLevelAttribute levelAttr)
626	            return true;
627	
628	        var sender = invocation.Context switch
629	        {
630	            CommandContext cmd => cmd.Sender,
631	            RegexMatchContext regex => regex.Sender,
632	            _ => null
633	        };
634	        if (sender == null) return true;
635	
636	        var level = await svc.GetUserLevelAsync(sender, ct);
637	        return level >= levelAttr.Level;
638	    }
639	}
640	```
641	
642	Usage on handlers:
643	
644	```csharp
645	[OnCommand("gline")]
646	[RequireLevel(700)]
647	public async Task HandleGline(CommandContext ctx, CancellationToken ct) { ... }
648	```
649	
650	The `MarvPlugin` dispatch loop:
651	
652	1. During handler discovery, scan each method for `IFilteringAttribute`
653	   instances and cache them alongside the handler registration.
654	2. Before invoking a handler, iterate its cached filter attributes.
655	3. For each, resolve the `Evaluator` type from the DI container
656	   (or via `IPluginActivator`) and call `FilterAsync`.
657	4. If any evaluator returns `false`, skip the handler.
658	
659	### Type-Safe Variant with Generics
660	
661	The base interface requires a cast from `IFilteringAttribute` to the
662	concrete type. A generic version eliminates this:
663	
664	```csharp
665	// Non-generic for framework dispatch
666	public interface IFilterEvaluator
667	{
668	    ValueTask<bool> FilterAsync(IFilteringAttribute attr,
669	        HandlerInvocation invocation, CancellationToken ct);
670	}
671	
672	// Generic for plugin authors — provides type-safe bridge
673	public abstract class FilterEvaluator<TAttribute> : IFilterEvaluator
674	    where TAttribute : Attribute, IFilteringAttribute
675	{
676	    public ValueTask<bool> FilterAsync(IFilteringAttribute attr,
677	        HandlerInvocation invocation, CancellationToken ct)
678	        => FilterAsync((TAttribute)attr, invocation, ct);
679	
680	    protected abstract ValueTask<bool> FilterAsync(TAttribute attr,
681	        HandlerInvocation invocation, CancellationToken ct);
682	}
683	
684	// Plugin author implements the generic version
685	public class RequireLevelFilter(IUserLevelService svc)
686	    : FilterEvaluator<RequireLevelAttribute>
687	{
688	    protected override async ValueTask<bool> FilterAsync(
689	        RequireLevelAttribute attr, HandlerInvocation invocation,
690	        CancellationToken ct)
691	    {
692	        // No cast needed — attr is already RequireLevelAttribute
693	        var sender = (invocation.Context as CommandContext)?.Sender;
694	        if (sender == null) return true;
695	        return await svc.GetUserLevelAsync(sender, ct) >= attr.Level;
696	    }
697	}
698	```
699	
700	### Strengths
701	
702	1. **No base class required.** Plugin authors define attributes and
703	   register evaluator services. No `ExplorationPlugin : MarvPlugin`
704	   needed. This directly addresses the boilerplate concern from
705	   Approach 2.
706	
707	2. **Open/closed.** New filter types are added by writing an attribute
708	   + evaluator pair. No existing code changes. No base class grows
709	   a new `if` branch.
710	
711	3. **Composable.** Multiple `IFilteringAttribute`s on one method are
712	   naturally AND'd. Each evaluator is independent and testable.
713	
714	4. **DI-native.** Evaluators inject whatever services they need. Same
715	   pattern plugin authors already know from handler groups.
716	
717	5. **Discoverable.** The attribute on the method tells you what's
718	   required; the `Evaluator` type tells you where the logic lives.
719	
720	### Weaknesses
721	
722	#### 1. OR Conditions Are Awkward
723	
724	Our most common pattern is "admin OR staff channel." Multiple
725	attributes are naturally AND'd. To express OR, you'd need either:
726	
727	- **Grouping:** `[RequireAdmin(Group = "access")]`,
728	  `[StaffChannelBypass(Group = "access")]` — same-group attributes
729	  are OR'd. Adds framework complexity (group tracking, evaluation
730	  semantics).
731	- **Composite attribute:** A single `[RequireAdminOrStaffChannel]`
732	  with one evaluator. Defeats composability.
733	- **Evaluator handles disjunction internally:** The evaluator checks
734	  multiple conditions. But then the attribute declaration doesn't
735	  fully describe the policy.
736	
737	This is the pattern's most significant limitation for our needs.
738	
739	#### 2. Event Type Breadth
740	
741	The evaluator receives a `HandlerInvocation` with the context as
742	`object`. Handlers fire on `CommandContext`, `RegexMatchContext`,
743	typed events (`UserJoinedEvent`), `IrcMessage` (raw), or nothing
744	(intervals). Evaluators must handle the types they care about and
745	pass through the rest. This is workable but requires each evaluator
746	to include a `switch`/`is` check on the context type.
747	
748	#### 3. Denial Responses
749	
750	The evaluator returns `bool` but can't send a reply. Options:
751	
752	- Return a richer type: `FilterResult { Allowed, DenialMessage? }`
753	- Give the evaluator access to the bot/context for sending
754	- Add `GetDenialMessage()` to `IFilteringAttribute`
755	
756	Each adds framework surface area. The simplest is probably a
757	`FilterResult` struct with an optional message, and have `MarvPlugin`
758	send it via the appropriate reply mechanism.
759	
760	#### 4. Evaluator Lifecycle
761	
762	When are evaluators resolved? Options:
763	
764	- **Per-invocation:** Correct scoping but allocates on every handler
765	  call. For an IRC bot, the volume is low enough that this is fine.
766	- **Per-plugin (cached):** Resolve once during `OnLoadAsync`,
767	  store in a dictionary keyed by evaluator type. More efficient
768	  but assumes singleton-like evaluators.
769	- **DI-managed lifetime:** Register evaluators as services, let the
770	  DI container control lifetime. Most idiomatic but requires
771	  evaluators to be registered in `ConfigureServices`.
772	
773	Recommendation: resolve per-plugin (cache after first resolution).
774	Evaluators that inject services will naturally share the service's
775	lifetime.
776	
777	#### 5. Two Artifacts Per Filter
778	
779	Every filter requires both an attribute class and an evaluator class.
780	For our ~5 filter types, that's 10 classes plus service
781	registrations. More boilerplate than `FilterHandlerAsync` (1 base
782	class + 5 attribute classes = 6 files), though each individual file
783	is smaller and more focused.
784	
785	#### 6. Framework Surface Area
786	
787	The framework needs:
788	- `IFilteringAttribute` interface (~5 lines)
789	- `IFilterEvaluator` interface (~5 lines)
790	- `FilterEvaluator<T>` abstract base class (~15 lines)
791	- `FilterResult` struct (~10 lines)
792	- Resolution and caching logic in `MarvPlugin` (~30 lines)
793	- Changes to `InvokeHandlerSafe` (~10 lines)
794	
795	**Total: ~75-100 lines.** More than `FilterHandlerAsync` (~48 lines)
796	but still modest.
797	
798	### Compared to FilterHandlerAsync
799	
800	| Concern | FilterHandler | Self-evaluating attribute |
801	|---|---|---|
802	| Base class required | Yes | No |
803	| OR conditions | Natural (code) | Needs grouping mechanism |
804	| New filter type | Add branch to override | Add attribute + evaluator |
805	| Framework surface | ~48 lines | ~80-100 lines |
806	| Plugin author artifacts | 1 base class + N attributes | 2N classes (attr + evaluator) |
807	| Denial messages | Direct (has context) | Needs `FilterResult` or similar |
808	| Event type coverage | Natural (cast in one place) | Each evaluator handles types |
809	| Testability | Test the base class | Test each evaluator independently |
810	
811	### Verdict
812	
813	**Strong alternative to `FilterHandlerAsync`.** Eliminates the base
814	class requirement at the cost of the OR-condition problem and slightly
815	more framework surface. Best suited for projects with simple AND-only
816	authorization. Projects needing disjunctive policies (like our
817	"admin OR staff channel") would find it awkward.
818	
819	### Possible Synthesis
820	
821	Ship `FilterHandlerAsync` *and* the self-evaluating attribute
822	infrastructure, where the **default** `FilterHandlerAsync`
823	implementation checks for `IFilteringAttribute` and evaluates them.
824	This avoids the hybrid problem from Approach 3 because the attribute
825	system is implemented *via* the filter method, not as a parallel
826	mechanism:
827	
828	```csharp
829	// In MarvPlugin — the default implementation
830	protected virtual async ValueTask<bool> FilterHandlerAsync(
831	    HandlerInvocation invocation, CancellationToken ct)
832	{
833	    foreach (var attr in invocation.Attributes.OfType<IFilteringAttribute>())
834	    {
835	        var evaluator = ResolveEvaluator(attr.Evaluator);
836	        if (!await evaluator.FilterAsync(attr, invocation, ct))
837	            return false;
838	    }
839	    return true;
840	}
841	```
842	
843	- Simple projects use self-evaluating attributes and never touch
844	  `FilterHandlerAsync`.
845	- Complex projects (needing OR logic, context mutation, etc.)
846	  override `FilterHandlerAsync` and handle it themselves — they
847	  can still read `IFilteringAttribute` if they want, or ignore
848	  the system entirely.
849	- The two mechanisms compose naturally because one is built on top
850	  of the other.

854	## Approach 6: `[RequireAuth]` with Dynamic Policy Object
855	
856	### The Question
857	
858	Can we avoid the string permission problem from Approach 1 by passing
859	a dynamic or structured object to `[RequireAuth]` instead?
860	
861	### C# Attribute Parameter Constraints
862	
863	C# attributes can only carry values of these types in their
864	constructor or property initializers:
865	
866	- Primitive types (`bool`, `int`, `string`, etc.)
867	- `System.Type`
868	- Enum types
869	- One-dimensional arrays of the above
870	
871	You **cannot** pass:
872	- Class instances (`new AdminPolicy()`)
873	- Anonymous types (`new { Level = 100 }`)
874	- Interfaces
875	- Records or structs (unless they're enum-valued)
876	- `dynamic` or `object` with non-primitive values
877	
878	This is a CLR limitation, not a C# language choice — attribute
879	arguments must be compile-time constants embeddable in metadata.
880	
881	### What Can Be Done Within the Constraints
882	
883	#### Option A: Named Properties on the Attribute
884	
885	```csharp
886	[RequireAuth(Admin = true)]
887	[RequireAuth(MinLevel = 100)]
888	[RequireAuth(Admin = true, StaffChannelBypass = true)]
889	```
890	
891	Implementation:
892	
893	```csharp
894	public sealed class RequireAuthAttribute : Attribute
895	{
896	    public bool Admin { get; init; }
897	    public int MinLevel { get; init; }
898	    public bool StaffChannelBypass { get; init; }
899	    public string? Permission { get; init; }
900	}
901	```
902	
903	**Problem:** Every project's authorization concepts must be
904	properties on this one attribute. We need `Admin`, `MinLevel`,
905	`StaffChannelBypass`. An RBAC project needs `Role`. An OAuth
906	project needs `Scope`. The attribute becomes a union of all
907	possible authorization models — it's `RequireAuth` trying to
908	be everything to everyone.
909	
910	Adding a new property to support a new project means changing the
911	framework. This is the opposite of extensible.
912	
913	#### Option B: `Type` as Policy Reference
914	
915	```csharp
916	[RequireAuth(typeof(AdminPolicy))]
917	[RequireAuth(typeof(LevelPolicy), Level = 100)]
918	```
919	
920	Implementation:
921	
922	```csharp
923	public sealed class RequireAuthAttribute(Type policyType) : Attribute
924	{
925	    public Type PolicyType { get; } = policyType;
926	
927	    // Optional parameters for the policy — but what shape are they?
928	    public int Level { get; init; }
929	    public string? Role { get; init; }
930	}
931	```
932	
933	**Problem:** This is essentially the self-evaluating attribute
934	pattern (Approach 5) with a worse API. The policy type reference
935	is the same as `IFilteringAttribute.Evaluator`. But the optional
936	parameters (`Level`, `Role`) are back to the union problem — the
937	attribute must pre-declare every property any policy might need.
938	
939	If we instead make the parameters generic:
940	
941	```csharp
942	[RequireAuth(typeof(LevelPolicy), Args = new object[] { 100 })]
943	```
944	
945	This compiles (arrays of primitives are allowed) but is stringly-
946	typed and fragile. The policy has to parse `Args[0]` as an int and
947	hope the caller got it right.
948	
949	#### Option C: Enum-Based Policy Selector
950	
951	```csharp
952	public enum AuthPolicy { Admin, Level100, Level700, StaffBypass }
953	
954	[RequireAuth(AuthPolicy.Admin)]
955	[RequireAuth(AuthPolicy.Level100)]
956	```
957	
958	**Problem:** Every authorization check must be a member of the enum.
959	New levels or policies require changing the enum — again, framework
960	changes for project-specific needs. And the enum can't carry
961	parameters (you can't express "level ≥ N" for arbitrary N).
962	
963	#### Option D: Policy Interface + `Type` (No Attribute Parameters)
964	
965	```csharp
966	public interface IAuthPolicy
967	{
968	    ValueTask<bool> EvaluateAsync(HandlerInvocation invocation,
969	        CancellationToken ct);
970	}
971	
972	[RequireAuth(typeof(AdminOrStaffChannelPolicy))]
973	public async Task HandleBan(...) { ... }
974	```
975	
976	Where `AdminOrStaffChannelPolicy : IAuthPolicy` is resolved from DI
977	and contains all the logic.
978	
979	**This is exactly Approach 5** (self-evaluating attributes), just
980	with the attribute named `[RequireAuth]` instead of a custom name.
981	The only difference is cosmetic — the attribute doesn't carry
982	parameters because the policy class handles everything internally.
983	
984	This actually *loses* information compared to Approach 5, because
985	`[RequireLevel(700)]` tells you the threshold at the call site,
986	while `[RequireAuth(typeof(Level700Policy))]` either bakes the
987	threshold into the class name or hides it inside the implementation.
988	
989	### Verdict
990	
991	**The dynamic object idea doesn't work within C# attribute
992	constraints.** Every attempt to make `[RequireAuth]` carry
993	structured authorization requirements either:
994	
995	1. Embeds all possible project models into one attribute (Option A)
996	   — violates extensibility.
997	2. Uses `Type` as an indirection to a policy class (Options B, D)
998	   — reinvents the self-evaluating attribute pattern with a less
999	   expressive API.
1000	3. Uses enums (Option C) — too rigid for parameterized checks.
1001	4. Uses `object[]` (Option B variant) — loses type safety.
1002	
1003	The fundamental issue is that C# attributes are static metadata.
1004	Authorization policies are runtime logic. Bridging these requires
1005	either a `Type` reference to runtime code (which is what Approach 5
1006	already does, better) or moving the logic out of attributes entirely
1007	(which is what Approach 2 does).
1008	
1009	---
1010	
1011	## Recommendation
1012	
1013	**Implement `FilterHandlerAsync` (Approach 2) with built-in
1014	`IFilteringAttribute` support (from Approach 5).**
1015	
1016	This is the synthesis described at the end of Approach 5: the default
1017	`FilterHandlerAsync` implementation scans for `IFilteringAttribute`
1018	and evaluates them via their associated evaluator classes. Projects
1019	with simple AND-only filters never touch `FilterHandlerAsync` — they
1020	just use self-evaluating attributes. Projects with complex needs
1021	(OR conditions, context mutation, custom denial messages) override
1022	`FilterHandlerAsync` and handle it themselves.
1023	
1024	Reasoning:
1025	
1026	1. **Marv shouldn't prescribe an authorization model.** The framework
1027	   doesn't know whether its users will implement RBAC, integer
1028	   levels, capability flags, or hostmask-based class checks.
1029	   `[RequireAuth("permission")]` forces projects to map their model
1030	   into a string-based permission check — a leaky abstraction.
1031	   Using `Type` as a dynamic policy object doesn't help (see
1032	   Approach 6) — it's just Approach 5 with a less expressive API.
1033	
1034	2. **Two tiers of complexity.** Simple projects use self-evaluating
1035	   attributes (no base class, just attribute + evaluator pairs).
1036	   Complex projects override `FilterHandlerAsync` for full control.
1037	   Both work through the same mechanism — no parallel systems to
1038	   learn.
1039	
1040	3. **The boilerplate concern is addressed at both tiers.** The
1041	   attribute tier requires no base class at all. The override tier
1042	   requires a base class but only for projects that genuinely need
1043	   OR-logic or other complex filters — and those projects will have
1044	   enough handlers to justify the cost.
1045	
1046	4. **It's more than authorization.** The same mechanism naturally
1047	   handles channel filtering (`if (ctx.IsDirect) return;`), which
1048	   is the other ubiquitous guard in our project. Two problems solved
1049	   by one mechanism.
1050	
1051	5. **It's additive.** Adding `FilterHandlerAsync` doesn't break any
1052	   existing plugins. It's a virtual method with a default
1053	   implementation that evaluates `IFilteringAttribute`s. The
1054	   framework surface change is modest (~80-100 lines including the
1055	   self-evaluating attribute infrastructure).
1056	
1057	6. **No `[RequireAuth]` needed.** The self-evaluating attribute
1058	   pattern makes `[RequireAuth]` unnecessary. Each project defines
1059	   attributes that carry their own semantics (`[RequireLevel(100)]`,
1060	   `[RequireRole("moderator")]`, `[RequireScope("channels:manage")]`)
1061	   — the framework doesn't need a universal `[RequireAuth]` that
1062	   tries to express all models.
1063	
1064	### Minimal Framework Changes Required
1065	
1066	1. Add `HandlerInvocation` struct to `Marv.Core.Plugin` (~20 lines)
1067	2. Add `HandlerType` enum to `Marv.Core.Plugin` (~5 lines)
1068	3. Add `IFilteringAttribute` interface to `Marv.Core.Plugin` (~5 lines)
1069	4. Add `IFilterEvaluator` interface to `Marv.Core.Plugin` (~5 lines)
1070	5. Add `FilterEvaluator<T>` abstract base class (~15 lines)
1071	6. Add `FilterHandlerAsync` virtual method to `MarvPlugin` with
1072	   default `IFilteringAttribute` evaluation (~20 lines)
1073	7. Modify `InvokeHandlerSafe` to call `FilterHandlerAsync` (~5 lines)
1074	8. Add evaluator resolution and caching in `MarvPlugin` (~20 lines)
1075	9. Pre-cache attributes in handler discovery (~10 lines)
1076	
1077	**Total: ~105 lines of framework code.** No new dependencies. No
1078	breaking changes. Two interfaces, one abstract base class, one
1079	struct, one enum, and one virtual method.

1083	## Open Questions for Implementation
1084	
1085	1. **Should handler groups participate in filtering?** If a handler
1086	   group class also overrides `FilterHandlerAsync`, whose filter
1087	   runs? The plugin's or the group's? Recommendation: only the
1088	   plugin's filter runs, since handler groups are owned by the
1089	   plugin and shouldn't have independent authorization.
1090	
1091	2. **Should `FilterHandlerAsync` receive the handler registration
1092	   metadata** (e.g. the matched command name, the regex pattern)?
1093	   This is available from the registration but not currently part
1094	   of `HandlerInvocation`. It could be useful for logging but adds
1095	   to the struct size.
1096	
1097	3. **Error handling:** If `FilterHandlerAsync` throws, should the
1098	   handler still run? Recommendation: treat it like a handler
1099	   exception — log and skip the handler. This is the safe default.

# CS-001: Command Prefix Configuration

**Source:** `downstream_suggestions/improvements.md` §4
**Scope:** Marv.Core
**Complexity:** Small
**Breaking changes:** None

---

## Problem

`MarvConfiguration.CommandPrefix` already exists (defaults to `"!"`) but is
unused. Command parsing in `MarvPlugin.DispatchCommandHandlers` (line 167) is
hardcoded to `'!'` with a TODO comment. Downstream projects that want a
different prefix (e.g. `.`) must use `[OnRegex]` workarounds.

## Changes

### 1. Wire up the existing config property

In `MarvPlugin`, inject or access `MarvConfiguration.CommandPrefix` and use it
in `DispatchCommandHandlers` instead of the hardcoded `'!'`.

**`MarvPlugin.cs` — DispatchCommandHandlers:**

Replace:
```csharp
if (text.Length < 2 || text[0] != '!')
    return;
```

With:
```csharp
var prefix = Bot.Configuration.CommandPrefix;
if (text.Length < prefix.Length + 1 || !text.StartsWith(prefix, StringComparison.Ordinal))
    return;
```

And adjust the command/arg extraction slice indices accordingly (replace `1`
with `prefix.Length`).

### 2. Expose CommandPrefix on IBot or via DI

`MarvPlugin` currently accesses `Bot` (an `IBot`), which does not expose the
configuration. Options:

- **Option A:** Add `CommandPrefix` property to `IBot`. Minimal surface; this
  is the only config property plugins need at runtime.
- **Option B:** Add `IOptions<MarvConfiguration>` as a constructor parameter
  to `MarvPlugin`. Heavier; exposes all config to all plugins.
- **Option C:** Inject `IOptions<MarvConfiguration>` in `MarvPlugin`
  internally via `IPluginActivator` during construction. No API change for
  plugin authors but adds hidden coupling.

**Recommendation:** Option A — add `string CommandPrefix { get; }` to `IBot`.
It's the most discoverable and keeps the plugin API clean. Plugin authors who
want to parse commands differently (multi-prefix, etc.) can read this property.

### 3. Support multi-character prefixes

The current implementation uses a single `char` comparison. Switching to
`string.StartsWith` (as shown above) naturally supports multi-character
prefixes like `!!` or `marv:`. No additional design work needed.

### 4. Multiple prefixes (deferred)

The downstream suggestion mentions supporting multiple prefixes. This can be
deferred — it's a nice-to-have that adds complexity (array config, iteration
in dispatch). If needed later, `CommandPrefix` could become `CommandPrefixes`
(string array) with a minor API evolution.

## Impact

- **Plugin API:** Adds `CommandPrefix` to `IBot` (additive, non-breaking).
- **Configuration:** Existing `CommandPrefix` property becomes functional.
  Default `"!"` preserves backward compatibility.
- **Tests:** Add test for custom prefix dispatch. Update any tests that
  depend on the hardcoded `'!'`.

## Open questions

1. Should the prefix be case-sensitive? Recommendation: yes (ordinal
   comparison), since IRC commands are conventionally case-sensitive after
   the prefix.

# CS-002: Handler Dispatch Filters

**Source:** `downstream_suggestions/improvements.md` §1
**Scope:** Marv.Core
**Complexity:** Small
**Breaking changes:** None (additive properties on existing attributes)

---

## Problem

Nearly every command and regex handler begins with a channel/DM guard:

```csharp
if (ctx.IsDirect) return;          // channel-only handler
if (!ctx.IsDirect) return;         // DM-only handler
if (ctx.Channel?.Name != "#ops")   // channel-specific handler
    return;
```

This is repetitive boilerplate that the framework can handle declaratively.

## Changes

### 1. Add filter properties to `OnCommandAttribute`

```csharp
[AttributeUsage(AttributeTargets.Method, AllowMultiple = true, Inherited = false)]
public sealed class OnCommandAttribute(string command) : Attribute
{
    public string Command { get; } = command;

    /// <summary>
    /// If true, handler only fires for channel messages (skips DMs).
    /// </summary>
    public bool ChannelOnly { get; init; }

    /// <summary>
    /// If true, handler only fires for direct/private messages (skips channel).
    /// </summary>
    public bool DirectOnly { get; init; }

    /// <summary>
    /// If set, handler only fires when the message is in this channel.
    /// Case-insensitive comparison using the server's case mapping.
    /// </summary>
    public string? Channel { get; init; }
}
```

### 2. Add the same properties to `OnRegexAttribute`

Same three properties: `ChannelOnly`, `DirectOnly`, `Channel`.

### 3. Apply filters in dispatch

**`MarvPlugin.DispatchCommandHandlers`** — after matching the command name
and before creating the `CommandContext`, check the filter properties:

```csharp
if (handler.ChannelOnly && msgEvt.Channel is null)
    continue;
if (handler.DirectOnly && msgEvt.Channel is not null)
    continue;
if (handler.Channel is not null
    && !string.Equals(msgEvt.Channel?.Name, handler.Channel,
        StringComparison.OrdinalIgnoreCase))
    continue;
```

Same logic in `DispatchRegexHandlers`.

### 4. Store filter values in registration records

The existing `CommandRegistration` and `RegexRegistration` records need the
filter values copied from the attribute at discovery time:

```csharp
private sealed record CommandRegistration(
    object Target, MethodInfo Method, string Command,
    bool ChannelOnly, bool DirectOnly, string? Channel);
```

### 5. Validation at discovery time

Warn (via logger) if both `ChannelOnly` and `DirectOnly` are set on the same
attribute — the handler would never fire. Similarly, warn if `Channel` is set
alongside `DirectOnly` (contradictory).

## Usage

```csharp

[OnCommand("identify", DirectOnly = true)]
```

channels with `{|}~` characters, which are rare. Can be refined later.

# CS-003: Handler Filter Pipeline

**Source:** `downstream_suggestions/authorization.md` (full analysis)
**Scope:** Marv.Core.Plugin
**Complexity:** Medium
**Breaking changes:** None (additive virtual method + new interfaces)
**Depends on:** CS-002 (handler dispatch filters provide the attribute-level
context this builds on)

---

## Problem

Plugins need cross-cutting handler logic — primarily authorization, but also
rate limiting, auditing, and custom channel filtering. Currently this must be
implemented as boilerplate at the top of every handler method. The downstream
analysis evaluated six approaches and recommends a synthesis of approaches 2
and 5: a virtual `FilterHandlerAsync` method whose default implementation
evaluates self-describing filter attributes.

## Design

Two tiers of complexity for two audiences:

1. **Simple tier:** Plugin authors define attribute + evaluator pairs. The
   framework evaluates them automatically. No base class override needed.
2. **Advanced tier:** Plugin projects override `FilterHandlerAsync` for full
   control (OR conditions, context-dependent auth, custom denial messages).

The simple tier is implemented *via* the advanced tier — the default
`FilterHandlerAsync` implementation scans for `IFilteringAttribute` and
calls their evaluators. This avoids the "two parallel systems" problem.

## Changes to MarvPlugin

### 1. Pre-cache attributes during handler discovery

In `DiscoverHandlers`, after registering each handler, also cache all custom
attributes on the method. Store as a `IReadOnlyList<Attribute>` in the
registration record (or a parallel `Dictionary<MethodInfo, IReadOnlyList<Attribute>>`).

### 2. Add FilterHandlerAsync virtual method

```csharp
/// <summary>
/// Called before each handler invocation. Return false to skip the handler.
/// The default implementation evaluates any <see cref="IFilteringAttribute"/>
/// attributes on the handler method.
/// </summary>
protected virtual async ValueTask<bool> FilterHandlerAsync(
    HandlerInvocation invocation, CancellationToken ct)
{
    foreach (var attr in invocation.Attributes.OfType<IFilteringAttribute>())
    {
        var evaluator = ResolveEvaluator(attr.EvaluatorType);
        var result = await evaluator.EvaluateAsync(attr, invocation, ct);
        if (!result.IsAllowed)
        {
            if (result.DenialMessage is not null)
                await SendDenialReply(invocation, result.DenialMessage, ct);
            return false;
        }
    }
    return true;
}
```

### 3. Modify InvokeHandlerSafe

Add a `HandlerType` parameter and construct `HandlerInvocation` before
calling the handler:

```csharp
private async Task InvokeHandlerSafe(
    object target, MethodInfo method, object? arg,
    HandlerType type, CancellationToken ct)
{
    try
    {
        var invocation = new HandlerInvocation
        {
            Method = method,
            Target = target,
            Type = type,
            Context = arg,
            Attributes = GetCachedAttributes(method)
        };

        if (!await FilterHandlerAsync(invocation, ct))
            return;

        await InvokeHandler(target, method, arg!, ct);
    }
    catch (OperationCanceledException) when (ct.IsCancellationRequested)
    {
        throw;
    }
    catch (Exception ex)
    {
        Logger.LogError(ex, "Handler {Type}.{Method} threw an exception",
            target.GetType().Name, method.Name);
    }
}
```

### 4. Evaluator resolution and caching

Resolve evaluators via `IPluginActivator.CreateInstance<T>()` on first use,
then cache them for the plugin's lifetime in a
`Dictionary<Type, IFilterEvaluator>`. This gives evaluators DI-injected
dependencies while avoiding per-invocation allocation.

### 5. Denial reply helper

A private `SendDenialReply` method that inspects the context type:

```csharp
private async Task SendDenialReply(
    HandlerInvocation invocation, string message, CancellationToken ct)
{
    switch (invocation.Context)
    {
        case CommandContext ctx:
            await ctx.ReplyAsync(message, ct);
            break;
        case RegexMatchContext ctx:
            await ctx.ReplyAsync(message, ct);
            break;

}
```

## Design decisions

### Why not a middleware pipeline?

Overengineered for the typical IRC bot use case. One or two cross-cutting
concerns don't justify pipeline infrastructure. `FilterHandlerAsync` can
handle multiple concerns in a single override. Revisit if three or more
independent concerns emerge across multiple downstream projects.

### Why not `[RequireAuth]` in the framework?

The permission string is meaningless without knowing the auth model. Every
downstream project brings its own authorization model. The framework should
not prescribe one — `IFilteringAttribute` lets each project define its own
semantics. See the full analysis in `downstream_suggestions/authorization.md`.

### Handler groups and filtering

`FilterHandlerAsync` runs on the owning plugin, not the handler group. The
`HandlerInvocation.Target` field distinguishes the plugin from its groups,
so the filter can branch if needed. Handler groups should not independently
override filtering — they are owned by their plugin.

### FilterHandlerAsync exceptions

If `FilterHandlerAsync` throws, treat it like a handler exception: log the
error and skip the handler. This is the safe default — a broken filter
should not allow a handler to run unguarded.

# CS-005: Bulk Channel Join

**Source:** `downstream_suggestions/improvements.md` §5
**Scope:** Marv.Core
**Complexity:** Small-Medium
**Breaking changes:** None (additive API)

---

## Problem

When the bot needs to join multiple channels (post-authentication, or when a
plugin requests joins), it currently sends individual `JOIN` commands in a
loop. This is slow due to outbound rate limiting and generates unnecessary
traffic. IRC allows comma-separated channel lists in a single `JOIN` command.

## Changes

### 1. Add `JoinMultipleAsync` to `IBot`

```csharp
/// <summary>
/// Joins multiple channels in a single IRC JOIN command.
/// Channel names are comma-separated per RFC 2812.
/// </summary>
Task JoinMultipleAsync(
    IReadOnlyList<string> channels,
    CancellationToken ct);
```

### 2. Implementation in MarvBot

Construct a single `JOIN` command with comma-separated channel names:

```csharp
public async Task JoinMultipleAsync(
    IReadOnlyList<string> channels, CancellationToken ct)
{
    if (channels.Count == 0) return;

    // IRC line length limit is 512 bytes. Batch channels to fit.
    // "JOIN " = 5 bytes, "\r\n" = 2 bytes, leaves 505 for channel list.
    const int maxLineLength = 505;
    var batch = new List<string>();
    var currentLength = 0;

    foreach (var channel in channels)
    {
        var addedLength = batch.Count == 0
            ? channel.Length
            : channel.Length + 1; // +1 for comma

        if (currentLength + addedLength > maxLineLength && batch.Count > 0)
        {
            await SendJoinBatch(batch, ct);
            batch.Clear();
            currentLength = 0;
            addedLength = channel.Length;
        }

        batch.Add(channel);
        currentLength += addedLength;
    }

    if (batch.Count > 0)
        await SendJoinBatch(batch, ct);
}

private Task SendJoinBatch(List<string> channels, CancellationToken ct)
{
    var joined = string.Join(',', channels);
    return SendRawAsync(new IrcMessage("JOIN", [joined]), ct);
}
```

### 3. Use in core channel join logic

The bot's post-authentication channel join (which iterates
`MarvConfiguration.Channels`) should use `JoinMultipleAsync` instead of
looping over `JoinAsync`.

### 4. Channel keys

The simple version above doesn't handle per-channel keys. Two options:

- **Option A:** Overload that accepts `(channel, key?)` tuples. Channels
  with keys must be first in the JOIN command per RFC 2812.
- **Option B:** Only batch keyless channels. Channels with keys use
  individual `JoinAsync` calls.

**Recommendation:** Option B for now. Key-protected channels are uncommon
in bot deployments. The primary win is batching the bulk of keyless channels.

## Slipstream / coalescing (deferred)

The downstream suggestion mentions a slipstream approach: maintaining a
pending join list and coalescing joins into a single message when flushed.
This is a good idea for generalization (could apply to WHO, MODE, etc.) but
raises layering concerns — the connection layer would need awareness of
pending commands.

**Recommendation:** Defer coalescing. `JoinMultipleAsync` gives the caller
explicit control over batching without complicating the connection layer. If
coalescing proves necessary, it can be added as a connection-level feature
later without changing the `IBot` API.

## Impact

- **Plugin API:** Adds one method to `IBot`. Additive, non-breaking.
- **Core behavior:** Initial channel join becomes a single IRC command
  instead of N individual commands. Faster startup, less rate-limit
  pressure.
- **Tests:** Add unit test for batching logic (line-length splitting).
  Integration test for multi-channel join.

# CS-001: Command Prefix Configuration

**Source:** `downstream_suggestions/improvements.md` §4
**Scope:** Marv.Core
**Complexity:** Small
**Breaking changes:** None

---

## Problem

`MarvConfiguration.CommandPrefix` already exists (defaults to `"!"`) but is
unused. Command parsing in `MarvPlugin.DispatchCommandHandlers` (line 167) is
hardcoded to `'!'` with a TODO comment. Downstream projects that want a
different prefix (e.g. `.`) must use `[OnRegex]` workarounds.

## Decisions

- Expose `CommandPrefix` as a property on `IBot`.
- Support multi-character prefixes (e.g. `"!!"`, `"marv:"`).
- Prefix matching is case-sensitive (ordinal comparison).
- `[OnCommand]` gains a `Prefix` property to override the bot-wide default
  on a per-handler basis.

## Changes

### 1. Add `CommandPrefix` to `IBot`

```csharp
/// <summary>The configured command prefix (e.g. "!").</summary>
string CommandPrefix { get; }
```

The `MarvBot` implementation returns the value from
`MarvConfiguration.CommandPrefix`.

### 2. Add `Prefix` property to `OnCommandAttribute`

```csharp
[AttributeUsage(AttributeTargets.Method, AllowMultiple = true, Inherited = false)]
public sealed class OnCommandAttribute(string command) : Attribute
{
    /// <summary>The command name to match (without the prefix).</summary>
    public string Command { get; } = command;

    /// <summary>
    /// Overrides the bot-wide command prefix for this handler.
    /// When null, the bot's configured <see cref="IBot.CommandPrefix"/> is used.
    /// </summary>
    public string? Prefix { get; init; }
}
```

Usage:

```csharp
// Uses the bot-wide prefix (default "!")
[OnCommand("ban")]
public async Task HandleBan(CommandContext ctx, CancellationToken ct) { ... }

// Uses "." regardless of bot-wide prefix
[OnCommand("invite", Prefix = ".")]
public async Task HandleInvite(CommandContext ctx, CancellationToken ct) { ... }
```

### 3. Store resolved prefix in `CommandRegistration`

Copy the effective prefix into the registration record at discovery time.
The per-handler `Prefix` property takes precedence; fall back to
`Bot.CommandPrefix` if null.

Since handler discovery happens in the `MarvPlugin` constructor (before
connection), the bot-wide prefix is available from config at construction
time.

```csharp
private sealed record CommandRegistration(
    object Target, MethodInfo Method, string Command, string Prefix);
```

During discovery:

```csharp
foreach (var cmdAttr in method.GetCustomAttributes<OnCommandAttribute>())
{
    _commandHandlers.Add(new CommandRegistration(
        target,
        method,
        cmdAttr.Command.ToLowerInvariant(),
        cmdAttr.Prefix ?? Bot.CommandPrefix));
}
```

### 4. Update `DispatchCommandHandlers`

Replace the current hardcoded prefix check with per-handler prefix matching.
Since different handlers may have different prefixes, the prefix check moves
inside the handler loop:

```csharp
private async Task DispatchCommandHandlers(MessageEvent msgEvt, CancellationToken ct)
{
    if (_commandHandlers.Count == 0)
        return;

    var text = IrcFormat.Strip(msgEvt.Text);

    foreach (var handler in _commandHandlers)
    {
        var prefix = handler.Prefix;

        if (text.Length < prefix.Length + 1
            || !text.StartsWith(prefix, StringComparison.Ordinal))
            continue;

        var afterPrefix = text.AsSpan(prefix.Length);
        var spaceIndex = afterPrefix.IndexOf(' ');
        var command = spaceIndex < 0
            ? afterPrefix.ToString().ToLowerInvariant()
            : afterPrefix[..spaceIndex].ToString().ToLowerInvariant();

        if (command != handler.Command)
            continue;

        var argString = spaceIndex < 0
            ? ""
            : afterPrefix[(spaceIndex + 1)..].ToString().TrimStart();
        var args = string.IsNullOrEmpty(argString)
            ? Array.Empty<string>()
            : argString.Split(' ', StringSplitOptions.RemoveEmptyEntries);

        var ctx = new CommandContext
        {
            Command = command,
            Args = args,
            ArgString = argString,
            Channel = msgEvt.Channel,
            Sender = msgEvt.Sender,
            RawMessage = msgEvt.RawMessage,
            Bot = Bot
        };

        await InvokeHandlerSafe(handler.Target, handler.Method, ctx, ct);
    }
}
```

**Performance note:** The current implementation does prefix matching and
command extraction once, then iterates handlers matching only on command name.
The new version does prefix matching per handler. This is fine for IRC
volumes, but if the handler count grows large, an optimization would be to
group handlers by prefix and only parse once per distinct prefix. This is
not worth doing upfront.

### 5. Remove the TODO comment

Delete the `// TODO: Make configurable per-bot` comment at line 166.

## Impact

- **Plugin API:** Adds `CommandPrefix` to `IBot` (additive, non-breaking).
  Adds `Prefix` property to `OnCommandAttribute` (additive, non-breaking —
  default `null` preserves current behavior).
- **Configuration:** Existing `CommandPrefix` property becomes functional.
  Default `"!"` preserves backward compatibility.
- **Tests:** Add tests for: default prefix dispatch, custom bot-wide prefix,
  per-handler prefix override, multi-character prefix, prefix case
  sensitivity.
