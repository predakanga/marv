#112026-06-05T15:30:18.305Z

Regarding CS-005, I think I prefer providing the IBot to the filter instead of adding FilterResult; that way the filters can do anything they need to (i.e. kicking or disconnecting the user). What are the pros & cons of doing it that way instead?

1 read

Good question. Here's the tradeoff:

Pros of passing IBot to the evaluator: - Filters can take real action: kick, ban, part, send notices — not just allow/deny - FilterResult.DenialMessage becomes unnecessary; the filter handles its own responses, which is more flexible (e.g. NOTICE vs PRIVMSG, or no reply at all) - Removes SendDenialReply helper from the framework — less surface area, fewer assumptions about response format - Consistent with how handlers already work (they receive the bot)

Cons: - Blurs the line between "should this handler run?" and "do something." A filter that kicks a user is a side effect that happens before the handler, which can be surprising — especially when multiple filters are stacked - Makes filter ordering matter more. If filter A kicks and filter B would have allowed, you get a different outcome depending on evaluation order - Harder to unit test evaluators in isolation — they need an IBot mock instead of just returning a result - The spec's FilterResult approach gives the framework a structured signal it can log/audit ("handler X was denied by filter Y with message Z"). With IBot passthrough, the framework loses visibility into what the filter did

My recommendation: Pass IBot but keep FilterResult as the return type (drop DenialMessage from it). Filters that want to kick or reply can do so via IBot, while the framework still gets a clean allowed/denied signal for logging. This gives you action capability without losing the structured result.

Want me to proceed with that hybrid approach, or do you want to go fully freeform (no FilterResult, just a bool)?

#122026-06-05T15:31:45.997Z

What would be the difference between returning FilterResult.Allowed/Denied vs just returning true/false?

The only difference in the current spec is DenialMessage — if we drop that field (since filters would reply via IBot themselves), FilterResult becomes a struct with a single bool IsAllowed property. At that point it's just a bool with extra ceremony.

The argument for keeping a struct would be future extensibility (e.g. adding a Reason for logging, or a StopEvaluation flag to short-circuit remaining filters). But that's speculative — we can always replace bool with a struct later without breaking existing filters, since true/false would still compile via an implicit conversion operator.

I'd go with bool for now. Simpler API, and if we need richer return values later, adding an implicit conversion from bool to a new result type is a non-breaking change.
