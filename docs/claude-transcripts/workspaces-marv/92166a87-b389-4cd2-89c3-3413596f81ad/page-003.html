4	**Scope:** Marv.Core.Plugin

11	
12	## Problem
13	
14	Plugins need cross-cutting handler logic — primarily authorization, but also
15	rate limiting, auditing, and custom channel filtering. Currently this must be
16	implemented as boilerplate at the top of every handler method. The downstream
17	analysis evaluated six approaches and recommends a synthesis of approaches 2
18	and 5: a virtual `FilterHandlerAsync` method whose default implementation
19	evaluates self-describing filter attributes.
20	
21	## Design
22	
23	Two tiers of complexity for two audiences:
24	
25	1. **Simple tier:** Plugin authors define attribute + evaluator pairs. The
26	   framework evaluates them automatically. No base class override needed.
27	2. **Advanced tier:** Plugin projects override `FilterHandlerAsync` for full
28	   control (OR conditions, context-dependent auth, custom denial messages).
29	
30	The simple tier is implemented *via* the advanced tier — the default
31	`FilterHandlerAsync` implementation scans for `IFilteringAttribute` and
32	calls their evaluators. This avoids the "two parallel systems" problem.

166	## Changes to MarvPlugin
167	
168	### 1. Pre-cache attributes during handler discovery
169	
170	In `DiscoverHandlers`, after registering each handler, also cache all custom
171	attributes on the method. Store as a `IReadOnlyList<Attribute>` in the
172	registration record (or a parallel `Dictionary<MethodInfo, IReadOnlyList<Attribute>>`).
173	
174	### 2. Add FilterHandlerAsync virtual method
175	
176	```csharp
177	/// <summary>
178	/// Called before each handler invocation. Return false to skip the handler.
179	/// The default implementation evaluates any <see cref="IFilteringAttribute"/>
180	/// attributes on the handler method.
181	/// </summary>
182	protected virtual async ValueTask<bool> FilterHandlerAsync(
183	    HandlerInvocation invocation, CancellationToken ct)
184	{
185	    foreach (var attr in invocation.Attributes.OfType<IFilteringAttribute>())
186	    {
187	        var evaluator = ResolveEvaluator(attr.EvaluatorType);
188	        var result = await evaluator.EvaluateAsync(attr, invocation, ct);
189	        if (!result.IsAllowed)
190	        {
191	            if (result.DenialMessage is not null)
192	                await SendDenialReply(invocation, result.DenialMessage, ct);
193	            return false;
194	        }
195	    }
196	    return true;
197	}
198	```

357	## Design decisions
358	
359	### Why not a middleware pipeline?
360	
361	Overengineered for the typical IRC bot use case. One or two cross-cutting
362	concerns don't justify pipeline infrastructure. `FilterHandlerAsync` can
363	handle multiple concerns in a single override. Revisit if three or more
364	independent concerns emerge across multiple downstream projects.
365	
366	### Why not `[RequireAuth]` in the framework?
367	
368	The permission string is meaningless without knowing the auth model. Every
369	downstream project brings its own authorization model. The framework should
370	not prescribe one — `IFilteringAttribute` lets each project define its own
371	semantics. See the full analysis in `downstream_suggestions/authorization.md`.
372	
373	### Handler groups and filtering
374	
375	`FilterHandlerAsync` runs on the owning plugin, not the handler group. The
376	`HandlerInvocation.Target` field distinguishes the plugin from its groups,
377	so the filter can branch if needed. Handler groups should not independently
378	override filtering — they are owned by their plugin.
379	
380	### FilterHandlerAsync exceptions
381	
382	If `FilterHandlerAsync` throws, treat it like a handler exception: log the
383	error and skip the handler. This is the safe default — a broken filter
384	should not allow a handler to run unguarded.

Good question. Here's the tradeoff:

Pros of passing IBot to the evaluator: - Filters can take real action: kick, ban, part, send notices — not just allow/deny - FilterResult.DenialMessage becomes unnecessary; the filter handles its own responses, which is more flexible (e.g. NOTICE vs PRIVMSG, or no reply at all) - Removes SendDenialReply helper from the framework — less surface area, fewer assumptions about response format - Consistent with how handlers already work (they receive the bot)

Cons: - Blurs the line between "should this handler run?" and "do something." A filter that kicks a user is a side effect that happens before the handler, which can be surprising — especially when multiple filters are stacked - Makes filter ordering matter more. If filter A kicks and filter B would have allowed, you get a different outcome depending on evaluation order - Harder to unit test evaluators in isolation — they need an IBot mock instead of just returning a result - The spec's FilterResult approach gives the framework a structured signal it can log/audit ("handler X was denied by filter Y with message Z"). With IBot passthrough, the framework loses visibility into what the filter did

My recommendation: Pass IBot but keep FilterResult as the return type (drop DenialMessage from it). Filters that want to kick or reply can do so via IBot, while the framework still gets a clean allowed/denied signal for logging. This gives you action capability without losing the structured result.

Want me to proceed with that hybrid approach, or do you want to go fully freeform (no FilterResult, just a bool)?

3	**Source:** `downstream_suggestions/authorization.md` (full analysis)
4	**Scope:** Marv.Core.Plugin
5	**Complexity:** Medium
6	**Breaking changes:** None (additive virtual method + new interfaces)
7	**Depends on:** CS-003 (handler dispatch filters provide the attribute-level
8	context this builds on)
9	
10	---
11	
12	## Problem
13	
14	Plugins need cross-cutting handler logic — primarily authorization, but also
15	rate limiting, auditing, and custom channel filtering. Currently this must be
16	implemented as boilerplate at the top of every handler method. The downstream
17	analysis evaluated six approaches and recommends a synthesis of approaches 2
18	and 5: a virtual `FilterHandlerAsync` method whose default implementation
19	evaluates self-describing filter attributes.
20	
21	## Design
22	
23	Two tiers of complexity for two audiences:
24	
25	1. **Simple tier:** Plugin authors define attribute + evaluator pairs. The
26	   framework evaluates them automatically. No base class override needed.
27	2. **Advanced tier:** Plugin projects override `FilterHandlerAsync` for full
28	   control (OR conditions, context-dependent auth, custom denial messages).
29	
30	The simple tier is implemented *via* the advanced tier — the default
31	`FilterHandlerAsync` implementation scans for `IFilteringAttribute` and
32	calls their evaluators. This avoids the "two parallel systems" problem.

166	## Changes to MarvPlugin
167	
168	### 1. Pre-cache attributes during handler discovery
169	
170	In `DiscoverHandlers`, after registering each handler, also cache all custom
171	attributes on the method. Store as a `IReadOnlyList<Attribute>` in the
172	registration record (or a parallel `Dictionary<MethodInfo, IReadOnlyList<Attribute>>`).
173	
174	### 2. Add FilterHandlerAsync virtual method
175	
176	```csharp
177	/// <summary>
178	/// Called before each handler invocation. Return false to skip the handler.
179	/// The default implementation evaluates any <see cref="IFilteringAttribute"/>
180	/// attributes on the handler method.
181	/// </summary>
182	protected virtual async ValueTask<bool> FilterHandlerAsync(
183	    HandlerInvocation invocation, CancellationToken ct)
184	{
185	    foreach (var attr in invocation.Attributes.OfType<IFilteringAttribute>())
186	    {
187	        var evaluator = ResolveEvaluator(attr.EvaluatorType);
188	        var result = await evaluator.EvaluateAsync(attr, invocation, ct);
189	        if (!result.IsAllowed)
190	        {
191	            if (result.DenialMessage is not null)
192	                await SendDenialReply(invocation, result.DenialMessage, ct);
193	            return false;
194	        }
195	    }
196	    return true;
197	}
198	```

324	
325	        if (!requireAdmin && !staffBypass)
326	            return true;
327	
328	        var sender = invocation.Context switch
329	        {

331	            RegexMatchContext regex => regex.Sender,
332	            _ => null

334	        if (sender is null) return true;

337	        if (isAdmin) return true;

342	            {

357	## Design decisions
358	
359	### Why not a middleware pipeline?
360	
361	Overengineered for the typical IRC bot use case. One or two cross-cutting
362	concerns don't justify pipeline infrastructure. `FilterHandlerAsync` can
363	handle multiple concerns in a single override. Revisit if three or more
364	independent concerns emerge across multiple downstream projects.
365	
366	### Why not `[RequireAuth]` in the framework?
367	
368	The permission string is meaningless without knowing the auth model. Every
369	downstream project brings its own authorization model. The framework should
370	not prescribe one — `IFilteringAttribute` lets each project define its own
371	semantics. See the full analysis in `downstream_suggestions/authorization.md`.
372	
373	### Handler groups and filtering
374	
375	`FilterHandlerAsync` runs on the owning plugin, not the handler group. The
376	`HandlerInvocation.Target` field distinguishes the plugin from its groups,
377	so the filter can branch if needed. Handler groups should not independently
378	override filtering — they are owned by their plugin.
379	
380	### FilterHandlerAsync exceptions
381	
382	If `FilterHandlerAsync` throws, treat it like a handler exception: log the
383	error and skip the handler. This is the safe default — a broken filter
384	should not allow a handler to run unguarded.

414	
415	1. Should `HandlerInvocation` include handler registration metadata (matched

### Why pass IBot to evaluators?

Evaluators need to take action when denying a handler — sending a denial
notice, kicking a user, or even disconnecting. Without `IBot`, the
framework would need to anticipate every possible denial action and
expose it through `FilterResult` (e.g. `DenialMessage`, `KickReason`).
That pushes IRC-specific logic into a struct that should be a simple
signal. Passing `IBot` lets evaluators handle denial responses themselves
using the same API handlers use, while `FilterResult` stays a clean
allowed/denied flag.

This does mean filter ordering matters more when filters have side
effects (a filter that kicks before a later filter would have allowed).
This is an acceptable tradeoff — filter evaluation order follows
attribute declaration order on the method, which is predictable.

### Why FilterResult instead of bool?

`FilterResult` currently contains only `IsAllowed`, making it
functionally equivalent to a `bool`. It exists as a struct to allow
future extension (e.g. a `Reason` field for structured logging, or a
`StopEvaluation` flag to short-circuit remaining filters) without
breaking existing evaluator signatures. If a richer result type is
needed later, existing evaluators continue to compile unchanged. A
`bool` return would require touching every evaluator to migrate.

12	## Problem
13	
14	Plugins need cross-cutting handler logic — primarily authorization, but also
15	rate limiting, auditing, and custom channel filtering. Currently this must be
16	implemented as boilerplate at the top of every handler method. The downstream
17	analysis evaluated six approaches and recommends a synthesis of approaches 2
18	and 5: a virtual `FilterHandlerAsync` method whose default implementation
19	evaluates self-describing filter attributes.
20	
21	## Design
22	
23	Two tiers of complexity for two audiences:
24	
25	1. **Simple tier:** Plugin authors define attribute + evaluator pairs. The
26	   framework evaluates them automatically. No base class override needed.
27	2. **Advanced tier:** Plugin projects override `FilterHandlerAsync` for full
28	   control (OR conditions, context-dependent auth, custom denial messages).
29	
30	The simple tier is implemented *via* the advanced tier — the default
31	`FilterHandlerAsync` implementation scans for `IFilteringAttribute` and
32	calls their evaluators. This avoids the "two parallel systems" problem.

342	## Design decisions
343	
344	### Why pass IBot to evaluators?
345	
346	Evaluators need to take action when denying a handler — sending a denial
347	notice, kicking a user, or even disconnecting. Without `IBot`, the
348	framework would need to anticipate every possible denial action and
349	expose it through `FilterResult` (e.g. `DenialMessage`, `KickReason`).
350	That pushes IRC-specific logic into a struct that should be a simple
351	signal. Passing `IBot` lets evaluators handle denial responses themselves
352	using the same API handlers use, while `FilterResult` stays a clean
353	allowed/denied flag.
354	
355	This does mean filter ordering matters more when filters have side
356	effects (a filter that kicks before a later filter would have allowed).
357	This is an acceptable tradeoff — filter evaluation order follows
358	attribute declaration order on the method, which is predictable.
359	
360	### Why FilterResult instead of bool?
361	
362	`FilterResult` currently contains only `IsAllowed`, making it
363	functionally equivalent to a `bool`. It exists as a struct to allow
364	future extension (e.g. a `Reason` field for structured logging, or a
365	`StopEvaluation` flag to short-circuit remaining filters) without
366	breaking existing evaluator signatures. If a richer result type is
367	needed later, existing evaluators continue to compile unchanged. A
368	`bool` return would require touching every evaluator to migrate.
369	
370	### Why not a middleware pipeline?
371	
372	Overengineered for the typical IRC bot use case. One or two cross-cutting
373	concerns don't justify pipeline infrastructure. `FilterHandlerAsync` can
374	handle multiple concerns in a single override. Revisit if three or more
375	independent concerns emerge across multiple downstream projects.
376	
377	### Why not `[RequireAuth]` in the framework?
378	
379	The permission string is meaningless without knowing the auth model. Every
380	downstream project brings its own authorization model. The framework should
381	not prescribe one — `IFilteringAttribute` lets each project define its own
382	semantics. See the full analysis in `downstream_suggestions/authorization.md`.
383	
384	### Handler groups and filtering
385	
386	`FilterHandlerAsync` runs on the owning plugin, not the handler group. The
387	`HandlerInvocation.Target` field distinguishes the plugin from its groups,
388	so the filter can branch if needed. Handler groups should not independently
389	override filtering — they are owned by their plugin.
390	
391	### FilterHandlerAsync exceptions
392	
393	If `FilterHandlerAsync` throws, treat it like a handler exception: log the
394	error and skip the handler. This is the safe default — a broken filter
395	should not allow a handler to run unguarded.
