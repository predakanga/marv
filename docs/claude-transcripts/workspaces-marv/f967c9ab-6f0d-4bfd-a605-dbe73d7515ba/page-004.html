37	**Provided services** are declared explicitly with a
38	`[ProvidesService(typeof(IFoo))]` attribute on the plugin class. The
39	plugin also provides a static `ConfigureServices(IServiceCollection)`
40	method to perform the actual DI registration. The attribute tells the
41	dependency sorter which plugin provides which service; the method does
42	the wiring.
43	
44	**Consumed services** are discovered automatically by inspecting the
45	plugin's constructor parameters. Any parameter whose type is not a
46	core service (not `IBot`, `IOptions<T>`, `ILogger<T>`, etc.) is
47	assumed to be a plugin-provided service dependency:
48	
49	- **Required**: Non-nullable parameter → the service must be
50	  registered by another plugin, or startup fails.
51	- **Optional**: Nullable parameter with a default of `null` → the
52	  service is used if available but does not block startup.
53	
54	Only the providing side needs an attribute. The consuming side is
55	inferred entirely from constructor signatures — nullability and
56	default values express optionality naturally. This keeps the common
57	case (consuming a service) completely boilerplate-free, while keeping
58	the uncommon case (providing a service) explicit and unambiguous.
59

116	## Consequences
117	
118	- Plugin authors use familiar .NET DI patterns for most things.
119	- Most plugins (consumers) need zero Marv-specific attributes — just
120	  constructor parameters with standard C# nullability.
121	- Plugins providing services need `[ProvidesService]` and a
122	  `ConfigureServices` method — explicit but only for the uncommon
123	  case.
124	- The `ConfigureServices` method is static and runs before plugin
125	  instances exist, which means service registration cannot depend on
126	  runtime state. This is intentional — services should be
127	  deterministic based on configuration.
128	- The single-container approach means plugin assemblies must not have
129	  conflicting type definitions. This is enforced by using a shared
130	  `AssemblyLoadContext`.
