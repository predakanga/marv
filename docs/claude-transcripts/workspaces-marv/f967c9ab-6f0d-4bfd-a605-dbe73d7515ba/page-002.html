25	### Marv.App
26	
27	The CLI host application. A thin shell that delegates to the core.
28	
29	Responsibilities:
30	
31	- Parse command-line arguments (using `System.CommandLine` or raw args)
32	- Read configuration from files, environment variables, and CLI args
33	  (in ascending priority order)
34	- Initialize logging (`Microsoft.Extensions.Logging` with console and
35	  file sinks)
36	- Call `services.AddMarv(configuration)` to delegate plugin loading,
37	  dependency sorting, service registration, and bot setup to the core
38	- Run the hosted service and handle graceful shutdown (Ctrl+C /
39	  SIGTERM)
40	
41	The app does **not** perform plugin discovery, DI wiring, or bot
42	orchestration itself — that is the core's responsibility. The app
43	builds the `IHostBuilder`, registers configuration and logging, calls
44	the core's extension method, and runs.
45	
46	This assembly references `Marv.Core` and the .NET hosting/DI packages.
47	It does not reference any plugin assemblies directly — plugins are
48	loaded at runtime.
49	
50	### Marv.Core
51	
52	The core library. Contains everything a plugin author needs to
53	reference at compile time, and everything the host needs to run the
54	bot. This is the only assembly that plugin projects reference.
55	
56	Responsibilities:
57	
58	- IRC message parsing and serialization
59	- TCP/TLS connection management
60	- IRCv3 capability negotiation and SASL authentication
61	- Protocol-level message handling (PING/PONG)
62	- Rate-limited message sending
63	- Channel/user/mode state tracking
64	- Plugin base classes, attributes, and lifecycle interfaces
65	- Event types and the event dispatch system
66	- The `IBot` facade interface
67	- Plugin discovery, dependency sorting, and lifecycle management
68	- The `IServiceCollection` extension method (`AddMarv`) that wires
69	  everything together
70	
71	### Plugin Assemblies
72	
73	Each plugin is a separate assembly (class library) that references
74	`Marv.Core`. A plugin assembly contains:
75	
76	- One or more plugin classes inheriting from `MarvPlugin` (or
77	  `MarvPlugin<TConfig>` for plugins with configuration)
78	- Optional configuration record/class
79	- Optional service interfaces (or these may live in a separate
80	  contracts assembly shared between provider and consumer)
81	- Optional service implementations
82	- Optional handler group classes
83	
84	Plugin assemblies are built as DLLs and placed in a known directory.
85	The host discovers them at startup via the configured plugin paths.

89	## Internal Layering (Marv.Core)
90	
91	The core library is organized into layers, each building on the one
92	below it. Higher layers depend on lower layers; lower layers never
93	reference higher layers.
94	
95	```
96	┌─────────────────────────────────────────┐
97	│            Plugin System                │  Plugin loading, lifecycle,
98	│   MarvPlugin, attributes, events        │  event dispatch
99	├─────────────────────────────────────────┤
100	│            Bot / Message Processor      │  IBot — high-level API
101	│   Send messages, query state,           │  exposed to plugins.
102	│   PING/PONG, CAP, state updates,        │  Protocol handling and
103	│   event fan-out to plugin tasks         │  state management.
104	├─────────────────────────────────────────┤
105	│            State Tracking               │  Channels, users, modes,
106	│   IChannelStore, IUserStore             │  ISUPPORT parameters
107	├─────────────────────────────────────────┤
108	│            Connection                   │  TCP/TLS, reconnection,
109	│   IIrcConnection                        │  rate limiting
110	├─────────────────────────────────────────┤
111	│            Protocol                     │  IrcMessage parsing,
112	│   IrcParser, IrcSerializer              │  serialization, tags,
113	│                                         │  case mapping
114	└─────────────────────────────────────────┘
115	```
116	
117	### Protocol Layer
118	
119	- `IrcMessage`: Immutable record representing a parsed IRC message
120	  (tags, source, command, parameters). Used for both inbound and
121	  outbound messages — the structure is identical (tags, command,
122	  parameters), with the only difference being that inbound messages
123	  have a source prefix and outbound messages do not. Keeping a single
124	  type avoids conversion overhead and lets plugins inspect/transform
125	  messages uniformly.
126	- `IrcParser`: Parses raw bytes/strings into `IrcMessage` instances.
127	  Handles tag value escaping, multi-space separation, empty trailing
128	  parameters, and source prefix parsing. Validated against
129	  ircdocs/parser-tests vectors.
130	- `IrcSerializer`: Serializes `IrcMessage` back to wire format.
131	- `CaseMapping`: Implements RFC 1459, strict-RFC 1459, and ASCII case
132	  mapping for nick/channel comparison. The active mapping is read from
133	  ISUPPORT and can change at runtime.
134	
135	### Connection Layer
136	
137	- `IIrcConnection`: Abstracts the TCP/TLS connection. Provides a
138	  `ChannelReader<IrcMessage>` for inbound messages and accepts
139	  outbound messages via a `ChannelWriter<IrcMessage>`.
140	- Implements rate limiting on outbound messages using a token bucket
141	  algorithm to prevent excess flood disconnections.
142	- Handles reconnection with exponential backoff.
143	- UTF-8 encoding with graceful handling of invalid sequences.
144	
145	The connection layer is a pure transport — it does not interpret
146	message content. PING/PONG handling, CAP negotiation, and all other
147	protocol-level logic live in the message processor (bot layer) where
148	they have access to state and can be tested without a network
149	connection.
150	
151	### State Tracking
152	
153	- `IChannelStore`: Maintains the set of channels the bot is in, each
154	  with its topic, modes, and member list (including per-user prefixes
155	  and join times).
156	- `IUserStore`: Maintains known users (nick, user, host, account, away
157	  status). Updated from NAMES, WHO, JOIN, PART, QUIT, NICK, CHGHOST,
158	  ACCOUNT, AWAY, SETNAME messages.
159	- `IModeParser`: Parses MODE changes using the server's CHANMODES and
160	  PREFIX from ISUPPORT to correctly handle type A/B/C/D modes.
161	- All comparisons use the server's advertised CASEMAPPING.
162	
163	State stores are written by the message processor task and read by
164	plugin tasks. Thread safety is achieved through a
165	snapshot-on-publish model: the message processor updates state, then
166	fans out events to plugin channels. Plugins read state during event
167	handling; the state stores provide read-safe access (via immutable
168	snapshots or concurrent-read-safe data structures). Only the message
169	processor writes, so no write contention exists.
170	
171	### Bot / Message Processor
172	
173	- `IBot`: The primary interface plugins interact with. Provides
174	  methods for sending messages, querying channel/user state, and
175	  checking capability availability. See `plugin-api-draft.md` for the
176	  full surface.
177	- The message processor is the central task that reads from the
178	  inbound channel and:
179	  - Handles PING/PONG (responds immediately, not exposed to plugins)
180	  - Drives CAP negotiation and SASL authentication
181	  - Updates state tracking (channels, users, modes)
182	  - Translates raw `IrcMessage` into typed events
183	  - Fans out events to each plugin's individual event channel
184	
185	### Plugin System
186	
187	- Plugin discovery, assembly loading, dependency graph construction,
188	  topological sorting, and lifecycle management.
189	- Per-plugin event channels and tasks (see Async/Threading Model).
190	- Described in detail below.

194	## Async / Threading Model
195	
196	Marv uses a small number of long-lived async tasks communicating via
197	`System.Threading.Channels`. Each plugin runs on its own dedicated
198	task, receiving events through its own channel.
199	
200	### Task Structure
201	
202	```
203	                                             ┌──────────────────┐
204	                                          ┌─►│  Plugin A Task   │
205	                                          │  │  Channel<Event>  │
206	┌──────────────┐   Channel<IrcMessage>   ┌┴───────────────────┐ │
207	│  Read Loop   │ ──────────────────────► │  Message           │ │
208	│  (network)   │   (inbound)             │  Processor         │ │
209	└──────────────┘                         │                    ├─┤
210	                                         │  - PING/PONG       │ │
211	                                         │  - CAP negotiation │ │  ┌──────────────────┐
212	                                         │  - State updates   ├─┼─►│  Plugin B Task   │
213	                                         │  - Event fan-out   │ │  │  Channel<Event>  │
214	                                         └┬───────────────────┘ │  └──────────────────┘
215	                                          │                     │
216	                                          └─►  ... more plugins
217	
218	         (plugins call IBot.SendAsync from any task)
219	                          │
220	                          ▼
221	┌──────────────┐   Channel<IrcMessage>   ┌──────────────────┐
222	│  Write Loop  │ ◄────────────────────── │  Rate Limiter    │
223	│  (network)   │   (outbound)            │  (token bucket)  │
224	└──────────────┘                         └──────────────────┘
225	```
226	
227	1. **Read Loop**: A dedicated async task reads from the TCP stream,
228	   parses raw lines into `IrcMessage` instances, and writes them to
229	   the inbound channel. This task does no processing beyond parsing.
230	
231	2. **Message Processor**: A dedicated async task reads from the
232	   inbound channel. For each message it:
233	   - Handles protocol-level concerns (PING/PONG, CAP negotiation)
234	   - Updates state tracking (channels, users, modes)
235	   - Translates raw `IrcMessage` into typed events
236	   - Writes the event to each plugin's individual event channel
237	
238	3. **Plugin Tasks**: Each plugin has its own dedicated async task and
239	   `Channel<MarvEvent>`. The task reads events from the channel and
240	   invokes the plugin's matching handlers sequentially. This means:
241	   - Each plugin processes events independently and concurrently with
242	     other plugins
243	   - Within a single plugin, handlers still run sequentially — no
244	     concurrency within a plugin
245	   - A slow plugin does not block other plugins or state tracking
246	   - Event ordering is preserved within each plugin
247	
248	4. **Rate Limiter**: Accepts outbound messages from any task (plugins
249	   call `IBot.SendAsync` which writes to this component) and drains
250	   them to the outbound channel at a rate that respects the server's
251	   flood limits.
252	
253	5. **Write Loop**: A dedicated async task reads from the outbound
254	   channel and writes serialized messages to the TCP stream.
255	
256	### Concurrency Rules
257	
258	- **Plugin event handlers run sequentially within their plugin task.**
259	  A plugin's handlers never run concurrently with each other. But
260	  different plugins' handlers do run concurrently.
261	
262	- **State stores are read-safe from any plugin task.** The message
263	  processor updates state before fanning out events. State stores use
264	  concurrent-read-safe data structures, so plugins can safely query
265	  `IBot.Channels` and `IBot.Users` from their event handlers without
266	  synchronization.
267	
268	- **`IBot.SendAsync` (and its variants) is thread-safe.** It can be
269	  called from any plugin task, background tasks, timers, etc.
270	
271	- **`CancellationToken` propagation**: All async methods accept a
272	  `CancellationToken`. The bot's top-level token is cancelled on
273	  shutdown, which drains the channels and allows tasks to exit cleanly.
274	
275	### Labeled Response Correlation
276	
277	When the bot sends a command that expects a response (e.g., WHO,
278	WHOIS), it uses the `labeled-response` capability to tag the outbound
279	message with a unique label. The message processor collects responses
280	with matching labels and delivers them as a batch to the caller via a
281	`TaskCompletionSource<T>`. This allows:
282	
283	```
284	var whoReply = await bot.SendAndAwaitAsync(whoMessage, cancellationToken);
285	```
286	
287	`SendAndAwaitAsync` sends an IRC command and returns the server's
288	correlated response messages. It uses the `labeled-response` IRCv3
289	capability to tag the outbound message with a unique label, then
290	collects all inbound messages bearing that label until the server
291	signals completion. This is useful for commands like WHO, WHOIS, and
292	LIST where the response spans multiple messages.
293	
294	If `labeled-response` is not negotiated, the bot falls back to
295	sequential command queuing with timeout-based correlation.

299	## Plugin Discovery and Loading
300	
301	### Startup Sequence
302	
303	Plugin loading happens during application startup, before the IRC
304	connection is established. The app calls
305	`services.AddMarv(configuration)`, which triggers the following
306	sequence inside `Marv.Core`.
307	
308	#### Phase 1: Bootstrap (No DI)
309	
310	1. **Read plugin paths**: From the configuration (already parsed by
311	   the app), extract the list of plugin assembly paths.
312	
313	2. **Discover assemblies**: For each configured plugin path, load the
314	   assembly into an `AssemblyLoadContext`. Scan for types that inherit
315	   from `MarvPlugin` or `MarvPlugin<TConfig>`.
316	
317	3. **Build dependency graph**: Inspect each discovered plugin type:
318	   - Read `[ProvidesService]` attributes for service types the plugin
319	     provides
320	   - Read `[DependsOn]` attributes for explicit plugin ordering
321	   - Read `[OptionalService]` attributes on constructor parameters
322	     for optional service dependencies
323	   - Read constructor parameters to identify required service
324	     dependencies (non-optional, non-core types)
325	   Construct a directed graph of plugin dependencies.
326	
327	4. **Topological sort**: Sort the graph. If there is a cycle, report
328	   it and fail startup. If a required dependency is missing, report
329	   it and fail startup. Optional dependencies participate in ordering
330	   (if present, the provider loads first) but do not block startup if
331	   absent.
332	
333	#### Phase 2: DI Container Build
334	
335	5. **Core service registration**: Register core services into the
336	   `IServiceCollection`: logging, configuration, `IIrcConnection`,
337	   `ICapabilityManager`, `IChannelStore`, `IUserStore`, `IBot`.
338	
339	6. **Plugin configuration registration**: For each plugin type that
340	   extends `MarvPlugin<TConfig>`, automatically register
341	   `IOptions<TConfig>` bound to the `Plugins:{PluginName}`
342	   configuration section. No boilerplate needed in the plugin.
343	
344	7. **Plugin service registration**: For each plugin type (in
345	   dependency order), if it has a static `ConfigureServices` method,
346	   call it with the `IServiceCollection`. Plugins that provide
347	   services to other plugins register their implementations here.
348	   Plugins that only handle events and use configuration do not need
349	   this method at all.
350	
351	8. **Plugin type registration**: Register each plugin type itself as
352	   a singleton in the container.
353	
354	9. **Build container**: Call `BuildServiceProvider()` to create the
355	   single `IServiceProvider`.
356	
357	10. **Resolve plugins**: Resolve each plugin type from the container.
358	    Constructor injection provides configuration, services, and the
359	    `IBot` facade.
360	
361	11. **Initialize plugins**: Call `OnLoadAsync()` on each plugin in
362	    dependency order.
363	
364	#### Runtime
365	
366	12. **Connect**: Establish the IRC connection, negotiate capabilities,
367	    authenticate, join channels.
368	
369	13. **Notify plugins**: Call `OnConnectedAsync()` on each plugin.
370	
371	14. **Start plugin tasks**: Create a dedicated `Channel<MarvEvent>`
372	    and async task for each plugin.
373	
374	15. **Message loop**: Process messages, update state, fan out events
375	    to plugin channels.
376	
377	16. **Shutdown**: Signal all plugin tasks to stop. Call
378	    `OnDisconnectedAsync()` then `OnUnloadAsync()` on each plugin in
379	    reverse dependency order. Dispose the DI container.
380	
381	### Assembly Load Context
382	
383	Each plugin assembly is loaded into a shared `AssemblyLoadContext`.
384	Using a single shared context (rather than isolated contexts per
385	plugin) avoids type identity issues — interfaces defined in
386	`Marv.Core` or in a shared contracts assembly are the same `Type`
387	across all plugins.
388	
389	If we later need assembly isolation (e.g., for hot-reloading or
390	conflicting dependencies), we can revisit this, but the single-context
391	approach is simpler and avoids a class of subtle bugs.
392

395	## Inter-Plugin Services
396	
397	### How It Works
398	
399	**Providing a service**: A plugin declares `[ProvidesService]` on its
400	class and registers the implementation in a static
401	`ConfigureServices` method. The attribute tells the dependency sorter
402	which plugin provides which service type; the method does the actual
403	DI registration.
404	
405	**Consuming a service**: A plugin declares a constructor parameter of
406	the service type. The plugin loader inspects constructor parameters to
407	identify consumed services. Non-nullable parameters are required
408	dependencies; parameters marked with `[OptionalService]` (and
409	nullable with a default of `null`) are optional.
410	
411	**Explicit ordering**: `[DependsOn(typeof(OtherPlugin))]` forces load
412	ordering without implying a service relationship.
413	
414	### Example
415	
416	```csharp
417	// Auth plugin provides IAuthorizationService
418	[ProvidesService(typeof(IAuthorizationService))]
419	public class AuthPlugin : MarvPlugin<AuthPluginConfig>
420	{
421	    public static void ConfigureServices(IServiceCollection services)
422	    {
423	        services.AddSingleton<IAuthorizationService, AccountBasedAuthService>();
424	    }
425	}
426	
427	// Moderation plugin consumes IAuthorizationService (required)
428	public class ModerationPlugin : MarvPlugin
429	{
430	    public ModerationPlugin(IBot bot, IAuthorizationService auth) { ... }
431	}
432	
433	// Greet plugin consumes IAuthorizationService (optional)
434	public class GreetPlugin : MarvPlugin<GreetPluginConfig>
435	{
436	    public GreetPlugin(
437	        IBot bot,
438	        [OptionalService] IAuthorizationService? auth = null) { ... }
439	}
440	```
441	
442	The loader sees:
443	- `AuthPlugin` provides `IAuthorizationService` (from attribute)
444	- `ModerationPlugin` requires `IAuthorizationService` (from
445	  constructor, non-nullable)
446	- `GreetPlugin` optionally uses `IAuthorizationService` (from
447	  constructor, `[OptionalService]`)
448	
449	Load order: AuthPlugin → ModerationPlugin, GreetPlugin (order between
450	Moderation and Greet is unspecified since neither depends on the
451	other).
452	
453	### Load Order Details
454	
455	The dependency sorter builds a graph from:
456	
457	- `[DependsOn(typeof(OtherPlugin))]` — direct plugin dependency
458	- Required constructor parameters — resolved to the plugin with a
459	  matching `[ProvidesService]` attribute
460	- `[OptionalService]` constructor parameters — ordered-if-present
461	
462	The graph is topologically sorted. Plugins with no dependencies load
463	first; plugins with dependencies load after their providers.
464	
465	**Cycle detection**: A cycle in the dependency graph is a
466	configuration error. The bot reports the cycle and refuses to start.
467	
468	**Missing required dependency**: If plugin A requires
469	`IAuthorizationService` but no loaded plugin provides it, startup
470	fails with a clear error message naming the missing service and the
471	plugin(s) that need it.
472	
473	**Missing optional dependency**: If plugin A optionally consumes
474	`IAuthorizationService` and no plugin provides it, A loads normally.
475	The constructor receives `null` for that parameter.
476	
477	### Diagnostics
478	
479	At startup (and available via a status command), the bot logs:
480	
481	- Which plugins are loaded, in what order
482	- Which services each plugin provides (from `[ProvidesService]`)
483	- Which services each plugin consumes (from constructors)
484	- Any plugins that were skipped and why

489	
490	Configuration is layered, with later sources overriding earlier ones:
491	
492	1. **Default values** (hardcoded in configuration classes)
493	2. **Configuration file** (`marv.toml` / `marv.json` — format TBD)
494	3. **Environment variables** (`MARV_*` prefix, double-underscore for
495	   nesting: `MARV_IRC__SERVER`)
496	4. **Command-line arguments** (`--irc:server=irc.example.com`)
497	
498	This uses the standard `Microsoft.Extensions.Configuration` stack.
499	
500	### Plugin Configuration
501	
502	Plugins that need configuration extend `MarvPlugin<TConfig>` instead
503	of `MarvPlugin`:
504	
505	```csharp
506	public record GreetPluginConfig
507	{
508	    public string GreetMessage { get; init; } = "Hello, {nick}!";
509	    public bool GreetOnJoin { get; init; } = true;
510	}
511	
512	public class GreetPlugin : MarvPlugin<GreetPluginConfig>
513	{
514	    // Config is available via this.Config (provided by the base class)
515	}
516	```
517	
518	The plugin loader automatically registers `IOptions<TConfig>` bound
519	to the `Plugins:{PluginName}` configuration section. The
520	`MarvPlugin<TConfig>` base class exposes a `Config` property so the
521	plugin can access its typed configuration without any DI boilerplate.
522	
523	There is no need for a `ConfigureServices` method just for
524	configuration — this is handled automatically. Only plugins that
525	register services for other plugins to consume need
526	`ConfigureServices`.

530	## Error Handling
531	
532	- **Parse errors**: Malformed messages from the server are logged and
533	  skipped — they never crash the message processor.
534	- **Plugin handler exceptions**: Caught by the plugin's event loop
535	  task, logged with the plugin name and event type, and do not affect
536	  other plugins or the message loop.
537	- **Connection loss**: The connection layer signals disconnection. The
538	  bot notifies plugins via `OnDisconnectedAsync`, then begins
539	  reconnection with exponential backoff.
540	- **Startup failures**: Missing required plugins/services, config
541	  validation errors, and dependency cycles all produce clear error
542	  messages and prevent the bot from starting.

29	### MarvPlugin Base Classes
30	
31	```csharp
32	public abstract class MarvPlugin

42	    public virtual Task OnDisconnectedAsync() => Task.CompletedTask;
43

45	    /// Use for cleanup (unsubscribe, flush, close handles).

75	## Registering Interest in Events
76	
77	Plugins declare event handlers using attributes on methods. The
78	method must be an instance method on the plugin class (or a handler
79	group class — see below) and return `Task`.
80	
81	### `[OnEvent]` — Subscribe to any typed event
82	
83	```csharp
84	[OnEvent]
85	public Task HandleJoin(UserJoinedEvent e, CancellationToken ct)
86	{
87	    // Runs when any user joins any channel the bot is in.
88	    return Task.CompletedTask;
89	}
90	```
91	
92	The event type is inferred from the method parameter. Only one event
93	parameter is allowed.
94	
95	### `[OnCommand]` — Respond to a user command
96	
97	```csharp
98	[OnCommand("hello")]
99	public async Task HandleHello(CommandContext ctx, CancellationToken ct)
100	{
101	    await ctx.ReplyAsync($"Hello, {ctx.Sender.Nick}!");
102	}
103	```
104	
105	`CommandContext` extends the message event with parsed command
106	arguments:
107	
108	```
109	CommandContext
110	├── Command: string                 ("hello")
111	├── Args: IReadOnlyList<string>     (remaining words)
112	├── ArgString: string               (remaining text, unparsed)
113	├── Channel: IChannel?              (null for private messages)
114	├── Sender: IUser
115	├── IsDirect: bool
116	├── ReplyAsync(string): Task        (responds in-context)
117	└── RawMessage: IrcMessage
118	```
119	
120	The command prefix (e.g., `!` or `.`) is configured per-bot, not
121	per-plugin.
122	
123	### `[OnRegex]` — Match messages against a regular expression
124	
125	```csharp
126	[OnRegex(@"https?://\S+")]
127	public async Task HandleUrl(RegexMatchContext ctx, CancellationToken ct)
128	{
129	    var url = ctx.Match.Value;
130	    await ctx.ReplyAsync($"I see a URL: {url}");
131	}
132	```
133	
134	`RegexMatchContext` extends the message event with the regex match:
135	
136	```
137	RegexMatchContext
138	├── Match: Match                    (System.Text.RegularExpressions.Match)
139	├── Channel: IChannel?
140	├── Sender: IUser
141	├── IsDirect: bool
142	├── ReplyAsync(string): Task
143	└── RawMessage: IrcMessage
144	```
145	
146	The regex is matched against the full message text. If there are
147	multiple matches, the handler is called once with the first match.
148	Named capture groups are accessible via `ctx.Match.Groups["name"]`.
149	
150	### `[OnRawMessage]` — Subscribe to raw IRC commands
151	
152	```csharp
153	[OnRawMessage("INVITE")]
154	public async Task HandleInvite(IrcMessage message, CancellationToken ct)
155	{
156	    // Direct access to the raw protocol message.
157	}
158	```
159	
160	This is for protocol-level handling that the typed events don't cover.
161	
162	### `[OnInterval]` — Periodic tasks
163	
164	```csharp
165	[OnInterval(minutes: 5)]
166	public async Task CheckSomething(CancellationToken ct)
167	{
168	    // Runs every 5 minutes while connected.
169	}
170	```
171	
172	Interval handlers run on the plugin's own task.

176	## Handler Groups
177	
178	For plugins with many handlers, related handlers can be organized
179	into separate classes using `[HandlerGroup]`. A handler group is a
180	class whose methods are treated as if they were methods on the plugin
181	itself.
182	
183	```csharp
184	public class MyPlugin : MarvPlugin
185	{
186	    // Plugin-level lifecycle, minimal handler code here
187	}
188	
189	[HandlerGroup(typeof(MyPlugin))]
190	public class MyAdminHandlers
191	{
192	    private readonly IBot _bot;
193	    private readonly IAuthorizationService _auth;
194	
195	    // Constructor-injected from the DI container, just like plugins
196	    public MyAdminHandlers(IBot bot, IAuthorizationService auth)
197	    {
198	        _bot = bot;
199	        _auth = auth;
200	    }
201	
202	    [OnCommand("kick")]
203	    public async Task HandleKick(CommandContext ctx, CancellationToken ct)
204	    {
205	        if (!await _auth.IsAuthorizedAsync(ctx.Sender, "mod.kick", ct))
206	        {
207	            await ctx.ReplyAsync("Permission denied.");
208	            return;
209	        }
210	        // ... perform the kick
211	    }
212	
213	    [OnCommand("ban")]
214	    public async Task HandleBan(CommandContext ctx, CancellationToken ct)
215	    {
216	        // ...
217	    }
218	}
219	```
220	
221	Handler groups are:
222	
223	- Discovered automatically by scanning the plugin's assembly for
224	  classes with `[HandlerGroup(typeof(MyPlugin))]`
225	- Constructed via DI — they can inject any service the plugin can
226	- Registered as singletons in the container
227	- Their event handlers run on the owning plugin's task, sequentially
228	  with the plugin's own handlers
229	- Useful for separating concerns without creating multiple plugins
230	  (which would each get their own task and independent event ordering)

350	
351	### `IBot` Interface
352	
353	```csharp
354	public interface IBot
355	{
356	    // --- Identity ---
357	    IUser Self { get; }
358	
359	    // --- Sending Messages ---
360	    Task SendMessageAsync(string target, string text, CancellationToken ct);
361	    Task SendNoticeAsync(string target, string text, CancellationToken ct);
362	    Task SendActionAsync(string target, string text, CancellationToken ct);
363	    Task SendRawAsync(IrcMessage message, CancellationToken ct);
364	
365	    // --- Channel Operations ---
366	    Task JoinAsync(string channel, string? key, CancellationToken ct);
367	    Task PartAsync(string channel, string? reason, CancellationToken ct);
368	
369	    // --- State ---
370	    IReadOnlyDictionary<string, IChannel> Channels { get; }
371	    IReadOnlyDictionary<string, IUser> Users { get; }
372	
373	    // --- Server Info ---
374	    IServerInfo ServerInfo { get; }
375	    ICapabilityManager Capabilities { get; }
376	
377	    // --- Advanced ---
378	    Task<IReadOnlyList<IrcMessage>> SendAndAwaitAsync(
379	        IrcMessage message, CancellationToken ct);
380	}
381	```
382	
383	**`Channels`**: Dictionary keyed by case-mapped channel name. Use the
384	indexer for O(1) lookup by name (e.g., `bot.Channels["#general"]`).
385	
386	**`Users`**: Dictionary keyed by case-mapped nick. Contains all users
387	the bot is aware of (through shared channels or direct interaction).
388	
389	**`SendAndAwaitAsync`**: Sends an IRC command and waits for the
390	server's correlated response. Uses the `labeled-response` IRCv3
391	capability to tag the outbound message with a unique label, then
392	collects all inbound messages bearing that label until the server
393	signals completion. Useful for commands like WHO, WHOIS, and LIST
394	where the response spans multiple messages. Falls back to
395	timeout-based correlation if `labeled-response` is not negotiated.
396	
397	**Thread safety**: All `Send*Async` methods, `JoinAsync`, `PartAsync`,
398	and `SendAndAwaitAsync` are thread-safe — they can be called from any
399	context (plugin tasks, background tasks, timers). The `Channels` and
400	`Users` dictionaries are read-safe from any plugin task (they use
401	concurrent-read-safe data structures updated only by the message
402	processor).
403

35	- **Repository**: <https://github.com/IrcDotNet/IrcDotNet>
36	- **NuGet**: `IrcDotNet`
37	- **License**: MIT
38	- **Target**: .NET Framework 4.0 / Silverlight 4.0 (with Mono support)
39	- **IRCv3 support**: None. Implements RFC 1459 and RFC 2812 only.
40	- **Maintenance**: Effectively abandoned. Multiple forks exist, none with
41	  significant activity. The original was designed for .NET Framework 4.0
42	  and Silverlight.
43	- **API quality**: Comprehensive RFC implementation, but the API is dated
44	  (event-based, no async/await, heavy use of `EventArgs` patterns).
45	- **Verdict**: Unsuitable. No IRCv3 support, unmaintained, legacy target
46	  framework.
47	
48	#### NetIRC
49	
50	- **Repository**: <https://github.com/fredimachado/NetIRC>
51	- **NuGet**: `NetIRC` (v1.1.2)
52	- **License**: MIT
53	- **Target**: .NET Standard 2.0 / .NET Framework 4.6.1
54	- **IRCv3 support**: None documented. Supports standard IRC commands
55	  (JOIN, PART, PRIVMSG, NICK, KICK, QUIT, TOPIC) and CTCP.
56	- **Maintenance**: Low activity, 4 stars, 2 forks.
57	- **API quality**: Async/await first, observable collections for UI binding,
58	  fluent builder pattern for configuration, custom message handler system.
59	  The cleanest modern API of the candidates, but limited scope.
60	- **Verdict**: Interesting API design to draw inspiration from, but no IRCv3
61	  support makes it unsuitable as a dependency.
62	
63	#### IrcNet (NowaLone)
64	
65	- **Repository**: <https://github.com/NowaLone/IrcNet>
66	- **NuGet**: Multiple packages (`NowaLone.IrcNet.Parser.V3`,
67	  `NowaLone.IrcNet.Parser.Rfc1459`, `NowaLone.IrcNet.Client`, etc.)
68	- **License**: MIT
69	- **Target**: .NET Standard 2.0+, .NET Framework 4.6.1+, .NET 6+
70	- **IRCv3 support**: Has a dedicated V3 parser and V3 client extensions
71	  package. Specific IRCv3 features supported are not well-documented.
72	- **Maintenance**: Very new (first release Jan 2025, latest May 2025). Only
73	  1 star, 0 forks. Essentially a single-developer project with no community
74	  adoption.
75	- **API quality**: Well-structured package decomposition (abstractions,
76	  parsers, client, extensions). Uses `IrcClientWebSocket` with
77	  `OnMessageReceived` events and `SendAsync`. The modular package structure
78	  is appealing but the WebSocket-based client is unusual for IRC.
79	- **Verdict**: Too immature and unproven. The package decomposition is
80	  interesting for reference, but adopting a library with zero community
81	  adoption and unclear IRCv3 coverage is risky.
82	
83	### Recommendation
84	
85	**None of the existing C# IRC libraries are suitable** for Marv's
86	requirements. The landscape is fragmented between abandoned projects
87	targeting legacy .NET (ChatSharp, IRC.NET) and immature projects with
88	unclear IRCv3 coverage (IrcNet/NowaLone).
89	
90	**Recommended approach**: Build on a minimal IRC message parser (either our
91	own or adapted from the IRCv3-compliant parsing layer in IrcNet) and
92	implement connection management and capability negotiation ourselves. This
93	gives us:
94	
95	- Full control over IRCv3 capability negotiation
96	- Modern .NET 10 / C# 13 idioms (async/await, `System.Threading.Channels`)
97	- No dependency on unmaintained or immature libraries
98	- Ability to use the [ircdocs/parser-tests](https://github.com/ircdocs/parser-tests)
99	  test vectors to validate our parser
100	
101	The IRC protocol is text-based and relatively simple to parse correctly
102	(with known edge cases — see section 5). The hard part is capability
103	negotiation and state management, which none of the existing libraries
104	handle well enough anyway.

108	## 2. IRCv3 Capabilities Relevant to a Bot
109	
110	### Must-Have Capabilities
111	
112	| Capability | Why |
113	|---|---|
114	| `message-tags` | Foundation for all tag-based features. Allows receiving and sending arbitrary tags. |
115	| `server-time` | Accurate timestamps on messages. Essential for logging and event ordering. |
116	| `sasl` | Secure authentication to services (NickServ) during connection registration, before joining channels. Avoids race conditions with post-connect auth. |
117	| `multi-prefix` | Receive all prefix modes (e.g. `@+`) in NAMES/WHO, not just the highest. Required for accurate channel state tracking. |
118	| `account-tag` | Every message carries the sender's services account name. Enables account-based authorization in plugins without WHOIS queries. |
119	| `echo-message` | Server echoes our own PRIVMSGs/NOTICEs back. Essential for confirming message delivery and maintaining accurate channel logs. |
120	| `cap-notify` | Server notifies when capabilities become available/unavailable at runtime. Required for robust capability management. |
121	| `batch` | Groups related messages (e.g. WHOIS replies, netsplit/netjoin). Allows plugins to process related messages atomically. |
122	| `labeled-response` | Correlate sent commands with server responses. Critical for any command that expects a reply (e.g. WHO, WHOIS). Without this, responses from concurrent commands can be ambiguous. |
123	| `bot` (bot-mode) | Marks the bot with a `B` flag so users and servers know it is a bot. Increasingly required by networks. |
124	
125	### Should-Have Capabilities
126	
127	| Capability | Why |
128	|---|---|
129	| `account-notify` | Notified when users log in/out of services accounts. Keeps account-based auth state current without polling. |
130	| `away-notify` | Notified when users change away status. Useful for plugins that care about user presence. |
131	| `extended-join` | JOIN messages include the user's account name and realname. Eliminates WHOIS on join. |
132	| `invite-notify` | Notified when users are invited to channels the bot is in. |
133	| `userhost-in-names` | NAMES replies include full `nick!user@host` masks. Eliminates WHO queries for host info. |
134	| `chghost` | Notified when a user's host/ident changes (e.g. after cloaking). Keeps internal state accurate. |
135	| `setname` | Notified when a user changes their realname. |
136	| `standard-replies` | Servers can send standardized FAIL/WARN/NOTE responses. Better error handling. |
137	| `monitor` | Watch for specific nicks coming online/offline. Useful for admin notification plugins. |
138	
139	### Not Relevant for Marv
140	
141	| Capability | Why not |
142	|---|---|
143	| `chathistory` / `event-playback` | Marv explicitly does not handle historic messages. |
144	| `tls` (STARTTLS) | We will connect with TLS from the start, not upgrade. |
145	| `multiline` | Nice-to-have at best; most bot messages are short. |
146	| `read-marker` | Intended for multi-client users, not bots. |
147	| `message-redaction` | Not relevant for a bot that does not maintain chat history. |
148	| `metadata-2` | Not widely deployed yet. |
149	| `channel-rename` | Rare operation; basic handling sufficient. |
150	
151	### Important Tags
152	
153	| Tag | Purpose |
154	|---|---|
155	| `account` | Sender's account name (from `account-tag` cap). |
156	| `batch` | Batch identifier for grouped messages. |
157	| `bot` | Marks messages from bots. |
158	| `label` | Correlates requests with responses (from `labeled-response` cap). |
159	| `msgid` | Unique message ID assigned by the server. Useful for deduplication. |
160	| `time` | ISO 8601 timestamp (from `server-time` cap). |
161	| `+reply` | Client-to-client: marks a message as a reply to a specific `msgid`. |

165	## 3. Existing IRC Bot Architectures
166	
167	### Sopel (Python)
168	
169	Sopel is the most relevant reference for Marv's design, being a mature,
170	well-documented IRC bot framework with a strong plugin system.
171	
172	**Plugin structure**:
173	- Plugins are Python modules containing decorated callables.
174	- Optional lifecycle hooks: `setup()` (called before connection),
175	  `shutdown()` (called after disconnection), `configure()` (interactive
176	  setup wizard).
177	- Callables receive `(bot, trigger)` — the bot object for sending messages
178	  and accessing state, and the trigger containing the matched message.
179	
180	**Event handling**:
181	- Decorator-based: `@rule()` (regex match), `@command()` (named command),
182	  `@event()` (IRC event type), `@ctcp()` (CTCP messages).
183	- `@interval()` decorator for periodic tasks (no message trigger needed).
184	- Rate limiting decorators: `@rate()`, `@rate_user()`, `@rate_channel()`.
185	
186	**Inter-plugin communication**:
187	- `bot.memory` — runtime dict-like shared memory. Any plugin can read/write.
188	  No formal contracts or typing; just convention.
189	- `bot.db` — persistent SQLite database. Plugins share tables.
190	- No formal dependency declaration between plugins. Plugins assume
191	  shared state exists or check for it.
192	
193	**Access control**:
194	- Built-in decorators: `@require_admin()`, `@require_privilege()`,
195	  `@require_account()`, `@require_owner()`.
196	- Channel privilege integration for op/voice checks.
197	
198	**Strengths**: Very easy to write plugins. Good decorator API. Mature.
199	**Weaknesses**: No typed inter-plugin contracts. Shared memory is
200	convention-based and fragile. No way to declare "this plugin requires
201	that plugin." Synchronous architecture.
202	
203	### Limnoria / Supybot (Python)
204	
205	Fork of Supybot, the original extensible Python IRC bot.
206	
207	**Architecture**:
208	- Synchronous main loop (`drivers.run()` in a loop).
209	- Two driver types: Socket driver (IRC connection) and schedule driver
210	  (periodic tasks like cron).
211	- All messages flow through `irclib.Irc`, which maintains a callback
212	  registry of plugins.
213	
214	**Plugin dispatch**:
215	- Uses `IrcCommandDispatcher` — method dispatch based on IRC command name
216	  (e.g., `doTopic()` handles TOPIC messages, `doPrivmsg()` handles PRIVMSG).
217	- `inFilter` / `outFilter` methods on plugins intercept messages before
218	  receipt / before sending.
219	
220	**State management**:
221	- Plugins maintain their own state. No shared memory system like Sopel.
222	- Each plugin can have its own database.
223	
224	**Strengths**: Well-tested, huge plugin ecosystem, granular ACL system.
225	**Weaknesses**: Synchronous, complex callback system, steeper learning
226	curve than Sopel, no typed inter-plugin services.
227	
228	### Errbot (Python, multi-platform)
229	
230	A chatbot framework supporting Slack, IRC, XMPP, Telegram, and more.
231	
232	**Architecture**:
233	- Backend abstraction: each chat platform is a "backend" implementing a
234	  common interface. Plugins are platform-agnostic.
235	- Plugins inherit from `BotPlugin` and use `@botcmd` decorator.
236	- Built-in persistent storage: `self['key'] = value` (dict-like).
237	- Plugin management via chat commands (!repos install, !plugin enable).
238	
239	**Relevance to Marv**: Errbot's backend abstraction is interesting as a
240	reference for how to separate protocol handling from plugin logic, even
241	though Marv only targets IRC. The `BotPlugin` base class with built-in
242	storage and command decorators is a good DX pattern.
243	
244	### Chaskis (C#, .NET)
245	
246	The only C# IRC bot framework found. Uses a plugin-based architecture.
247	
248	- Last release: v0.31.0 (January 2021) — appears abandoned.
249	- Targets .NET Core.
250	- Plugin-based, but detailed architecture documentation is sparse.
251	- No evidence of IRCv3 support.
252	
253	**Relevance**: Demonstrates that C# IRC bot frameworks exist but confirms
254	the ecosystem is immature. The wiki (if still accessible) may have useful
255	patterns.
256	
257	### Key Design Patterns Across Frameworks
258	
259	1. **Decorator/attribute-based event registration**: Every modern framework
260	   uses decorators (Python) or attributes (C#) to declare what events a
261	   handler responds to. This is clearly the right pattern.
262	
263	2. **Bot object as service facade**: Plugins receive a `bot` object that
264	   provides sending capabilities and state access. This keeps plugins
265	   decoupled from protocol details.
266	
267	3. **Configuration via bot object (anti-pattern)**: All studied frameworks
268	   have plugins access configuration through the bot object (e.g.
269	   `bot.config`, `self.config` from a base class). This couples plugins
270	   to the framework's configuration plumbing and makes configuration
271	   requirements implicit. **For Marv, we will not follow this pattern.**
272	   Instead, plugins will declare a typed configuration class, which will
273	   be injected via constructor — making configuration requirements
274	   explicit, validated at startup, and testable without a bot instance.
275	
276	4. **Trigger/context object**: The matched message, parsed into a
277	   convenient form with sender info, channel, match groups, etc.
278	
279	5. **Lifecycle hooks**: setup/teardown at plugin level, tied to bot
280	   lifecycle rather than individual messages.
281	
282	6. **Missing pattern**: None of the frameworks studied have typed
283	   inter-plugin service contracts. They all use shared mutable state
284	   (dicts, databases) or assume co-residency. This is Marv's opportunity
285	   to do better.

289	## 4. Plugin Architectures with Inter-Plugin Services
290	
291	### The Problem
292	
293	We want plugins to be able to:
294	1. **Provide services** (e.g., an auth plugin exposes `IAuthorizationService`)
295	2. **Consume services** from other plugins (e.g., a moderation plugin uses
296	   `IAuthorizationService` to check permissions)
297	3. **Handle optional dependencies** gracefully (the moderation plugin works
298	   without auth, just with reduced functionality)
299	4. **Load in correct order** based on dependencies
300	
301	### Approach 1: .NET `IServiceProvider` (Microsoft DI)
302	
303	**How it works**: Plugins register services in a `IServiceCollection`
304	during a configuration phase. The DI container is built once. Plugins
305	receive dependencies via constructor injection.
306	
307	**Pros**:
308	- Standard .NET pattern; familiar to C# developers
309	- Well-tested, high-performance implementation
310	- Supports scoped, singleton, and transient lifetimes
311	- Constructor injection makes dependencies explicit and testable
312	
313	**Cons**:
314	- Container is built once and is immutable — adding services after build
315	  requires rebuilding the container
316	- Plugin load order must be determined before container build
317	- Optional dependencies are awkward (you must register a null/no-op
318	  implementation or use `IServiceProvider.GetService<T>()` which returns
319	  null)
320	- No built-in concept of "this service is provided by plugin X"
321	
322	**Suitability**: Good foundation, but needs augmentation for plugin
323	lifecycle management.
324	
325	### Approach 2: Explicit Service Registry
326	
327	**How it works**: A custom `IServiceRegistry` managed by the bot core.
328	Plugins call `registry.Register<IAuthService>(this, implementation)` during
329	setup and `registry.Get<IAuthService>()` to consume. The registry
330	understands plugin identity and lifecycle.
331	
332	**Pros**:
333	- Can track which plugin provides which service
334	- Can handle late registration and optional dependencies naturally
335	- Can provide diagnostics ("auth service provided by AuthPlugin v1.2")
336	- Can enforce single-provider-per-interface or allow multiple providers
337	
338	**Cons**:
339	- Service locator anti-pattern (hides dependencies)
340	- Must be built and maintained ourselves
341	- Less familiar to .NET developers
342	- Testing requires mocking the registry
343	
344	### Recommended Approach: Hybrid
345	
346	Use Microsoft's `IServiceCollection` / `IServiceProvider` as the underlying
347	mechanism, but wrap it in a plugin-aware layer. **There is a single DI
348	container for the entire application** — core services (configuration,
349	logging, IRC client, bot) and plugin-contributed services all live in one
350	`IServiceCollection` which builds one `IServiceProvider`. There is no
351	separate container for plugins.
352	
353	The startup sequence has two distinct phases:
354	
355	1. **Bootstrap phase** (before DI): Read configuration from files,
356	   environment variables, and command-line arguments. Determine which
357	   plugin assemblies to load. This phase uses no DI — it runs before the
358	   container exists. The plugin list comes from core configuration read
359	   during bootstrap, so there is no circular dependency.
360	
361	2. **DI phase** (building the single container):
362	   a. **Assembly loading**: Load plugin assemblies discovered during
363	      bootstrap, discover plugin types.
364	   b. **Dependency sort**: Topological sort based on declared dependencies
365	      (attributes on plugin classes, e.g.
366	      `[DependsOn(typeof(AuthPlugin))]` or
367	      `[ConsumeService(typeof(IAuthService), Optional = true)]`).
368	   c. **Service registration**: Each plugin gets a chance to register
369	      services into the shared `IServiceCollection` via a static or
370	      type-level method (e.g. `ConfigureServices(IServiceCollection)`).
371	      This does not require constructing the plugin. Core services
372	      (configuration, logging, IRC client) are also registered here.
373	      Plugins are called in dependency order.
374	   d. **Container build**: The single `IServiceProvider` is built.
375	   e. **Plugin construction**: Plugin instances are resolved from the
376	      container — configuration and services injected via constructor.
377	
378	3. **Runtime**: Plugins can query for optional services via
379	   `IServiceProvider.GetService<T>()` (returns null if not registered).
380	
381	This gives us:
382	- A single, standard .NET DI container for the whole application
383	- Familiar .NET DI patterns for most use cases
384	- Explicit dependency declarations for load ordering
385	- Optional dependencies via nullable injection or runtime resolution
386	- Plugin identity tracking via a thin metadata layer on top
387	
388	### Load Order and Optional Dependencies
389	
390	**Topological sort**: Declare dependencies as attributes. Before loading,
391	build a dependency graph and topologically sort it. Cycles are a
392	configuration error. Missing required dependencies prevent startup.
393	Optional dependencies are ordered-if-present but don't block.
394	
395	**Graceful degradation**: Plugins should declare whether a service
396	dependency is required or optional. Required = fail to load if not met.
397	Optional = load but potentially with reduced functionality. The plugin
398	base class can provide helpers like `HasService<T>()` and
399	`GetOptionalService<T>()`.

403	## 5. Common Failure Modes in IRC Bot Implementations
404	
405	Based on the [ircdocs/parser-tests](https://github.com/ircdocs/parser-tests)
406	test suite, the [Modern IRC documentation](https://modern.ircdocs.horse/),
407	implementation guides, and issue trackers of IRC libraries, the following
408	edge cases and failure modes are most common.
409	
410	### Message Parsing
411	
412	1. **Trailing parameter not treated as normal parameter**: Many parsers
413	   create a separate field for the trailing parameter (after `:`). The
414	   correct behavior is to always add it to the parameter list as a normal
415	   parameter. Creating a separate `trailing` field leads to bugs when
416	   commands have varying parameter counts.
417	
418	2. **Tags on unexpected messages**: Once `message-tags` or `server-time` is
419	   enabled, ANY message from the server can have tags. Parsers that only
420	   handle tags on PRIVMSG will break on tagged CAP, AUTHENTICATE, JOIN,
421	   etc.
422	
423	3. **Tag value escaping**: Backslash escaping in tag values follows specific
424	   rules (`\:` → `;`, `\s` → space, `\\` → `\`, `\r` → CR, `\n` → LF).
425	   A trailing backslash with no escape character should produce no output
426	   character. An invalid escape like `\b` should drop the backslash
427	   (producing `b`).
428	
429	4. **Multiple spaces between parameters**: The spec says parameters are
430	   separated by "one or more" spaces. Parsers that split on single space
431	   will produce empty parameters. Parsers that are too strict will reject
432	   valid messages.
433	
434	5. **Empty trailing parameter**: `:` with nothing after it is a valid empty
435	   trailing parameter, not a parse error.
436	
437	6. **Source (prefix) parsing**: The source prefix `nick!user@host` can have
438	   missing components (server-originated messages have no `!user@host`).
439	   Parsers must handle `nick`, `nick@host`, `nick!user@host`, and bare
440	   server names.
441	
442	### Case Mapping
443	
444	7. **CASEMAPPING inconsistency**: Servers advertise their case mapping via
445	   ISUPPORT (`CASEMAPPING=rfc1459|ascii|strict-rfc1459`). Under `rfc1459`,
446	   `{`, `|`, `}` are the lowercase equivalents of `[`, `\`, `]`. Under
447	   `strict-rfc1459`, `~` and `^` are additionally equivalent. Under `ascii`,
448	   only A-Z/a-z are equivalent. Bots that use standard `ToLower()` for nick
449	   comparison will have subtle bugs. **This must be handled correctly for
450	   all nick and channel name comparisons**.
451	
452	8. **CASEMAPPING can change**: The server sends ISUPPORT during registration,
453	   but it can technically resend it. The bot should use the server's
454	   advertised mapping, not a hardcoded default.
455	
456	### Connection Management
457	
458	9. **PING/PONG timeout**: Servers send PING periodically; failing to PONG
459	   within the timeout causes disconnection ("Ping timeout"). Bots must
460	   handle PING at the protocol level, not in a plugin.
461	
462	10. **Excess flood**: Sending too many messages too quickly causes the server
463	    to disconnect the client ("Excess Flood"). Bots need rate limiting /
464	    message queue with throttling. A common approach is a token bucket or
465	    leaky bucket algorithm.
466	
467	11. **Reconnection with backoff**: Network disruptions are common. Bots
468	    should reconnect with exponential backoff to avoid being banned for
469	    rapid reconnection. Some networks also require different nick on
470	    reconnection if the old session hasn't timed out (nick collision).
471	
472	12. **Registration race conditions**: Without SASL, authenticating to
473	    NickServ after connecting creates a window where the bot is
474	    unauthenticated. During this window, joining channels with `+r`
475	    (registered-only) will fail. SASL solves this.
476	
477	### Channel and User State
478	
479	13. **MODE parsing complexity**: Channel modes have varying parameter counts
480	    depending on the mode type (A/B/C/D as defined in ISUPPORT
481	    `CHANMODES`). Parsing `MODE #channel +ov nick1 nick2` requires knowing
482	    that `o` and `v` are type B (always have a parameter). Getting this
483	    wrong causes state tracking to desynchronize.
484	
485	14. **NAMES/WHO state initialization**: When joining a channel, the bot must
486	    process NAMES (RPL_NAMREPLY/RPL_ENDOFNAMES) to build the initial user
487	    list. With `multi-prefix`, each name can have multiple prefix
488	    characters. Without `userhost-in-names`, the bot only gets nicks (no
489	    hostmasks).
490	
491	15. **Nick changes affecting state**: When a user changes nick, all channel
492	    membership records must be updated. This is a common source of state
493	    desynchronization.
494	
495	16. **QUIT vs PART**: QUIT removes a user from all channels; PART removes
496	    from one. Bots that only handle PART will have stale user lists.
497	
498	### Encoding
499	
500	17. **Character encoding**: IRC has no standard encoding. Messages can be
501	    UTF-8, Latin-1, or arbitrary bytes. Bots should default to UTF-8 but
502	    handle invalid sequences gracefully (replace or skip, never crash).
503	
504	### Protocol Quirks
505	
506	18. **Numeric replies are strings**: Despite being called "numerics," IRC
507	    reply codes are transmitted as three-character strings (e.g., `"001"`),
508	    not integers. Leading zeros matter.
509	
510	19. **Maximum message length**: IRC messages are limited to 512 bytes
511	    (including CR-LF), or 8191 bytes with the `message-tags` spec (tags
512	    occupy a separate 8191-byte budget from the 512-byte message budget).
513	    Bots must split messages that exceed these limits.
514	
515	20. **CAP negotiation subtleties**: `CAP LS 302` (IRCv3.2) enables
516	    multi-line capability lists and capability values. Bots must handle
517	    both single-line (`CAP * LS :cap1 cap2`) and multi-line
518	    (`CAP * LS * :cap1 cap2` followed by `CAP * LS :cap3`) responses.
519	    The `*` indicates "more to follow."

1	# Platform Abstraction Draft
2	
3	This document describes the core concepts that Marv models and
4	presents to plugins. Although Marv only targets IRC, these
5	abstractions exist to give plugins a clean, typed API rather than
6	forcing them to work with raw protocol strings.
7	
8	---
9	
10	## Messages
11	
12	### Raw Message: `IrcMessage`
13	
14	The lowest-level representation. An immutable record used for both
15	inbound and outbound messages:
16	
17	```
18	IrcMessage
19	├── Tags: IReadOnlyDictionary<string, string?>
20	├── Source: MessageSource?  (nick, user, host — any component may be absent)
21	├── Command: string         ("PRIVMSG", "001", "CAP", etc.)
22	└── Parameters: IReadOnlyList<string>
23	```
24	
25	**Design notes**:
26	
27	- The trailing parameter (after `:`) is always folded into
28	  `Parameters` as the last element. There is no separate `Trailing`
29	  property — this avoids the class of bugs described in research
30	  section 5.1.
31	- `Command` is always uppercase for consistency, regardless of how the
32	  server sent it.
33	- `Tags` values are already unescaped. The parser handles `\:`, `\s`,
34	  `\\`, `\r`, `\n`, and invalid escape sequences per the IRCv3 spec.
35	- `Source` is parsed into its components. Server-originated messages
36	  may have a source with only a hostname (no nick/user). For outbound
37	  messages, `Source` is null.
38	- The same type is used for both directions. The structure is
39	  identical; only the presence of `Source` differs.
40	
41	### Message Metadata
42	
43	Common tags are surfaced as strongly-typed properties on event objects
44	so plugins don't need to dig into the tag dictionary:
45	
46	| Property | Tag | Type | Availability |
47	|---|---|---|---|
48	| `Timestamp` | `time` | `DateTimeOffset` | When `server-time` is negotiated |
49	| `MessageId` | `msgid` | `string?` | When server assigns one |
50	| `Account` | `account` | `string?` | When `account-tag` is negotiated |
51	| `IsBot` | `bot` | `bool` | When `bot` tag is present |
52	| `Label` | `label` | `string?` | Internal use for labeled-response |
53	| `BatchId` | `batch` | `string?` | When message is part of a batch |
54	
55	Plugins can always access the full tag dictionary via `RawMessage.Tags`
56	for non-standard or vendor-specific tags.
57	
58	### High-Level Message Types
59	
60	Plugins typically work with typed event objects rather than raw
61	`IrcMessage`. See the Events section below. The event objects contain
62	the relevant `IrcMessage` for plugins that need protocol-level access.
63	
64	---
65	
66	## Channels
67	
68	### `IChannel`
69	
70	Represents a channel the bot is currently a member of.
71	
72	```
73	IChannel
74	├── Name: string                            ("#channel")
75	├── Topic: string?
76	├── TopicSetBy: string?                     (nick or mask)
77	├── TopicSetAt: DateTimeOffset?
78	├── Modes: IReadOnlyDictionary<char, string?> (mode → parameter)
79	├── Members: IReadOnlyCollection<IUser>
80	├── GetPrefixes(string nick): IReadOnlySet<char>   ('@', '+', etc.)
81	├── GetJoinTime(string nick): DateTimeOffset?
82	├── HasMember(string nick): bool
83	├── IsOp(string nick): bool                (shorthand: has '@' prefix)
84	├── IsVoiced(string nick): bool             (shorthand: has '+' prefix)
85	└── CreatedAt: DateTimeOffset?
86	```
87	
88	Per-user channel state (prefixes and join time) is stored on the
89	channel itself rather than in a separate `IChannelMember` relation.
90	These are the only two per-user-per-channel properties, and a
91	dedicated join type would add API surface without meaningful benefit.
92	Plugins query prefix/join state through the `IChannel` methods.
93	
94	### Channel Comparisons
95	
96	Channel names are compared using the server's advertised `CASEMAPPING`
97	(from ISUPPORT). The `IChannel` and related types use this
98	automatically — plugins do not need to handle case mapping themselves.
99	
100	All channel collections are keyed using case-mapped comparison so that
101	`#Channel` and `#channel` resolve to the same entry under ASCII case
102	mapping.
103	
104	---
105	
106	## Users
107	
108	### `IUser`
109	
110	Represents a user the bot is aware of (through shared channels or
111	direct interaction):
112	
113	```
114	IUser
115	├── Nick: string
116	├── User: string?            (ident / username)
117	├── Host: string?
118	├── Account: string?         (services account, from account-tag/extended-join/WHOX)
119	├── RealName: string?        (from extended-join or WHOIS)
120	├── IsAway: bool             (from away-notify)
121	├── AwayMessage: string?
122	├── IsBot: bool              (from bot tag or bot mode)
123	├── Channels: IReadOnlyCollection<IChannel>  (shared channels)
124	└── Hostmask: string         ("nick!user@host")
125	```
126	
127	### User Identity
128	
129	Users are identified primarily by nick (case-mapped per CASEMAPPING).
130	When `account-tag` is negotiated, the `Account` property provides a
131	stable identity across nick changes.
132	
133	The user store tracks nick changes: when user A renames to B, the
134	`IUser` object is updated in place (same reference) with the new nick.
135	Plugins holding a reference to the `IUser` see the updated nick
136	automatically.
137	
138	### The Bot's Own Identity
139	
140	The bot itself is represented as a special `IUser` accessible via
141	`IBot.Self`. This allows plugins to check the bot's current nick,
142	modes, and other properties.
143	
144	---
145	
146	## Capabilities
147	
148	### `ICapabilityManager`
149	
150	Plugins can query which IRCv3 capabilities the server supports and
151	which have been successfully negotiated:
152	
153	```
154	ICapabilityManager
155	├── IsNegotiated(string cap): bool       ("Is echo-message active?")
156	├── IsAvailable(string cap): bool        ("Does the server support it?")
157	├── NegotiatedCapabilities: IReadOnlySet<string>
158	├── AvailableCapabilities: IReadOnlyDictionary<string, string?>  (cap → value)
159	└── event CapabilitiesChanged            (from cap-notify)
160	```
161	
162	### Usage Pattern
163	
164	Plugins should check capability availability before relying on
165	cap-dependent features:
166	
167	```csharp
168	if (capabilities.IsNegotiated("echo-message"))
169	{
170	    // We will see our own messages echoed back — no need to
171	    // self-track what we send.
172	}
173	else
174	{
175	    // We need to manually track our outgoing messages.
176	}
177	```
178	
179	### Capability Constants
180	
181	`Marv.Core` provides string constants for all known capabilities to
182	avoid magic strings:
183	
184	```csharp
185	static class Capabilities
186	{
187	    public const string MessageTags = "message-tags";
188	    public const string ServerTime = "server-time";
189	    public const string EchoMessage = "echo-message";
190	    public const string AccountTag = "account-tag";
191	    public const string LabeledResponse = "labeled-response";
192	    // ... etc.
193	}
194	```

214	├── MaxMessageLength: int             (default 512 minus overhead)

217	└── GetValue(string token): string?
218	```

225	## Events
226	
227	### Event Hierarchy
228	
229	Events are strongly-typed classes organized by category. Each event
230	carries the relevant context and the raw `IrcMessage` for advanced use.
231	
232	#### Connection Events
233	
234	| Event | When |
235	|---|---|
236	| `ConnectedEvent` | IRC registration complete (001 received) |
237	| `DisconnectedEvent` | Connection lost or closed |
238	| `CapabilitiesChangedEvent` | Capabilities added/removed at runtime (cap-notify) |
239	
240	#### Message Events
241	
242	Message events use a unified type with an `IsDirect` flag rather than
243	separate channel/private variants. This halves the event type count
244	and means a handler that doesn't care about the distinction (which is
245	common) needs only one subscription.
246	
247	| Event | Key Properties |
248	|---|---|
249	| `MessageEvent` | `Channel?`, `Sender`, `Text`, `IsDirect`, `ReplyTo?` |
250	| `NoticeEvent` | `Channel?`, `Sender`, `Text`, `IsDirect` |
251	| `ActionEvent` | `Channel?`, `Sender`, `Text`, `IsDirect` |
252	
253	When `IsDirect` is true, `Channel` is null (the message was sent
254	directly to the bot). When `IsDirect` is false, `Channel` identifies
255	the channel the message was sent to.
256	
257	#### Channel Events
258	
259	| Event | Key Properties |
260	|---|---|
261	| `UserJoinedEvent` | `Channel`, `User`, `Account?` |
262	| `UserPartedEvent` | `Channel`, `User`, `Reason?` |
263	| `UserKickedEvent` | `Channel`, `Kicker`, `Kicked`, `Reason?` |
264	| `TopicChangedEvent` | `Channel`, `SetBy`, `NewTopic` |
265	| `ModeChangedEvent` | `Channel`, `SetBy`, `Changes` |
266	| `InviteReceivedEvent` | `Channel`, `InvitedBy` |
267	
268	#### User Events
269	
270	| Event | Key Properties |
271	|---|---|
272	| `UserQuitEvent` | `User`, `Reason?`, `AffectedChannels` |
273	| `NickChangedEvent` | `User`, `OldNick`, `NewNick` |
274	| `AccountChangedEvent` | `User`, `OldAccount?`, `NewAccount?` |
275	| `AwayChangedEvent` | `User`, `IsAway`, `Message?` |
276	| `HostChangedEvent` | `User`, `OldHost`, `NewHost` |
277	
278	#### Raw Protocol Event
279	
280	| Event | Key Properties |
281	|---|---|
282	| `RawMessageEvent` | `Message: IrcMessage` |
283	
284	The `RawMessageEvent` fires for every inbound message, before any
285	higher-level event is dispatched. Plugins that need to handle protocol
286	messages not covered by the typed events can subscribe to this.
287	
288	### Common Event Properties
289	
290	All events inherit from `MarvEvent` and share:
291	
292	```
293	MarvEvent
294	├── Timestamp: DateTimeOffset   (from server-time tag, or local clock)
295	├── RawMessage: IrcMessage      (the underlying protocol message)
296	├── MessageId: string?          (from msgid tag)
297	└── BatchId: string?            (from batch tag, null if not batched)
298	```
299	
300	### Batched Messages
301	
302	When the server sends a `BATCH` group, individual messages within the
303	batch are delivered as normal typed events — each carries a `BatchId`
304	property linking it to the batch. Plugins that don't care about
305	batching simply ignore `BatchId` and process events normally.
306	
307	Plugins that need batch-aware processing (e.g., collecting all
308	netsplit QUITs atomically) can subscribe to the batch start/end
309	signals and collect events by `BatchId`:
310	
311	| Event | Key Properties |
312	|---|---|
313	| `BatchStartEvent` | `BatchId`, `Type`, `Parameters` |
314	| `BatchEndEvent` | `BatchId` |
315	
316	This approach avoids forcing all plugin authors to handle both
317	individual and batched event delivery. The default path (ignore
318	batching) works without any special handling.
319	
320	### Event Ordering
321	
322	Events are dispatched per-plugin (each plugin has its own channel and
323	task — see `architecture.md`). The ordering guarantees are:
324	
325	1. State tracking updates happen before events are fanned out
326	2. `RawMessageEvent` is dispatched before the corresponding typed
327	   event
328	3. Within a single plugin, events arrive in the order the server
329	   sent them
330	4. Across plugins, events are delivered concurrently — there is no
331	   ordering guarantee between different plugins' handling of the same
332	   event

1	# ADR-001: Platform Abstraction
2	
3	**Status**: Proposed  
4	**Date**: 2026-05-30
5	
6	## Context
7	
8	Marv targets IRC exclusively and does not need to support other chat
9	platforms. However, the raw IRC protocol is a poor API surface for
10	plugin authors — it requires knowledge of protocol details, manual
11	string parsing, and careful state tracking.
12	
13	We need to decide how much abstraction to place between the IRC wire
14	protocol and the plugin API.
15	
16	The spectrum of options:
17	
18	1. **No abstraction**: Plugins work with raw `IrcMessage` objects and
19	   must parse parameters, track state, and handle protocol quirks
20	   themselves.
21	
22	2. **Thin IRC-specific models**: Typed models for IRC concepts
23	   (channels, users, messages) that directly reflect IRC semantics
24	   but hide parsing details.
25	
26	3. **Platform-agnostic abstraction**: Generic chat concepts
27	   (conversations, participants, messages) designed for
28	   multi-platform portability, as frameworks like Errbot do.
29	
30	## Decision
31	
32	**Option 2: Thin IRC-specific models.**
33	
34	We model IRC's entities — channels, users, messages, modes,
35	capabilities — as first-class types with typed properties and
36	consistent APIs, but we do not abstract away IRC's semantics. A
37	channel is an `IChannel` (not a "conversation"), a user is an `IUser`
38	(not a "participant"), and capabilities are IRCv3 capabilities (not
39	generic "platform features").
40	
41	Plugins work with these typed models in event handlers and queries.
42	Raw `IrcMessage` access is always available via the `RawMessage`
43	property on events, and plugins can subscribe to `RawMessageEvent` for
44	protocol-level handling.
45	
46	## Rationale
47	
48	**Why not option 1 (no abstraction)**: Forcing every plugin to parse
49	PRIVMSG parameters, track nick changes, handle case mapping, and
50	manage channel membership would violate the DX design goal. The same
51	state-tracking code would be duplicated across every non-trivial
52	plugin.
53	
54	**Why not option 3 (platform-agnostic)**: Marv will only support IRC.
55	Building a platform-agnostic abstraction layer adds complexity without
56	delivering value:
57	
58	- IRC-specific features (modes, prefixes, CTCP, capabilities) would
59	  need to leak through the abstraction anyway, creating a worst-of-
60	  both-worlds API.
61	- Plugin authors targeting Marv are writing for IRC. An abstraction
62	  that hides IRC semantics makes their job harder, not easier.
63	- If multi-platform support is ever desired, it would be better to
64	  build it as a separate project that composes protocol-specific bots,
65	  rather than burdening the IRC bot with abstractions it doesn't need.
66	
67	**Why option 2 works**: IRC's concepts are well-defined and stable.
68	Channels, users, modes, and messages have clear semantics that map
69	directly to typed models. The abstraction removes boilerplate (parsing,
70	state tracking, case mapping) while preserving the mental model that
71	IRC-knowledgeable plugin authors already have.
72	
73	## Consequences
74	
75	- Plugin authors must understand IRC concepts (channels, nicks, modes)
76	  to be productive. This is acceptable because anyone writing an IRC
77	  bot plugin is expected to understand IRC.
78	- If Marv ever needs to support a non-IRC platform, the plugin API
79	  would need significant changes. We accept this tradeoff — YAGNI.
80	- The raw `IrcMessage` escape hatch ensures that no IRC functionality
81	  is inaccessible, even if the typed models don't cover every edge
82	  case.
83	- The typed models serve as a natural place to centralize correct
84	  handling of protocol quirks (case mapping, mode parsing, message
85	  length limits).

1	# ADR-002: IRC Library Choice
2	
3	**Status**: Proposed  
4	**Date**: 2026-05-30
5	
6	## Context
7	
8	Marv needs to parse IRC messages, manage a TCP/TLS connection,
9	negotiate IRCv3 capabilities, and track channel/user state. We
10	evaluated whether to use an existing C# IRC library or build our own
11	protocol layer.
12	
13	Five libraries were evaluated (see `docs/research.md` section 1):
14	
15	| Library | Target | IRCv3 | Maintained | Verdict |
16	|---|---|---|---|---|
17	| ChatSharp | .NET Framework | Partial | No | Unsuitable |
18	| IRC.NET (IrcDotNet) | .NET Framework 4.0 | None | No | Unsuitable |
19	| NetIRC | .NET Standard 2.0 | None | Low | Unsuitable |
20	| IrcNet (NowaLone) | .NET 6+ | Unclear | Too new | Unsuitable |
21	
22	## Decision
23	
24	**Build our own IRC protocol layer**, consisting of:
25	
26	1. An `IrcParser` for parsing raw messages into `IrcMessage` records,
27	   validated against the ircdocs/parser-tests test vectors.
28	2. An `IrcSerializer` for converting `IrcMessage` back to wire format.
29	3. A `CaseMapping` utility implementing RFC 1459, strict-RFC 1459, and
30	   ASCII case folding.
31	4. An `IIrcConnection` managing TCP/TLS, reconnection, rate limiting,
32	   and PING/PONG.
33	5. A `CapabilityEngine` for IRCv3 CAP negotiation and SASL
34	   authentication.
35	6. State tracking for channels, users, and modes.
36	
37	We do not take a dependency on any existing IRC library.
38	
39	## Rationale
40	
41	**No suitable library exists.** The C# IRC library ecosystem is
42	fragmented between abandoned projects targeting legacy .NET and
43	immature projects with unclear IRCv3 coverage. None of the candidates
44	meet Marv's requirements:
45	
46	- Target .NET 10 (or at least .NET Standard 2.1+)
47	- Comprehensive IRCv3 capability support (message-tags, labeled-
48	  response, batch, echo-message, etc.)
49	- Async/await-first API
50	- Active maintenance
51	
52	**The IRC protocol is tractable to implement.** The wire protocol is
53	text-based with well-documented parsing rules. Community-maintained
54	test vectors (ircdocs/parser-tests) provide comprehensive coverage for
55	the parser. The hard parts — capability negotiation, state tracking,
56	mode parsing — are not handled well by any existing library anyway.
57	
58	**Full control over the async model.** Building our own connection
59	layer lets us use `System.Threading.Channels` for internal message
60	passing and control the threading model precisely (see ADR-004).
61	Wrapping an existing library's event model would add friction and
62	limit our design options.
63	
64	**No maintenance risk from upstream.** Given that every candidate
65	library is either abandoned or has zero community adoption, depending
66	on one would add risk rather than reduce it.
67	
68	## Consequences
69	
70	- We own the parser, connection management, and capability negotiation
71	  code. This is more initial work but eliminates external dependency
72	  risk.
73	- We must validate the parser against ircdocs/parser-tests and
74	  maintain correctness as the IRC protocol evolves.
75	- The common failure modes documented in `docs/research.md` section 5
76	  must be addressed in our implementation and test suite.
77	- If a high-quality C# IRC library emerges in the future, the
78	  protocol layer is internal to `Marv.Core` and could be replaced
79	  without affecting the plugin API.

1	# ADR-003: Plugin Service Registry
2	
3	**Status**: Proposed  
4	**Date**: 2026-05-30
5	
6	## Context
7	
8	Marv's plugin system needs to support inter-plugin services: one
9	plugin provides an implementation (e.g., `IAuthorizationService`),
10	and other plugins consume it. We need to decide how services are
11	registered, discovered, and resolved.
12	
13	Three approaches were evaluated (see `docs/research.md` section 4):
14	
15	1. **.NET `IServiceProvider`** (Microsoft DI) — plugins register into
16	   `IServiceCollection`, the container is built once, dependencies are
17	   constructor-injected.
18	
19	2. **Explicit service registry** — a custom `IServiceRegistry` where
20	   plugins call `Register<T>()` and `Get<T>()` at runtime.
21	
22	3. **Hybrid** — Microsoft DI as the underlying mechanism, wrapped in
23	   a plugin-aware metadata layer for dependency sorting and
24	   diagnostics.
25	
26	## Decision
27	
28	**Option 3: Hybrid approach with a single DI container.**
29	
30	There is one `IServiceCollection` and one `IServiceProvider` for the
31	entire application. Core services and plugin-contributed services all
32	live in the same container. There is no separate container for
33	plugins.
34	
35	### Service Discovery
36	
37	**Provided services** are declared explicitly with a
38	`[ProvidesService(typeof(IFoo))]` attribute on the plugin class. The
39	plugin also provides a static `ConfigureServices(IServiceCollection)`
40	method to perform the actual DI registration. The attribute tells the
41	dependency sorter which plugin provides which service; the method does
42	the wiring.
43	
44	**Consumed services** are discovered automatically by inspecting the
45	plugin's constructor parameters. Any parameter whose type is not a
46	core service (not `IBot`, `IOptions<T>`, `ILogger<T>`, etc.) is
47	assumed to be a plugin-provided service dependency:
48	
49	- **Required**: Non-nullable parameter → the service must be
50	  registered by another plugin, or startup fails.
51	- **Optional**: Parameter marked with `[OptionalService]`, nullable
52	  type, and a default of `null` → the service is used if available
53	  but does not block startup.
54	
55	Only the providing side needs an attribute. The consuming side is
56	inferred from constructor signatures, which is where the dependency
57	information naturally lives. This keeps the common case (consuming a
58	service) boilerplate-free, while keeping the uncommon case (providing
59	a service) explicit and unambiguous.
60	
61	### Explicit Ordering
62	
63	`[DependsOn(typeof(OtherPlugin))]` forces one plugin to load after
64	another without implying any service relationship. This is a
65	secondary mechanism for cases where the service graph alone doesn't
66	capture the needed ordering.
67	
68	### Automatic Configuration
69	
70	Plugins extending `MarvPlugin<TConfig>` have their configuration type
71	automatically registered as `IOptions<TConfig>` bound to
72	`Plugins:{PluginName}`. No `ConfigureServices` boilerplate is needed
73	for the common case of a plugin that only has configuration and event
74	handlers.
75	
76	## Rationale
77	
78	**Why not pure Microsoft DI (option 1)**: Microsoft DI alone does not
79	understand plugin identity or dependency ordering. It cannot answer
80	"which plugin provides this service?" or "in what order should plugins
81	load?" We need the metadata layer for:
82	
83	- Correct load ordering (provider must register before consumer)
84	- Clear startup error messages ("ModerationPlugin requires
85	  IAuthorizationService, but no loaded plugin provides it")
86	- Diagnostics and introspection
87	
88	**Why not a custom registry (option 2)**: A custom service locator
89	would duplicate functionality that Microsoft DI already provides
90	(lifetime management, constructor injection, scoping) and would be
91	unfamiliar to .NET developers. It also hides dependencies — consumers
92	call `registry.Get<T>()` at arbitrary points rather than declaring
93	them in the constructor.
94	
95	**Why `[ProvidesService]` on the provider only**: The providing side
96	is the uncommon case — most plugins only consume services or handle
97	events. An explicit attribute here is low-cost and avoids the
98	alternatives (scanning `ConfigureServices` registrations via a
99	throwaway `ServiceCollection`, or scanning assemblies for interface
100	implementations — both fragile). The consuming side needs no attribute
101	because the dependency information already lives in the constructor
102	signature.
103	
104	The `[OptionalService]` attribute remains because optionality cannot
105	be reliably inferred from nullability alone — a plugin author might
106	use a nullable parameter for other reasons.
107	
108	**Why a single container**: One `IServiceProvider` for core and
109	plugins avoids type identity issues and complex cross-container
110	resolution. A plugin's `IAuthorizationService` is the same type
111	whether resolved by core code or another plugin.
112	
113	## Consequences
114	
115	- Plugin authors use familiar .NET DI patterns for most things.
116	- Most plugins (consumers) need zero attributes — just constructor
117	  parameters.
118	- Plugins providing services need `[ProvidesService]` and a
119	  `ConfigureServices` method — explicit but only for the uncommon
120	  case.
121	- The `[OptionalService]` attribute is the only Marv-specific
122	  attribute needed for service consumption.
123	- The `ConfigureServices` method is static and runs before plugin
124	  instances exist, which means service registration cannot depend on
125	  runtime state. This is intentional — services should be
126	  deterministic based on configuration.
127	- The single-container approach means plugin assemblies must not have
128	  conflicting type definitions. This is enforced by using a shared

1	# ADR-004: Async / Threading Model
2	
3	**Status**: Proposed  
4	**Date**: 2026-05-30
5	
6	## Context
7	
8	An IRC bot has several concurrent concerns:
9	
10	- Reading from the network (blocking I/O)
11	- Writing to the network (with rate limiting)
12	- Processing inbound messages (state updates, event dispatch)
13	- Running plugin handlers (which may do I/O of their own)
14	- Periodic tasks (timers, health checks)
15	
16	We need to decide how these concerns are distributed across threads
17	and tasks, and what concurrency guarantees plugins receive.
18	
19	## Decision
20	
21	**Per-plugin tasks with a central message processor, connected by
22	`System.Threading.Channels`.**
23	
24	### Architecture
25	
26	The system uses N+4 long-lived async tasks (where N is the number of
27	loaded plugins):
28	
29	1. **Read loop**: Reads raw lines from the TCP stream, parses them
30	   into `IrcMessage`, and writes them to an inbound
31	   `Channel<IrcMessage>`. This task does no processing beyond parsing.
32	
33	2. **Message processor**: Reads from the inbound channel. For each
34	   message:
35	   - Handles protocol-level concerns (PING/PONG, CAP negotiation)
36	   - Updates state tracking (channels, users, modes)
37	   - Translates raw messages into typed events
38	   - Fans out each event to every plugin's individual event channel
39	
40	3. **Plugin tasks** (one per plugin): Each plugin has its own
41	   `Channel<MarvEvent>` and a dedicated async task. The task reads
42	   events from the channel and invokes the plugin's matching handlers
43	   (including handlers from the plugin's handler groups) sequentially.
44	
45	4. **Rate limiter**: Accepts outbound messages from any task and
46	   releases them to the outbound channel at a rate that respects the
47	   server's flood limits (token bucket algorithm).
48	
49	5. **Write loop**: Reads from the outbound channel and writes
50	   serialized messages to the TCP stream.
51	
52	### Concurrency Guarantees
53	
54	- **Within a plugin, handlers run sequentially.** A plugin's handlers
55	  never run concurrently with each other. This means a plugin author
56	  does not need to think about thread safety for the plugin's own
57	  state.
58	
59	- **Different plugins run concurrently.** Plugin A's handler for
60	  an event may be running at the same time as Plugin B's handler for
61	  the same (or a different) event.
62	
63	- **State stores are read-safe from any plugin task.** The message
64	  processor updates state before fanning out events. The state stores
65	  use concurrent-read-safe data structures (e.g., immutable snapshots
66	  or lock-free reads). Since only the message processor writes, there
67	  is no write contention. Plugins can safely read `IBot.Channels` and
68	  `IBot.Users` from their event handlers.
69	
70	- **`IBot.SendAsync` (and its variants) is thread-safe.** It writes
71	  to the rate limiter's input channel, which supports concurrent
72	  writers.
73	
74	- **`CancellationToken` propagation**: All async methods accept a
75	  `CancellationToken`. The bot's top-level token is cancelled on
76	  shutdown, which drains the channels and allows tasks to exit cleanly.
77	
78	### Plugin Background Work
79	
80	A plugin that needs to do slow work (HTTP requests, database queries)
81	can:
82	
83	1. Start the work with `Task.Run` or an async call
84	2. When the work completes, use `IBot.SendAsync` to send any resulting
85	   messages
86	3. Safely read `IBot.Channels` and `IBot.Users` (these are read-safe)
87	
88	If a plugin needs to update its own internal state from background
89	work, it should use its own synchronization (e.g., a `Channel<T>`
90	that the event handler drains, or `lock`/`ConcurrentDictionary` for
91	simple cases).
92	
93	## Rationale
94	
95	### Why per-plugin tasks instead of a single dispatcher
96	
97	**Plugin isolation.** With a single message processor calling all
98	plugin handlers sequentially, a slow plugin blocks every other plugin
99	and stalls state tracking. Per-plugin tasks isolate plugins from each
100	other — a slow handler in Plugin A only delays Plugin A's subsequent
101	events.
102	
103	**Natural concurrency.** Plugins are independent units of
104	functionality. Running them concurrently matches the mental model:
105	the greeting plugin and the moderation plugin shouldn't need to wait
106	for each other.
107	
108	**Sequential within a plugin.** Within a single plugin, handlers
109	still run sequentially. This preserves the key DX benefit: a plugin
110	author doesn't need to think about thread safety for their own state.
111	The concurrency boundary is between plugins, not within them.
112	
113	### Why state stores are read-safe
114	
115	The message processor updates state (channels, users, modes) before
116	fanning out events to plugin channels. Since writes happen on one
117	task and reads happen on plugin tasks, the data structures must
118	support concurrent reads. Options include:
119	
120	- Immutable snapshots (rebuild on each state change)
121	- `ConcurrentDictionary` with atomic value replacement
122	- Reader-writer locks (heavyweight, unlikely to be needed)
123	
124	The first two options provide lock-free reads, which is important
125	since every plugin reads state on every event. The exact
126	implementation is an internal detail.
127	
128	### Why System.Threading.Channels
129	
130	- **Bounded memory**: Channels can be bounded, providing natural
131	  backpressure if a plugin falls behind.
132	- **Async-native**: `ReadAsync` / `WriteAsync` integrate with
133	  `async/await` and `CancellationToken`.
134	- **High performance**: Minimal allocation, lock-free for
135	  single-producer/single-consumer channels.
136	- **Standard .NET**: No third-party dependency, familiar API.
137	- **Fan-out friendly**: The message processor writes to N plugin
138	  channels — `Channel<T>` handles this efficiently.
139	
140	### Why not Rx (System.Reactive)
141	
142	Rx provides powerful composition operators (merge, buffer, throttle)
143	but adds a dependency and a learning curve. The message flow in Marv
144	is simple: one inbound stream, state update, fan-out to N plugin
145	channels. Channels are sufficient and more predictable.
146	
147	### Why not a thread pool / Task.Run per event
148	
149	Dispatching each event to the thread pool would mean a plugin's
150	handlers could run concurrently with each other, requiring every
151	plugin to be thread-safe. Per-plugin channels preserve sequential
152	ordering within a plugin without sacrificing inter-plugin concurrency.
153	
154	## Consequences
155	
156	- A misbehaving plugin handler that blocks its task will only affect
157	  that plugin, not others. However, it will miss subsequent events
158	  (they queue up in its channel). Mitigation: log warnings if a
159	  handler takes longer than a configurable threshold; bounded channels
160	  with drop-oldest policy as a safety valve.
161	
162	- Plugins must not assume ordering relative to other plugins. If
163	  Plugin A and Plugin B both handle `UserJoinedEvent`, either one
164	  might process it first.
165	
166	- State store implementations must be concurrent-read-safe. This is
167	  an implementation concern inside `Marv.Core`, not a plugin concern.
168	
169	- The rate limiter prevents any plugin (or combination of plugins)
170	  from flooding the server, even if multiple plugins send messages
171	  concurrently.
172	
173	- Reconnection is handled by tearing down all tasks and restarting
174	  them. Plugins are notified via `OnDisconnectedAsync` /
175	  `OnConnectedAsync`.

437	the service type. The plugin loader inspects constructor parameters to

### Immutable Snapshots

`IUser` objects are immutable snapshots. When user state changes
(nick change, account change, away status, etc.), the message
processor creates a new snapshot and atomically replaces it in the
user store. This ensures thread safety without locks — plugins
reading from `IBot.Users` during event handling always get a
consistent snapshot.

A consequence of this model is that plugins holding a reference to
an `IUser` from a previous event will have stale data. This is
intentional — within a single event handler, all properties on the
`IUser` are consistent. To get the current state, read from
`IBot.Users`.

Internally, user snapshots are implemented as C# records with
`init`-only properties. State updates use `with` expressions to
create new snapshots:

```csharp
// Internal to Marv.Core — not part of the plugin API

    string Nick,
    string? User,
    string? Host,
    string? Account,
    string? RealName,
    bool IsAway,
    string? AwayMessage,
    bool IsBot
) : IUser
{
    public string Hostmask => $"{Nick}!{User}@{Host}";
}

// In the message processor, on NICK change:
var updated = existingUser with { Nick = newNick };
_userStore.Replace(oldNick, newNick, updated);
```

The user store uses `ConcurrentDictionary<string, IUser>` with
case-mapped keys. `Replace` atomically removes the old key and
inserts the new one. The `IChannel.Members` collection is similarly
rebuilt with the updated snapshot.

The same immutable snapshot model applies to `IChannel` — channel
objects are replaced atomically when topic, modes, or membership
change.

Good questions. Let me address the mutable models question first since it needs a decision, then I'll make the edits for the other points.

Mutable models — risks and mitigations

There are two categories of risk:

1. Collection modification during enumeration (crash risk) A plugin iterates Channel.Members while the message processor adds/removes a member on its task. This throws InvalidOperationException. This is the serious one.

Mitigation: Use ConcurrentDictionary for the backing stores (safe to enumerate while another thread writes — it snapshots the enumerator at creation) or return defensive copies from collection properties. Either way, no crash.

2. Torn reads across properties (correctness risk) A plugin reads user.Nick, then the message processor handles a NICK+CHGHOST, then the plugin reads user.Host. The plugin sees the new nick with the old host. Could cause a subtle bug if combined in an auth check or hostmask comparison.

Mitigation: Accept it. Individual property reads of reference types are atomic in .NET. The torn-read scenario requires a state change to land between two reads in the same handler — low probability, and plugins that need strict consistency can copy the fields they need into locals at the start of a handler. Document the behavior.

Pragmatic approach: Keep models mutable, use ConcurrentDictionary for collections, and document that individual property reads are atomic but cross-property consistency within a handler is not guaranteed. This is what most IRC bots actually do, and the DX is better — plugins holding an IUser reference see live updates without re-querying IBot.Users.

The immutable snapshot approach is "more correct" but adds allocation pressure (new record for every NICK, AWAY, MODE change) and the stale-reference footgun (plugin holds an IUser that silently stops updating). The mutable approach trades theoretical purity for practical simplicity.

### Immutable Snapshots

`IUser` objects are immutable snapshots. When user state changes
(nick change, account change, away status, etc.), the message
processor creates a new snapshot and atomically replaces it in the
user store. This ensures thread safety without locks — plugins

### Concurrency Model

`IUser` and `IChannel` objects are mutable — properties are updated
in place by the message processor when state changes occur (NICK,
CHGHOST, AWAY, MODE, etc.). Plugins holding a reference to an
`IUser` or `IChannel` see live updates.

- **Individual property reads are atomic.** Reading a single property
  (e.g., `user.Nick`) always returns a consistent value — you will
  never see a partial write.

  CHGHOST change could land between the two reads. In practice this
  is rare and usually harmless. Plugins that need strict consistency
  across multiple properties should copy the values they need into
  locals at the start of their handler.
- **Collection enumeration is safe.** Backing collections use
  `ConcurrentDictionary`, which safely handles concurrent reads and
  writes. Iterating `Channel.Members` while the message processor
  adds or removes a member will not throw.
