1	# CS-022: Live Config Reload & IOptions API Documentation
2	
3	**Source:** Downstream feature request
4	**Scope:** Host + Documentation (Program.cs, PLUGIN_API.md)
5	**Complexity:** Small
6	**Breaking changes:** None
7	**Status:** Pending
8	
9	---
10	
11	## Problem
12	
13	Two related gaps prevent plugins from reacting to configuration changes at
14	runtime:
15	
16	1. **No live reload:** All file-based configuration providers in `Program.cs`
17	   are registered with `reloadOnChange: false`. Even though the underlying
18	   providers (JSON5, YAML, XML) support file-watching, the bot never picks up
19	   edits to the configuration file without a restart.
20	
21	2. **Undocumented IOptions variants:** The Plugin API documentation
22	   (§8 Configuration) only shows `IOptions<T>` in the constructor injection
23	   example. Plugin authors don't realize they can also inject
24	   `IOptionsMonitor<T>` or `IOptionsSnapshot<T>` from the standard
25	   `Microsoft.Extensions.Options` package.
26	
27	Since Marv registers plugin configuration using the standard
28	`services.Configure<T>(section)` pattern, the full `IOptions` API is
29	available automatically through the DI container:
30	
31	- `IOptions<T>` — singleton, read once at startup
32	- `IOptionsSnapshot<T>` — scoped, re-reads per scope (less useful for
33	  long-lived plugins, but available)
34	- `IOptionsMonitor<T>` — singleton, fires `OnChange` callbacks when the
35	  underlying configuration source changes
36	
37	`IOptionsMonitor<T>` is particularly valuable: if the bot's configuration
38	file is edited at runtime and the configuration provider supports reload
39	(which the JSON5/YAML providers do when `reloadOnChange: true` is set),
40	plugins can react to configuration changes without a restart. But this
41	requires `reloadOnChange: true` to be set on the file providers — which
42	it currently is not.
43	
44	## Changes
45	
46	### 1. Enable `reloadOnChange` on all file-based config providers
47	
48	In `src/Marv/Program.cs`, change the `AddConfigFile` helper to pass
49	`reloadOnChange: true` for all file formats (JSON5, YAML, XML):
50	
51	```csharp
52	static void AddConfigFile(IConfigurationBuilder config, string path, bool required)
53	{
54	    var extension = Path.GetExtension(path).ToLowerInvariant();
55	
56	    switch (extension)
57	    {
58	        case ".json" or ".json5":
59	            config.AddJson5File(path, optional: !required, reloadOnChange: true);
60	            break;
61	        case ".yaml" or ".yml":
62	            config.AddYamlFile(path, optional: !required, reloadOnChange: true);
63	            break;
64	        case ".xml":
65	            config.AddXmlFile(path, optional: !required, reloadOnChange: true);
66	            break;
67	        default:
68	            throw new InvalidOperationException(
69	                $"Unsupported configuration file format: '{extension}'. " +
70	                "Supported formats: .json, .json5, .yaml, .yml, .xml");
71	    }
72	}
73	```
74	
75	This is the infrastructure change that makes `IOptionsMonitor<T>.OnChange`
76	actually fire when a user edits the config file at runtime.
77	
78	### 2. Update §8 (Configuration) in PLUGIN_API.md
79	
80	After the existing `IOptions<T>` example, add a note and example:
81	
82	```markdown
83	### Options API variants
84	
85	The full `Microsoft.Extensions.Options` API is available for plugin
86	configuration. In addition to `IOptions<T>`, you can inject:
87	
88	| Type | Lifetime | Use case |
89	|---|---|---|
90	| `IOptions<T>` | Singleton | Read config once at construction |
91	| `IOptionsMonitor<T>` | Singleton | React to config changes at runtime via `OnChange` |
92	| `IOptionsSnapshot<T>` | Scoped | Re-read config per scope (rarely needed for plugins) |
93	
94	Example using `IOptionsMonitor<T>` to react to config file edits:
95	
96	```csharp
97	public class MyPlugin(IBot bot, IPluginActivator activator, ILoggerFactory loggerFactory,
98	    IOptionsMonitor<MyConfig> configMonitor)
99	    : MarvPlugin(bot, activator, loggerFactory)
100	{
101	    private MyConfig _config = configMonitor.CurrentValue;
102	
103	    public override Task OnConnectedAsync(CancellationToken ct)
104	    {
105	        configMonitor.OnChange(updated => _config = updated);
106	        return Task.CompletedTask;
107	    }
108	}
109	```
110	```
111	
112	### 3. Update §13 (Available Services) table
113	
114	Add `IOptionsMonitor<T>` and `IOptionsSnapshot<T>` alongside the existing
115	`IOptions<T>` row:
116	
117	```markdown
118	| `IOptions<T>` | Singleton config for `[PluginConfig]` types |
119	| `IOptionsMonitor<T>` | Config with change notification support |
120	| `IOptionsSnapshot<T>` | Scoped config (re-reads per scope) |
121	```
122	
123	## Design decisions
124	
125	**Why enable reloadOnChange on all providers?** Without it,
126	`IOptionsMonitor<T>.OnChange` never fires — the documentation would be
127	describing a capability that doesn't work in practice. Enabling reload
128	completes the live-config story end-to-end: edit the file, the bot picks
129	up the change, plugins react via `OnChange`.
130	
131	**Why not a separate spec for reloadOnChange?** The code change is a
132	single-line-per-provider flip from `false` to `true`. It's the
133	infrastructure that makes the documented `IOptionsMonitor<T>` pattern
134	actually useful, so bundling them keeps the story coherent.
135	
136	**Why mention IOptionsSnapshot at all?** For completeness. Plugin authors
137	coming from ASP.NET Core expect to see all three variants documented.
138	The note that it's "rarely needed for plugins" sets expectations.
139	
140	## Testing
141	
142	- **Review only:** Verify the documentation is accurate by confirming that
143	  `services.Configure<T>()` is used in plugin config registration (which
144	  makes all three `IOptions` variants available).
145	- **Manual verification:** After the code change, confirm that modifying
146	  the config file at runtime causes `IOptionsMonitor<T>.OnChange` to fire
147	  (observable via debug logging in a test plugin).
148	- **Build verification:** `dotnet build` must pass — the change is a
149	  parameter value flip with no new dependencies.
150	
151	## Impact
152	
153	- **Plugin DX:** Authors discover `IOptionsMonitor<T>` without reading
154	  framework source code, and it actually works out of the box.
155	- **Runtime behaviour:** Config file edits are now picked up without a
156	  restart. This is a new capability but non-breaking — plugins using
157	  `IOptions<T>` are unaffected (it reads once at startup regardless).
158	- **API surface:** No plugin API changes.

2

11	## Problem
12	
13	The bot's outbound message queue (`IrcConnection._outboundChannel`) is a
14	bounded `Channel<IrcMessage>` with a capacity of 512. Plugins have no
15	visibility into or control over this queue. Two common needs:
16	
17	1. **Inspect queue depth** — a monitoring plugin or status command wants to
18	   show how backed up the outbound queue is (e.g. after a flood of messages).
19	2. **Clear the queue** — an operator or admin plugin wants to abort a
20	   large batch of pending messages (e.g. a plugin accidentally enqueued
21	   hundreds of messages, or the bot is being shut down gracefully).
22	
23	Today there is no way to do either without reaching into `IrcConnection`
24	internals.
25	
26	## Changes
27	
28	### 1. Add queue inspection/management to `IBot`
29	
30	```csharp
31	/// <summary>
32	/// Number of messages currently waiting in the outbound send queue.
33	/// </summary>
34	int OutboundQueueCount { get; }
35	
36	/// <summary>
37	/// Discards all messages currently waiting in the outbound send queue.
38	/// Messages already handed to the rate limiter or TCP write are not affected.
39	/// </summary>
40	Task ClearOutboundQueueAsync(CancellationToken ct);
41	```
42	
43	### 2. Expose queue state on `IrcConnection`
44	
45	`IrcConnection` already holds the `_outboundChannel`. Add:
46	
47	```csharp
48	/// <summary>Number of items waiting in the outbound channel.</summary>
49	public int OutboundQueueCount =>
50	    _outboundChannel?.Reader.Count ?? 0;
51	```
52	
53	For clearing, the simplest approach is to drain the channel by reading and
54	discarding all currently available items:
55	
56	```csharp
57	/// <summary>Drains all pending messages from the outbound channel.</summary>
58	public int DrainOutboundQueue()
59	{
60	    if (_outboundChannel is null) return 0;
61	    var drained = 0;
62	    while (_outboundChannel.Reader.TryRead(out _))
63	        drained++;
64	    return drained;
65	}
66	```
67	
68	This is safe because `SingleWriter = false` on the outbound channel, so
69	reads from any thread are valid as long as we respect the `SingleReader`
70	constraint. Since the write loop is the single reader, we need to
71	coordinate: either temporarily pause the write loop, or accept that a
72	small number of messages may be sent between the drain and the next
73	send. Given that this is an operator-initiated emergency action, the
74	race is acceptable and documented.
75	
76	**Alternative:** Replace the channel entirely by creating a new
77	`Channel<IrcMessage>` and swapping the reference. This guarantees no
78	stragglers but adds complexity around the write loop's reader reference.
79	The drain approach is simpler and sufficient.
80
