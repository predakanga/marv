`IOptionsMonitor<T>.OnChange` never fires — the documentation would be

single-line-per-provider flip from `false` to `true`. It's the
infrastructure that makes the documented `IOptionsMonitor<T>` pattern
actually useful, so bundling them keeps the story coherent.

**Why mention IOptionsSnapshot at all?** For completeness. Plugin authors

1	# CS-023: CTCP VERSION Response Override
2	
3	**Source:** Downstream feature request
4	**Scope:** Core
5	**Complexity:** Small
6	**Breaking changes:** None
7	**Status:** Pending
8	
9	---
10	
11	## Problem
12	
13	The bot responds to CTCP VERSION queries with a hardcoded string:
14	
15	```csharp
16	$"\x01VERSION Marv IRC Bot {MarvVersion.Current}\x01"
17	```
18	
19	(`IrcBot.cs`, line ~904)
20	
21	Some operators want to customize this — to include plugin names, the host
22	OS, or to obscure the bot's identity for security. There is currently no
23	way to change this without modifying the bot's source code.
24	
25	## Approach options considered
26	
27	| Approach | Pros | Cons |
28	|---|---|---|
29	| **A. Configuration property** | Simple, discoverable, no code changes at runtime | Static — can't include dynamic info (plugin list, uptime) |
30	| **B. Writable property on IBot** | Plugins can set it dynamically | Unclear ownership if multiple plugins set it; still just a string |
31	| **C. Subclass IrcBot** | Maximum flexibility | Defeats the plugin model; IrcBot is internal |
32	| **D. Configuration + format tokens** | Config-driven but with dynamic placeholders | Custom token system adds complexity |
33	| **E. Event/delegate on IBot** | Plugin provides a callback; full dynamic control | Clean ownership, composable, maximum flexibility |
34	
35	**Recommendation: Configuration property (A) with a delegate fallback (E).**
36	
37	A simple `CtcpVersionResponse` config property covers the 90% case (operators
38	who want a static string). For plugins that need dynamic responses, a
39	delegate property on `IBot` allows full control.
40	
41	## Changes
42	
43	### 1. Add `CtcpVersionResponse` to `MarvConfiguration`
44	
45	```csharp
46	/// <summary>
47	/// Custom response to CTCP VERSION queries. If null, uses the default
48	/// "Marv IRC Bot {version}" string. Set to empty string to suppress
49	/// VERSION responses entirely.
50	/// </summary>
51	public string? CtcpVersionResponse { get; set; }
52	```
53	
54	### 2. Add a delegate property to `IBot`
55	
56	```csharp
57	/// <summary>
58	/// Optional callback that generates the CTCP VERSION response string.
59	/// When set, takes precedence over the <c>CtcpVersionResponse</c>
60	/// configuration value. Return null to suppress the response.
61	/// </summary>
62	Func<string?>? CtcpVersionProvider { get; set; }
63	```
64	
65	### 3. Update `HandleCtcp` in `IrcBot`
66	
67	```csharp
68	case "VERSION":
69	    var versionResponse = CtcpVersionProvider?.Invoke()
70	        ?? _config.CtcpVersionResponse
71	        ?? $"Marv IRC Bot {MarvVersion.Current}";
72	
73	    if (!string.IsNullOrEmpty(versionResponse))
74	    {
75	        await SendRawAsync(new IrcMessage("NOTICE", [sender.Nick,
76	            $"\x01VERSION {versionResponse}\x01"]), ct);
77	    }
78	    break;
79	```
80	
81	### 4. Update PLUGIN_API.md
82	
83	Add `CtcpVersionProvider` to the IBot table in §5. Document the precedence
84	order: delegate > config > default.
85	
86	## Design decisions
87	
88	**Why not just config?** A static string can't include runtime information
89	like loaded plugins, uptime, or platform details. The delegate lets
90	plugins like a system-info plugin provide rich version strings.
91	
92	**Why not just a delegate?** Operators who just want to set
93	`"CtcpVersionResponse": "My Custom Bot"` in their config file shouldn't
94	need to write a plugin for it.
95	
96	**Why `Func<string?>` instead of an event?** Only one VERSION response
97	can be sent. An event implies multiple subscribers, which doesn't make
98	sense here. A single delegate with last-writer-wins semantics is clear.
99	
100	**Why allow suppressing the response?** Some operators don't want to
101	reveal bot software information. Returning null or setting an empty
102	string in config suppresses the NOTICE entirely.
103	
104	## Testing
105	
106	- **Unit test:** Default behavior — verify VERSION response contains
107	  `MarvVersion.Current`.
108	- **Unit test:** Set config value — verify it's used instead of the default.
109	- **Unit test:** Set delegate — verify it takes precedence over config.
110	- **Unit test:** Delegate returns null — verify no NOTICE is sent.
111	- **Unit test:** Config set to empty string — verify no NOTICE is sent.
112	
113	## Impact
114	
115	- **Configuration:** One new optional property in `MarvConfiguration`.
116	- **API surface:** One new property on `IBot`.
117	- **Plugin DX:** Plugins can dynamically control VERSION responses.

You're right — [OnRawMessage] handlers don't suppress the bot's built-in CTCP handling. The bot would still send its default VERSION response regardless of what the plugin does.

So for a plugin that wants full dynamic control, the path would be: set CtcpVersionResponse to empty string in config (to suppress the default), then handle it manually via [OnRawMessage("PRIVMSG")] and parse the CTCP yourself. That works but it's clunky — the plugin author has to coordinate config and code, plus manually parse CTCP framing.

A cleaner alternative that fits Marv's existing patterns: add a dedicated [OnCtcp("VERSION")] handler attribute, analogous to [OnCommand] and [OnRawMessage]. If a plugin registers a handler for a CTCP command, the bot skips its built-in response for that command. This keeps plugin authors in the attribute-based handler world they already know, and gives them a typed context with the sender/args already parsed — no raw CTCP parsing needed.

The spec would then be: - Config property (CtcpVersionResponse) for operators who want a static override - [OnCtcp] handler for plugins that need dynamic control — presence suppresses the default
