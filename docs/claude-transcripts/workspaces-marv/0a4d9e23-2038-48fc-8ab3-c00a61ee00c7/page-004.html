Triage GitHub Issues

Reconcile open GitHub issues with the local codebase by reviewing, discussing, and — when accepted — converting them into change specifications.

When to use

Invoke with /triage-issues when you want to process open GitHub issues.

Workflow

1. Fetch open issues

Run:

gh issue list --repo predakanga/marv --state open --json number,title,body,labels,comments --limit 50

Filter out issues that already have a label triaged or rejected.

2. For each untriaged issue

2a. If the issue has NO prior bot analysis comment

Read the issue body and any comments. Analyse the suggestion against the current codebase:

  • Is it feasible?
  • Does it overlap with an existing change spec or completed work?
  • What is the estimated scope/complexity?
  • Are there any design concerns or open questions?

Post a comment on the issue with your analysis using this template:

**Feasibility:** <High / Medium / Low>
**Scope:** <Core / Host / Plugin API / Docs / CI/CD / New package>
**Complexity:** <Trivial / Small / Medium / Large>
**Overlaps:** <None / CS-NNN — description>

<2-4 sentence summary of what the issue proposes and how it fits the project>

<Bullet points covering key design considerations, potential approaches,
and any concerns or trade-offs>

<Numbered list of questions for the issue author, if any>

`/accept` to approve or `/reject` to decline.*

Report to the user what you posted and move to the next issue.

2b. If the issue already has a bot analysis comment

Read ALL comments after the analysis. Look for /accept or /reject commands, but only honour them if the comment's authorAssociation is OWNER. Commands from other users should be treated as regular discussion comments.

  • /accept (from OWNER) — the issue has been approved. Proceed to step 3.
  • /reject (from OWNER) — the issue has been declined. Add the rejected label and post a short acknowledgement comment. Move on.
  • Other comments (or /accept//reject from non-owners) — these are discussion/clarification. Post a follow-up comment addressing the points raised, updating your analysis if needed. Move on.

3. Create change specifications (on /accept)

When an issue is accepted:

  1. Determine the next change spec number by reading docs/change_specs/README.md.
  2. Write one or more change spec .md files following the established format (see existing specs in docs/change_specs/ for the template). The spec's Source metadata should reference the GitHub issue (e.g. **Source:** GitHub issue #42). Do NOT write any code — specs only.
  3. Update docs/change_specs/README.md to include the new spec(s) with status Pending.
  4. Add the triaged label to the issue.
  5. Post a comment on the issue noting which change spec(s) were created.
  6. Follow the mandatory instructions in CLAUDE.md (commit, changelog if user-visible, prompt log).

Important notes

  • This skill does NOT implement any code. It only creates change specifications.
  • Only log to docs/prompts.md if actions were taken (e.g. posted analysis, created change specs, responded to discussion). If no issues needed action, skip the prompt log. The entry must match the format used by the rest of the file — a ## heading, a **Date**: line, the prompt in a blockquote, then a concise bulleted summary of actions taken (e.g. "Posted triage analysis on #5", "Created CS-029 from #2").
  • When analysing feasibility, read relevant source files — don't guess.
  • Keep issue comments concise and professional.
  • If gh commands fail with auth errors, ask the user to run ! gh auth login in their terminal.

## Summary: Handler Filter Pipeline and Handler Invocation System

Based on my thorough exploration of the Marv IRC bot codebase, here's a comprehensive analysis of the handler filter pipeline and invocation system:

### 1. **HandlerInvocation Struct**
**File:** `/workspaces/marv/src/Marv.Core/Plugin/HandlerInvocation.cs`

The `HandlerInvocation` is a readonly struct that describes a handler about to be invoked:
- **Method** (`MethodInfo`): The handler method that will be invoked
- **Target** (`object`): The target object (plugin instance or handler group instance)
- **Type** (`HandlerType`): The handler type (enum with values: Command, Regex, Event, RawMessage, Interval)
- **Context** (`object?`): The context object passed to the handler—cast to appropriate type based on Type (CommandContext, RegexMatchContext, event type, IrcMessage for raw, or null for intervals)
- **Attributes** (`IReadOnlyList<Attribute>`): Custom attributes on the handler method, pre-cached during discovery

### 2. **FilterResult Struct**
**File:** `/workspaces/marv/src/Marv.Core/Plugin/FilterResult.cs`

A simple readonly struct that carries only an allow/deny flag with static factories:
- **IsAllowed** (`bool`): Whether the handler is allowed to proceed
- **Static factories:** `FilterResult.Allowed` and `FilterResult.Denied`

**Design rationale:** Exists as a struct rather than plain bool to allow future extension (e.g., logging reasons, short-circuit flags) without breaking existing evaluator signatures.

### 3. **Filter Evaluation Pipeline**
**File:** `/workspaces/marv/src/Marv.Core/Plugin/MarvPlugin.cs` (lines 276-287)

The `FilterHandlerAsync` virtual method runs before each handler invocation:
```csharp
protected virtual async ValueTask<bool> FilterHandlerAsync(
    HandlerInvocation invocation, CancellationToken ct)
{
    foreach (var attr in invocation.Attributes.OfType<IFilteringAttribute>())
    {
        var evaluator = ResolveEvaluator(attr.EvaluatorType);
        var result = await evaluator.EvaluateAsync(attr, invocation, Bot, ct);
        if (!result.IsAllowed)
            return false;
    }
    return true;
}
```

The default implementation iterates through `IFilteringAttribute` attributes on the handler method and evaluates them in order. The first deny wins (short-circuit).

### 4. **Handler Invocation Flow**
**File:** `/workspaces/marv/src/Marv.Core/Plugin/MarvPlugin.cs` (lines 321-355)

The `InvokeHandlerSafe` method:
1. Constructs the `HandlerInvocation` struct with cached attributes
2. Calls `FilterHandlerAsync` to evaluate all filters
3. If filtering returns false, the handler is skipped
4. If filtering passes, invokes the handler with appropriate parameters
5. Catches and logs exceptions without crashing subsequent handlers

### 5. **IFilteringAttribute Interface**
**File:** `/workspaces/marv/src/Marv.Core/Plugin/IFilteringAttribute.cs`

A marker interface for attributes that participate in handler filtering:

### 9. **Handler Method Dispatch and Reflection**
**File:** `/workspaces/marv/src/Marv.Core/Plugin/MarvPlugin.cs` (lines 360-391)

Two overloaded static methods handle the actual invocation:

**With context argument:**

```csharp
private static async Task InvokeHandler(object target, MethodInfo method, object arg, CancellationToken ct)
{
    var parameters = method.GetParameters();
    object?[] args = parameters.Length switch
    {
        1 => [arg],
        2 when parameters[1].ParameterType == typeof(CancellationToken) => [arg, ct],
        _ => [arg, ct]
    };

    if (result is Task task)

```

**Without context (interval handlers):**

### 10. **Attribute Caching**

### 11. **Evaluator Caching and Resolution**

### Design Decisions (from CS-005)

1. **Why pass IBot to evaluators?** Evaluators need to take action when denying (send notices, kick users). Without IBot, the framework would need to anticipate every denial action.

2. **Why FilterResult instead of bool?** Future extensibility (logging reasons, short-circuit flags) without breaking signatures.

3. **Why not middleware pipeline?** Overengineered for typical IRC bot use. FilterHandlerAsync can handle multiple concerns in one override.

4. **Handler groups and filtering:** FilterHandlerAsync runs on the owning plugin, not handler groups. HandlerInvocation.Target distinguishes between them.

5. **Filter exceptions:** Treated like handler exceptions—logged and handler skipped (fail-closed).

The system currently doesn't have an explicit mechanism for this; evaluators can only return allow/deny, and handlers must re-examine context if they need filter-computed data.
