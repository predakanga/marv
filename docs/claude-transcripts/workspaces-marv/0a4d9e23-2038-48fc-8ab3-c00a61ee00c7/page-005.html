3	Quick reference for building Marv plugins. All types are in the `Marv.Core`
4	namespace unless noted otherwise.

8	## 1. Minimal Plugin
9	
10	```csharp

12	using Marv.Core.Plugin;
13	using Microsoft.Extensions.Logging;
14	
15	public class HelloPlugin : MarvPlugin
16	{

19

21	    private async Task HandleHello(CommandContext ctx, CancellationToken ct)

25	}
26	```

28	The three-parameter constructor (`IBot`, `IPluginActivator`, `ILoggerFactory`)
29	is the minimum. Add more DI parameters after `ILoggerFactory` as needed (see
30	§8 and §9).

34	## 2. Constructor & Base Class
35	
36	```
37	protected MarvPlugin(IBot bot, IPluginActivator activator, ILoggerFactory loggerFactory)
38	```
39	
40	**Protected members:** `IBot Bot`, `ILogger Logger` (scoped to your plugin type).
41	
42	**Lifecycle overrides** (all `virtual`, all no-op by default):
43	
44	| Method | When |
45	|---|---|
46	| `OnLoadAsync(ct)` | Once, after construction |
47	| `OnConnectedAsync(ct)` | Each IRC connection |
48	| `OnDisconnectedAsync()` | Connection lost (IChannel/IUser refs are stale) |
49	| `OnUnloadAsync()` | Shutdown, before DI disposal |
50	| `HandleEventAsync(evt, ct)` | Each event (sequential, never concurrent) |
51	| `FilterHandlerAsync(invocation, ct)` | Before each handler — return `false` to skip |

55	## 3. Handler Attributes
56	
57	### `[OnCommand("name")]` → `Task Handler(CommandContext ctx, CancellationToken ct)`
58	
59	Fires when a message starts with `[prefix][command]`. Command matching is
60	case-insensitive. AllowMultiple — same method can handle multiple commands.
61	
62	| Property | Type | Default | Effect |
63	|---|---|---|---|
64	| `Prefix` | `string?` | bot's `CommandPrefix` | Override the command prefix |
65	| `ChannelOnly` | `bool` | `false` | Skip DMs |
66	| `DirectOnly` | `bool` | `false` | Skip channel messages |
67	| `Channel` | `string?` | `null` | Only fire in this channel (case-insensitive) |
68	
69	### `[OnRegex("pattern")]` → `Task Handler(RegexMatchContext ctx, CancellationToken ct)`
70	
71	Fires when message text (IRC formatting stripped) matches the pattern. Same
72	filter properties as `[OnCommand]` minus `Prefix`, plus:
73	
74	| Property | Type | Default | Effect |
75	|---|---|---|---|
76	| `Options` | `RegexOptions` | `None` | Additional regex options (`Compiled` is always added) |
77	
78	### `[OnEvent]` → `Task Handler(TEvent evt, CancellationToken ct)`
79	
80	Event type is inferred from the first parameter (must extend `MarvEvent`).

283	## 8. Configuration
284	
285	1. Create a config class with `[PluginConfig]`:
286	
287	```csharp
288	[PluginConfig(Section = "Greet")]
289	public record GreetConfig
290	{
291	    public string Message { get; init; } = "Welcome, {nick}!";
292	    public bool Enabled { get; init; } = true;
293	}
294	```
295	
296	2. Inject `IOptions<T>` in your plugin constructor:
297	
298	```csharp
299	public GreetExamplePlugin(IBot bot, IPluginActivator activator, ILoggerFactory loggerFactory,
300	    IOptions<GreetConfig> config)
301	    : base(bot, activator, loggerFactory)
302	{
303	    _config = config.Value;
304	}
305	```
306	
307	Config binds to a root-level section in the configuration file (e.g. `"Greet"`).
308	
309	### Options API variants
310	
311	The full `Microsoft.Extensions.Options` API is available for plugin
312	configuration. In addition to `IOptions<T>`, you can inject:
313	
314	| Type | Lifetime | Use case |
315	|---|---|---|
316	| `IOptions<T>` | Singleton | Read config once at construction |
317	| `IOptionsMonitor<T>` | Singleton | React to config changes at runtime via `OnChange` |
318	| `IOptionsSnapshot<T>` | Scoped | Re-read config per scope (rarely needed for plugins) |
319	
320	Marv enables `reloadOnChange` on all file-based configuration providers, so
321	`IOptionsMonitor<T>.OnChange` fires automatically when the config file is
322	edited at runtime.
323	
324	Example using `IOptionsMonitor<T>` to react to config file edits:
325	
326	```csharp
327	public class MyPlugin(IBot bot, IPluginActivator activator, ILoggerFactory loggerFactory,
328	    IOptionsMonitor<MyConfig> configMonitor)
329	    : MarvPlugin(bot, activator, loggerFactory)
330	{
331	    private MyConfig _config = configMonitor.CurrentValue;
332	
333	    public override Task OnConnectedAsync(CancellationToken ct)
334	    {
335	        configMonitor.OnChange(updated => _config = updated);
336	        return Task.CompletedTask;
337	    }
338	}
339	```

343	## 9. Services
344	
345	### Service lifetimes
346	
347	Core services like `IBot`, `IServerInfo`, `ICapabilityManager`,
348	`IBotStatistics`, and `IPluginActivator` are **connection-scoped** — a fresh
349	instance is created for each IRC connection and disposed on disconnect.
350	Plugins are also recreated per connection, so they always receive the
351	current connection's services.
352	
353	Plugins can register services with any standard DI lifetime:
354	
355	| Lifetime | `ConfigureServices` call | Behaviour |
356	|---|---|---|
357	| **Scoped** | `services.AddScoped<T, TImpl>()` | Fresh instance per connection — matches plugin lifetime |
358	| **Singleton** | `services.AddSingleton<T, TImpl>()` | Survives reconnects — use for cross-connection state (caches, metrics) |
359	| **Transient** | `services.AddTransient<T, TImpl>()` | New instance per resolution |
360	
361	> **Note:** Singleton services must not capture scoped services (e.g. `IBot`)
362	> in their constructors. The DI container will reject this. If a singleton
363	> needs access to connection-scoped services, inject `IServiceScopeFactory`
364	> and create a scope on demand.
365	
366	**Providing a service:**
367	
368	```csharp
369	[ProvidesService(typeof(IMyService))]
370	public class MyServicePlugin : MarvPlugin
371	{
372	    public MyServicePlugin(IBot bot, IPluginActivator activator, ILoggerFactory loggerFactory)
373	        : base(bot, activator, loggerFactory) { }
374	
375	    public static void ConfigureServices(IServiceCollection services)
376	    {
377	        services.AddScoped<IMyService, MyServiceImpl>();
378	    }
379	}
380	```
381	
382	**Consuming a service** (use `= null` for optional):
383	
384	```csharp
385	public MyConsumerPlugin(IBot bot, IPluginActivator activator, ILoggerFactory loggerFactory,
386	    IMyService? svc = null)
387	    : base(bot, activator, loggerFactory) { _svc = svc; }
388	```
389	
390	Use `[DependsOn(typeof(OtherPlugin))]` for explicit load ordering without a
391	service relationship.

422	## 11. Handler Filters
423	
424	Declarative cross-cutting logic (auth, rate limits, auditing) via attributes:
425	
426	```csharp
427	[AttributeUsage(AttributeTargets.Method)]
428	public sealed class RequireAccountAttribute : Attribute, IFilteringAttribute
429	{
430	    public Type EvaluatorType => typeof(RequireAccountEvaluator);
431	}
432	
433	public class RequireAccountEvaluator : FilterEvaluator<RequireAccountAttribute>
434	{
435	    protected override ValueTask<FilterResult> EvaluateAsync(
436	        RequireAccountAttribute attribute, HandlerInvocation invocation,
437	        IBot bot, CancellationToken ct)
438	    {
439	        if (invocation.Context is HandlerContext ctx && ctx.Sender.Account is null)
440	        {
441	            _ = ctx.ReplyAsync("You must be logged in.", ct);
442	            return ValueTask.FromResult(FilterResult.Denied);
443	        }
444	        return ValueTask.FromResult(FilterResult.Allowed);
445	    }
446	}
447	```
448	
449	Apply to any handler: `[RequireAccount] [OnCommand("admin")] private async Task ...`
450	
451	**HandlerInvocation** fields: `Method`, `Target`, `Type` (Command/Regex/Event/
452	RawMessage/Interval), `Context` (the context object or `null` for intervals),
453	`Attributes` (pre-cached).
454

# TDW.Marv.Core

Core library for the [Marv IRC bot](https://github.com/predakanga/marv).
Provides the plugin API, bot abstractions, IRC protocol handling, and
service registry.

## Who is this for?

This package is for **plugin authors** building extensions for Marv. It
provides the base classes, attributes, context types, and interfaces you
need to write plugins.

If you're writing **tests** for your plugins, also add
[TDW.Marv.Testing](https://www.nuget.org/packages/TDW.Marv.Testing).

## Quick start

Create a class library targeting the same .NET version as Marv, add a
reference to this package, and implement a plugin:

```csharp
using Marv.Core.Platform;
using Marv.Core.Plugin;
using Microsoft.Extensions.Logging;

public class HelloPlugin : MarvPlugin
{
    public HelloPlugin(IBot bot, IPluginActivator activator, ILoggerFactory loggerFactory)
        : base(bot, activator, loggerFactory) { }

    [OnCommand("hello")]
    private async Task HandleHello(CommandContext ctx, CancellationToken ct)
    {
        await ctx.ReplyAsync($"Hi, {ctx.Sender.Nick}!", ct);
    }
}
```

## Key types

| Type | Description |
|------|-------------|
| `MarvPlugin` | Base class for all plugins |
| `IBot` | Bot instance — send messages, query state |
| `CommandContext` | Context for `[OnCommand]` handlers |
| `RegexMatchContext` | Context for `[OnRegex]` handlers |
| `IPluginActivator` | Create instances with DI resolution |
| `IFilteringAttribute` | Declare handler filter attributes |
| `FilterEvaluator<T>` | Implement handler filter logic |

## Handler attributes

| Attribute | Handler signature | Fires when |
|-----------|-------------------|------------|
| `[OnCommand("name")]` | `Task(CommandContext, CancellationToken)` | Prefixed command message |
| `[OnRegex("pattern")]` | `Task(RegexMatchContext, CancellationToken)` | Message matches pattern |
| `[OnEvent]` | `Task(TEvent, CancellationToken)` | Typed event (inferred from parameter) |
| `[OnRawMessage("CMD")]` | `Task(IrcMessage, CancellationToken)` | Raw IRC message |
| `[OnInterval(Seconds = n)]` | `Task(CancellationToken)` | Timer tick while connected |

All handler methods may omit the `CancellationToken` parameter.

## Configuration

Declare a config class with `[PluginConfig]` and inject `IOptions<T>`:

```csharp
[PluginConfig(Section = "MyPlugin")]
public record MyConfig
{
    public string Greeting { get; init; } = "Hello!";
}
```

Config binds to a root-level JSON section matching the `Section` name.
`IOptionsMonitor<T>` is also available for live-reload support.

## Services

Plugins can provide services to other plugins via `[ProvidesService]` and
`ConfigureServices`. Consume services by adding constructor parameters
(use `= null` for optional dependencies).

Full API reference: [Plugin API docs](https://github.com/predakanga/marv/blob/main/docs/PLUGIN_API.md)

# Dependencies and .NET libraries - .NET | Microsoft Learn

The primary way of adding dependencies to a .NET library is referencing NuGet packages. NuGet package references allow you to quickly reuse and leverage already written functionality, but they're a common source of friction for .NET developers. Correctly managing dependencies is important to prevent changes in other .NET libraries from breaking your .NET library, and vice versa!

## Diamond dependencies

It's common for a .NET project to have multiple versions of a package in its dependency tree. For example, an app depends on two NuGet packages, each of which depends on a different version of the same package. A diamond dependency now exists in the app's dependency graph.

![Diamond dependency](media/dependencies/diamond-dependency.png)

At build time, NuGet analyzes all the packages that a project depends on, including the dependencies of dependencies. When multiple versions of a package are detected, rules are evaluated to pick one. Unifying packages is necessary because running side-by-side versions of an assembly in the same application is problematic in .NET.

Most diamond dependencies are easily resolved; however, they can create issues in certain circumstances:

- **Conflicting NuGet package references** prevent a version from being resolved during package restore.
- **Breaking changes between the versions** cause bugs and exceptions at runtime.
- **The package assembly is strong named**, the assembly version changed, and the app is running on .NET Framework. Assembly binding redirects are required.

It's not possible to know what packages will be used alongside your own. A good way to reduce the likelihood of a diamond dependency breaking your library is to minimize the number of packages you depend on.

✔️ DO review your .NET library for unnecessary dependencies.

## NuGet dependency version ranges

A package reference specifies the range of valid packages it allows. Typically, the package reference version in the project file is the minimum version, and there's no maximum.

```xml
<!-- Accepts any version 1.0 and above. -->
<PackageReference Include="ExamplePackage" Version="1.0" />
```

The rules that NuGet uses when resolving dependencies are [complex](/en-us/nuget/consume-packages/dependency-resolution), but NuGet [by default](/en-us/nuget/consume-packages/install-use-packages-visual-studio#install-and-update-options) looks for the lowest applicable version. NuGet prefers the lowest applicable version over using the highest available because the lowest will have the least compatibility issues.

Because of NuGet's lowest applicable version rule, it isn't necessary to place an upper version or exact range on package references to avoid getting the latest version. NuGet already tries to find the lowest, most compatible version for you.

```xml
<!-- Accepts 1.0 up to 1.x, but not 2.0 and higher. -->
<PackageReference Include="ExamplePackage" Version="[1.0,2.0)" />

<!-- Accepts exactly 1.0. -->
<PackageReference Include="ExamplePackage" Version="[1.0]" />
```

Upper version limits will cause NuGet to fail if there's a conflict. For example, one library accepts exactly 1.0 while another library requires 2.0 or above. While breaking changes may have been introduced in version 2.0, a strict or upper limit version dependency guarantees an error.

![Diamond dependency conflict](media/dependencies/diamond-dependency-conflict.png)

❌ DO NOT have NuGet package references with no minimum version.

❌ AVOID NuGet package references that demand an exact version.

❌ AVOID NuGet package references with a version upper limit.

For more information, see [Package versioning](/en-us/nuget/concepts/package-versioning).

## NuGet shared source packages

One way to reduce external NuGet package dependencies is to reference shared source packages. A shared source package contains [source code files](/en-us/nuget/reference/nuspec#including-content-files) that are included in a project when referenced. Because you're just including source code files that are compiled with the rest of your project, there's no external dependency and chance of conflict.

Shared source packages are great for including small pieces of functionality. For example, you might reference a shared source package of helper methods for making HTTP calls.

![Shared source package](media/dependencies/shared-source-package.png)

```xml
<PackageReference Include="Microsoft.Extensions.Buffers.Testing.Sources" PrivateAssets="All" Version="1.0" />
```

![Shared source project](media/dependencies/shared-source-project.png)

Shared source packages have some limitations. They can only be referenced by `PackageReference`, so older `packages.config` projects are excluded. Also, shared source packages are only usable by projects with the same language. Because of these limitations, shared source packages are best used to share functionality within an open-source project.

✔️ CONSIDER referencing shared source packages for small, internal pieces of functionality.

✔️ CONSIDER making your package a shared source package if it provides small, internal pieces of functionality.

✔️ DO reference shared source packages with `PrivateAssets="All"`.

> 
> This setting tells NuGet the package is only to be used at development time and shouldn't be exposed as a public dependency.

❌ DO NOT have shared source package types in your public API.

> 
> Shared source types are compiled into the referencing assembly and can't be exchanged across assembly boundaries. For example, a shared-source `IRepository` type in one project is a separate type from the same shared-source `IRepository` in another project. Types in shared source packages should have an `internal` visibility.

❌ DO NOT publish shared source packages to NuGet.org.

> 
> Shared source packages contain source code and can only be used by projects with the same language type. For example, a C# shared source package cannot be used by an F# application.
> 
> Publish shared source packages to a [local feed or MyGet](publish-nuget-package) to consume them internally within your project.

NuGet's "lowest applicable version" rule only applies when resolving the dependency graph — it picks the lowest version that satisfies all constraints across all packages in the consumer's project. In practice, consumers almost always have their own direct or transitive reference to Microsoft.Extensions.* at a higher patch version (from the .NET SDK, the runtime metapackage, or other dependencies), so NuGet unifies upward to that version anyway.

The only scenario where a consumer would actually get 10.0.0 is if they had zero other references to those packages and did a fresh restore — and even then, 10.0.0 is a shipped, supported release. If it had a critical bug, Microsoft would yank it from the feed.

The current setup is correct per the guidance.
