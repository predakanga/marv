## Triage Analysis

**Feasibility:** High
**Scope:** Core / Host
**Complexity:** Small
**Overlaps:** None

### Summary

The bot currently auto-reconnects unconditionally in `MarvBotService.ExecuteAsync`, with hardcoded exponential backoff (5s initial, 300s max). There is no configuration option to disable this. The request is to allow downstream projects to let exceptions propagate and terminate the process instead of silently reconnecting.

### Design Notes

- The reconnect loop lives in `MarvBotService.ExecuteAsync` — it wraps the entire connection lifecycle in a `while (!stoppingToken.IsCancellationRequested)` loop with exception handling that always continues.
- A simple `AutoReconnect` boolean on `MarvConfiguration` (defaulting to `true`) would be the least-disruptive approach. When `false`, the service would re-throw or exit cleanly after a connection failure.
- The backoff constants (`InitialBackoffSeconds`, `MaxBackoffSeconds`) are also hardcoded — these could optionally be exposed as configuration at the same time, but that's a separate concern.
- Since `MarvBotService` is a `BackgroundService`, an unhandled exception will stop the host. The downstream use case of "let exceptions bubble up and kill the program" maps cleanly to this: just don't catch the exception when `AutoReconnect` is `false`.
- Plugins are already notified of disconnections via `NotifyDisconnectedAsync` — this behaviour should be preserved regardless of the reconnect setting.

### Open Questions

1. When reconnect is disabled, should the bot exit with a non-zero exit code on connection failure, or shut down gracefully via `IHostApplicationLifetime.StopApplication()`?
2. Should the backoff timing also be configurable as part of this change, or kept as a separate concern?
