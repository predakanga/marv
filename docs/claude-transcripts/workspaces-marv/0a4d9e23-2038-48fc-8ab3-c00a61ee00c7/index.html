#242026-06-17T13:08:44.993Z

Just re-reading that page, is there any reason not to set the package versions to something like "[10.0, 11.0)"?

Yes — the guidance on that same page explicitly warns against it:

❌ AVOID NuGet package references with a version upper limit.

The reason is diamond dependencies. If your library specifies [10.0, 11.0) and a consumer also depends on another package that requires Microsoft.Extensions.* >= 11.0, NuGet will fail to resolve the conflict — it can't pick a version that satisfies both constraints. Without the upper bound, NuGet can unify to the higher version, which is almost always compatible (especially within Microsoft.Extensions where major version bumps track the .NET runtime version).

Since Marv.Core already targets net10.0, the TFM itself already constrains consumers to the .NET 10+ ecosystem. The version floor of 10.0.0 is sufficient.

#252026-06-17T13:10:23.228Z

Good point. My concern is just that since NuGet prefers the lowest applicable version, it'll default to using 10.0.0 even when a newer version is available with bugfixes. Or am I overthinking this?

You're overthinking it. NuGet's "lowest applicable version" rule only applies when resolving the dependency graph — it picks the lowest version that satisfies all constraints across all packages in the consumer's project. In practice, consumers almost always have their own direct or transitive reference to Microsoft.Extensions.* at a higher patch version (from the .NET SDK, the runtime metapackage, or other dependencies), so NuGet unifies upward to that version anyway.

The only scenario where a consumer would actually get 10.0.0 is if they had zero other references to those packages and did a fresh restore — and even then, 10.0.0 is a shipped, supported release. If it had a critical bug, Microsoft would yank it from the feed.

The current setup is correct per the guidance.

#262026-06-17T13:12:26.799Z

Okay. One last question then - the Dockerfile includes PDBs for Marv and Marv.Core. Is it good practice to include these?

1 read

Yes, it's good practice to include them. PDBs in a Docker image enable meaningful stack traces with file names and line numbers when exceptions occur in production. Without them, you'd only get method names and IL offsets, which makes debugging much harder.

The size cost is minimal — portable PDBs for a project this size are typically a few hundred KB. The tradeoff would only matter for very size-constrained environments, and even then most teams keep them.
