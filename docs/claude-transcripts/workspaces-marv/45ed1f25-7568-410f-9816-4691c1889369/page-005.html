Assistant2026-06-01T12:35:41.310Z

Two good questions. Let me address them:

1. Release depending on CI checks: Yes, the cleanest approach is to add a gate job at the start of the release workflow that waits for the CI workflow to pass on the same commit. This avoids duplicating all the lint/analysis jobs while guaranteeing they've passed. We can use gh to check for a successful CI run on the tagged commit SHA.

2. Pre-built artifacts in Docker: I'd advise against this. The standard practice is to keep Docker builds self-contained — the Dockerfile plus source should be everything needed to produce the image. Injecting pre-built binaries means the image is no longer reproducible from the repo alone, and you lose the guarantee that the image contents were built in a consistent environment. The actual build time in the Docker step is only ~8 seconds (most is NuGet restore, which layers cache well). The tradeoff isn't worth the complexity.

Want me to go ahead with just the CI gate approach?
