Triage GitHub Issues

Reconcile open GitHub issues with the local codebase by reviewing, discussing, and — when accepted — converting them into change specifications.

When to use

Invoke with /triage-issues when you want to process open GitHub issues.

Workflow

1. Fetch open issues

Run:

gh issue list --repo predakanga/marv --state open --json number,title,body,labels,comments --limit 50

Filter out issues that already have a label triaged or rejected.

2. For each untriaged issue

2a. If the issue has NO prior bot analysis comment

Read the issue body and any comments. Analyse the suggestion against the current codebase:

  • Is it feasible?
  • Does it overlap with an existing change spec or completed work?
  • What is the estimated scope/complexity?
  • Are there any design concerns or open questions?

Post a comment on the issue with your analysis using this template:

## Triage Analysis

**Feasibility:** <High / Medium / Low>
**Scope:** <Core / Host / Plugin API / Docs / CI/CD / New package>
**Complexity:** <Trivial / Small / Medium / Large>
**Overlaps:** <None / CS-NNN — description>

### Summary

<2-4 sentence summary of what the issue proposes and how it fits the project>

### Design Notes

<Bullet points covering key design considerations, potential approaches,
and any concerns or trade-offs>

### Open Questions

<Numbered list of questions for the issue author, if any>

---
*Automated triage by Claude Code. Reply to discuss, or comment
`/accept` to approve or `/reject` to decline.*

Report to the user what you posted and move to the next issue.

2b. If the issue already has a bot analysis comment

Read ALL comments after the analysis. Look for:

  • /accept — the issue author has approved the change. Proceed to step 3.
  • /reject — the issue author has declined the change. Add the rejected label and post a short acknowledgement comment. Move on.
  • Other comments — these are discussion/clarification. Post a follow-up comment addressing the points raised, updating your analysis if needed. Move on.

3. Create change specifications (on /accept)

When an issue is accepted:

  1. Determine the next change spec number by reading docs/change_specs/README.md.
  2. Write one or more change spec .md files following the established format (see existing specs in docs/change_specs/ for the template). The spec's Source metadata should reference the GitHub issue (e.g. **Source:** GitHub issue #42). Do NOT write any code — specs only.
  3. Update docs/change_specs/README.md to include the new spec(s) with status Pending.
  4. Add the triaged label to the issue.
  5. Post a comment on the issue noting which change spec(s) were created.
  6. Follow the mandatory instructions in CLAUDE.md (commit, changelog if user-visible, prompt log).

Important notes

  • This skill does NOT implement any code. It only creates change specifications.
  • When analysing feasibility, read relevant source files — don't guess.
  • Keep issue comments concise and professional.
  • If gh commands fail with auth errors, ask the user to run ! gh auth login in their terminal.

191	    private static string? FindClosestMatch(
192	        string requested, IReadOnlyList<PluginMetadata> allMetadata)
193	    {
194	        var requestedLower = requested.ToLowerInvariant();
195	        string? bestMatch = null;
196	        var bestDistance = int.MaxValue;
197

225	    /// <summary>
226	    /// Computes the Levenshtein edit distance between two strings.
227	    /// </summary>
228	    private static int LevenshteinDistance(string a, string b)
229	    {
230	        if (a.Length == 0) return b.Length;
231	        if (b.Length == 0) return a.Length;
232	
233	        var prev = new int[b.Length + 1];
234	        var curr = new int[b.Length + 1];
235	
236	        for (var j = 0; j <= b.Length; j++)
237	            prev[j] = j;
238	
239	        for (var i = 1; i <= a.Length; i++)
240	        {
241	            curr[0] = i;
242	            for (var j = 1; j <= b.Length; j++)
243	            {
244	                var cost = a[i - 1] == b[j - 1] ? 0 : 1;
245	                curr[j] = Math.Min(
246	                    Math.Min(curr[j - 1] + 1, prev[j] + 1),
247	                    prev[j - 1] + cost);
248	            }
249	
250	            (prev, curr) = (curr, prev);
251	        }
252	
253	        return prev[b.Length];
254	    }

### Summary

This proposes introducing `IServiceScope` into the plugin lifecycle so that plugins are explicitly scoped to each IRC connection rather than being implicitly tied to it. Currently, all core services and plugins are registered as singletons, and plugin instances are created once per connection cycle in `MarvBotService.ExecuteAsync`. Plugins can only register singleton or transient services via `ConfigureServices`. This change would create a new DI scope per connection and allow plugins to register scoped services that follow the connection lifecycle.

### Design Notes

- Currently `MarvBotService` calls `PluginManager.InstantiatePlugins` at the top of each reconnect loop — plugins are recreated per connection, but DI services they register are singletons that survive reconnects. This mismatch is the core issue.
- The `ConfigureServices` static method is called during `AddMarv` (at startup), long before any connection. A new scope would need to be created in `MarvBotService` at connection time and disposed on disconnect.
- `IrcBot`, `ServerInfo`, `CapabilityManager`, and `IBotStatistics` are currently singletons but semantically belong to a single connection — they reset on reconnect. These would be natural candidates for scoped registration.
- `PluginActivator` currently resolves from the root `IServiceProvider`. It would need to resolve from the connection-scoped `IServiceProvider` instead, so that plugins receive scoped dependencies.
- This is a **breaking change to the plugin API**: plugin services registered as singletons today might need to become scoped, and plugins that inject `IServiceProvider` directly would get a scoped provider.
- The `Marv.Testing` package would need updates to create appropriate scopes in test fixtures.

1. Should plugins themselves be scoped services (created by the DI container per scope), or should they remain manually instantiated but receive scoped dependencies?
