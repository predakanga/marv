289	## 4. Plugin Architectures with Inter-Plugin Services
290	
291	### The Problem
292	
293	We want plugins to be able to:
294	1. **Provide services** (e.g., an auth plugin exposes `IAuthorizationService`)
295	2. **Consume services** from other plugins (e.g., a moderation plugin uses
296	   `IAuthorizationService` to check permissions)
297	3. **Handle optional dependencies** gracefully (the moderation plugin works
298	   without auth, just with reduced functionality)
299	4. **Load in correct order** based on dependencies
300	
301	### Approach 1: .NET `IServiceProvider` (Microsoft DI)
302	
303	**How it works**: Plugins register services in a `IServiceCollection`
304	during a configuration phase. The DI container is built once. Plugins
305	receive dependencies via constructor injection.
306	
307	**Pros**:
308	- Standard .NET pattern; familiar to C# developers
309	- Well-tested, high-performance implementation
310	- Supports scoped, singleton, and transient lifetimes
311	- Constructor injection makes dependencies explicit and testable
312	
313	**Cons**:
314	- Container is built once and is immutable — adding services after build
315	  requires rebuilding the container
316	- Plugin load order must be determined before container build
317	- Optional dependencies are awkward (you must register a null/no-op
318	  implementation or use `IServiceProvider.GetService<T>()` which returns
319	  null)
320	- No built-in concept of "this service is provided by plugin X"
321	
322	**Suitability**: Good foundation, but needs augmentation for plugin
323	lifecycle management.
324	
325	### Approach 2: Explicit Service Registry
326	
327	**How it works**: A custom `IServiceRegistry` managed by the bot core.
328	Plugins call `registry.Register<IAuthService>(this, implementation)` during
329	setup and `registry.Get<IAuthService>()` to consume. The registry
330	understands plugin identity and lifecycle.
331	
332	**Pros**:
333	- Can track which plugin provides which service
334	- Can handle late registration and optional dependencies naturally
335	- Can provide diagnostics ("auth service provided by AuthPlugin v1.2")
336	- Can enforce single-provider-per-interface or allow multiple providers

371	### Load Order and Optional Dependencies
372	
373	**Topological sort**: Declare dependencies as attributes. Before loading,
374	build a dependency graph and topologically sort it. Cycles are a
375	configuration error. Missing required dependencies prevent startup.
376	Optional dependencies are ordered-if-present but don't block.
377	
378	**Graceful degradation**: Plugins should declare whether a service
379	dependency is required or optional. Required = fail to load if not met.
380	Optional = load but potentially with reduced functionality. The plugin
381	base class can provide helpers like `HasService<T>()` and
382	`GetOptionalService<T>()`.

### Recommended Approach: Hybrid

Use Microsoft's `IServiceCollection` / `IServiceProvider` as the underlying
mechanism, but wrap it in a plugin-aware layer. **There is a single DI
container for the entire application** — core services (configuration,
logging, IRC client, bot) and plugin-contributed services all live in one
`IServiceCollection` which builds one `IServiceProvider`. There is no
separate container for plugins.

The startup sequence has two distinct phases:

1. **Bootstrap phase** (before DI): Read configuration from files,
   environment variables, and command-line arguments. Determine which
   plugin assemblies to load. This phase uses no DI — it runs before the
   container exists. The plugin list comes from core configuration read
   during bootstrap, so there is no circular dependency.

2. **DI phase** (building the single container):
   a. **Assembly loading**: Load plugin assemblies discovered during
      bootstrap, discover plugin types.
   b. **Dependency sort**: Topological sort based on declared dependencies
      (attributes on plugin classes, e.g.
      `[DependsOn(typeof(AuthPlugin))]` or
      `[ConsumeService(typeof(IAuthService), Optional = true)]`).
   c. **Service registration**: Each plugin gets a chance to register
      services into the shared `IServiceCollection` via a static or
      type-level method (e.g. `ConfigureServices(IServiceCollection)`).
      This does not require constructing the plugin. Core services
      (configuration, logging, IRC client) are also registered here.
      Plugins are called in dependency order.
   d. **Container build**: The single `IServiceProvider` is built.
   e. **Plugin construction**: Plugin instances are resolved from the
      container — configuration and services injected via constructor.

3. **Runtime**: Plugins can query for optional services via
   `IServiceProvider.GetService<T>()` (returns null if not registered).

This gives us:
- A single, standard .NET DI container for the whole application
- Familiar .NET DI patterns for most use cases
- Explicit dependency declarations for load ordering
- Optional dependencies via nullable injection or runtime resolution
- Plugin identity tracking via a thin metadata layer on top

Plugins should declare a class modeling their configuration, which is injected into the plugin via constructor. Do not follow the common bot framework pattern of accessing configuration through a bot object (e.g. `bot.config`, `self.config`).

**Why:** The user considers bot-object config access an anti-pattern. Constructor-injected typed config makes requirements explicit, validates at startup, and is testable without a bot instance.

**How to apply:** When designing plugin APIs or writing example plugins, always use a dedicated config POCO/record injected via constructor. Never expose plugin configuration through the bot class or a shared config bag. Related: [[single-di-container]].
