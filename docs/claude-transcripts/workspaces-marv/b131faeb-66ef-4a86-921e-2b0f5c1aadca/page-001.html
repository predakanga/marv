10	
11	## Problem
12	
13	`SendAndAwaitAsync` currently relies on the `labeled-response` IRCv3
14	capability to correlate requests with responses. When `labeled-response`
15	is not available, the method falls back to sending the message and
16	immediately returning an empty list — making it effectively useless:
17	
18	```csharp
19	else
20	{
21	    // Fallback: just send and return empty (no correlation available)
22	    await SendRawAsync(message, ct);
23	    return [];
24	}
25	```
26	
27	Many IRC commands have well-defined response sequences terminated by an
28	`ENDOF*` numeric. For example:
29	
30	| Command | Reply numerics | Terminator |
31	|---|---|---|
32	| `WHO` | `352` (RPL_WHOREPLY) | `315` (RPL_ENDOFWHO) |
33	| `WHOIS` | `311`, `312`, `313`, `317`, `318`, `319`, etc. | `318` (RPL_ENDOFWHOIS) |
34	| `WHOWAS` | `314` (RPL_WHOWASUSER) | `369` (RPL_ENDOFWHOWAS) |
35	| `LIST` | `322` (RPL_LIST) | `323` (RPL_LISTEND) |
36	| `NAMES` | `353` (RPL_NAMREPLY) | `366` (RPL_ENDOFNAMES) |
37	| `BANLIST` (`MODE +b`) | `367` (RPL_BANLIST) | `368` (RPL_ENDOFBANLIST) |
38	| `LINKS` | `364` (RPL_LINKS) | `365` (RPL_ENDOFLINKS) |
39	| `INFO` | `371` (RPL_INFO) | `374` (RPL_ENDOFINFO) |

# CS-025: Replace Custom Docker Logic with Testcontainers

**Source:** Developer feedback
**Scope:** Tests / Build infrastructure
**Complexity:** Small-Medium
**Breaking changes:** None (test infrastructure only)
**Status:** Pending

---

## Problem

Integration tests rely on a manually managed ngircd Docker container
orchestrated through Makefile targets (`make ircd-start` / `make ircd-stop`)
and a hand-rolled TCP probe in `IrcServerFixture`. This has several drawbacks:

1. **Manual lifecycle management.** Developers must remember to start the
   container before running integration tests and stop it afterwards. The
   `make test-integration` target automates this, but running tests from an
   IDE or directly via `dotnet test` does not.

2. **Fragile port assumptions.** The fixture hardcodes `localhost:6667`. If
   another process occupies that port, or if tests run in parallel CI jobs,
   they collide silently.

3. **No container cleanup on failure.** If a test run crashes or is
   interrupted, the container is left running until someone manually runs
   `make ircd-stop` or `docker rm -f marv-ircd`.

4. **Skip-on-unavailable heuristic.** `IrcServerFixture` probes the port and
   sets `IsAvailable`; every test must call `SkipIfUnavailable()`. This means
   integration tests silently pass in CI if the container failed to start.

## Design

Replace the custom Docker orchestration with
[Testcontainers for .NET](https://dotnet.testcontainers.org/), a mature
library that manages container lifecycles programmatically within the test
process.

### Revised `IrcServerFixture`

```csharp
public class IrcServerFixture : IAsyncLifetime
{
    private readonly IContainer _container = new ContainerBuilder()
        .WithImage("linuxserver/ngircd")
        .WithPortBinding(6667, true)  // random host port
        .WithWaitStrategy(Wait.ForUnixContainer()
            .UntilPortIsAvailable(6667))
        .Build();

    public string Host => _container.Hostname;
    public int Port => _container.GetMappedPublicPort(6667);

    public async Task InitializeAsync()
    {
        await _container.StartAsync();
    }

    public async Task DisposeAsync()
    {
        await _container.DisposeAsync();
    }

    // CreateConnectionAsync, CreateBot, CreateConfig remain the same
    // but use Host/Port properties instead of constants.
}
```

### Key changes

| Area | Before | After |
|---|---|---|
| Container start | `make ircd-start` / manual `docker run` | Automatic in `InitializeAsync` |
| Container stop | `make ircd-stop` / manual | Automatic in `DisposeAsync` (also on crash) |
| Port allocation | Hardcoded `localhost:6667` | Random mapped port, no collisions |
| Server readiness | TCP probe + `IsAvailable` flag | `WaitStrategy` blocks until port is listening |
| Test skip logic | `SkipIfUnavailable()` in every test | Not needed — fixture guarantees the server is up |
| IDE test runs | Require prior `make ircd-start` | Just run tests; container starts automatically |

### Test changes

- Remove `SkipIfUnavailable()` calls from all integration tests — the
  container is guaranteed to be running when tests execute.
- Remove `IrcServerCollection` if the fixture is used as a class fixture

# Testcontainers xUnit.net Integration

## Package Overview

The Testcontainers xUnit.net integration comes in two packages depending on your xUnit.net version:
- **Testcontainers.XunitV3** for xUnit.net v3
- **Testcontainers.Xunit** for xUnit.net v2

## Key Benefits

The package streamlines test container management by automating resource lifecycle. Rather than manually implementing `IAsyncLifetime` and managing setup/teardown logic, developers inherit from base classes that handle container creation and disposal automatically.

As stated in the documentation: "This reduces repetitive code and avoids common patterns that developers would otherwise need to implement repeatedly."

## Core Classes

Two primary base classes support different test scenarios:

1. **ContainerTest<TBuilderEntity, TContainerEntity>** - Creates isolated container instances per test, ideal for destructive operations
2. **ContainerFixture<TBuilderEntity, TContainerEntity>** - Shares a single container across all tests in a class, improving performance when container setup is expensive

For database-specific scenarios:
3. **DbContainerTest** and **DbContainerFixture** - Provide additional convenience features for ADO.NET services, requiring implementation of the `DbProviderFactory` property

## Usage Pattern

Developers override the `Configure()` method to customize container behavior, then access the container via the `Container` property (or `fixture.Container` in fixture-based tests). The framework handles all lifecycle management automatically.
