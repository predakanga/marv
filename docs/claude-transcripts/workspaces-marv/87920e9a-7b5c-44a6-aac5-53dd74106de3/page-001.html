2	
3	**Source:** GitHub issue #12
4	**Scope:** Core / Host
5	**Complexity:** Medium

10	
11	## Problem
12	
13	When Marv is used as the foundation for a downstream project (e.g. an
14	"IdleRPG" bot), the bot identifies itself as "Marv" everywhere:
15	
16	- Sentry error reports use Marv's version number, not the downstream
17	  project's.
18	- The CTCP VERSION response defaults to "Marv IRC Bot {version}".
19	- The `!version` command in CannedResponses is hardcoded to
20	  "Marv IRC Bot v{version}".
21	- The IRC GECOS (real name) defaults to "Marv IRC Bot".
22	- `MarvVersion.Current` always reads from the `Marv.Core` assembly,
23	  so downstream projects that reference Marv.Core as a NuGet package
24	  get Marv's version, not their own.
25	
26	CS-023 partially addressed this by adding a `CtcpVersionResponse`
27	configuration override, but that's a point fix for one touchpoint.
28	There's no unified identity concept that downstream distributions can
29	use to take ownership of the bot's branding.
30

108	The version resolution order is:
109	1. Explicit `BotVersion` config value (highest priority).
110	2. Entry assembly's informational version (catches downstream hosts
111	   that set their own version in their `.csproj`).
112	3. `Marv.Core` assembly's informational version (fallback for test
113	   hosts or environments with no entry assembly).
114	
115	```csharp
116	private static string ResolveVersion()
117	{
118	    // Try the entry assembly first — downstream hosts set their
119	    // own version in their .csproj
120	    var entry = Assembly.GetEntryAssembly();
121	    var info = (entry ?? typeof(MarvServiceExtensions).Assembly)
122	        .GetCustomAttribute<AssemblyInformationalVersionAttribute>()
123	        ?.InformationalVersion;
124	
125	    if (info is not null)
126	    {
127	        // Strip build metadata suffix (e.g. "+abc123def")
128	        var plus = info.IndexOf('+');
129	        return plus >= 0 ? info[..plus] : info;
130	    }
131	
132	    return entry?.GetName().Version?.ToString(3)
133	        ?? typeof(MarvServiceExtensions).Assembly.GetName().Version?.ToString(3)
134	        ?? "0.0.0";
135	}

200	## Design decisions
201	
202	**Why a dedicated `BotIdentity` type instead of just config properties?**
203	A typed record in DI gives plugins a clean injection point without
204	coupling to `MarvConfiguration`. It also provides `FullIdentity` as a
205	canonical formatted string, preventing each consumer from assembling
206	name + version differently.
207	
208	**Why remove `CtcpVersionResponse`?** It was a stopgap from CS-023 that
209	addressed one touchpoint. With `BotIdentity` providing the unified
210	name + version, the config override is redundant — changing `BotName`
211	and `BotVersion` covers the common case. The suppress/fully-custom case
212	is already handled by the `[OnEvent]` + `CtcpEvent` handler pattern,
213	which is more powerful and doesn't require a special config property.
214	
215	**Why remove `MarvVersion`?** Its sole purpose was reading the version
216	from the `Marv.Core` assembly. That logic is now inlined into the
217	`BotIdentity` construction, and `BotIdentity` is the canonical source
218	for all version display. Keeping `MarvVersion` around would be a
219	confusing alternative path to the same information.
220	
221	**Why auto-detect from the entry assembly?** Downstream projects that
222	create their own host application (referencing Marv.Core as a NuGet
223	package) naturally have their own assembly version in their `.csproj`.
224	Auto-detecting from the entry assembly means they get correct identity
225	without any configuration, while still allowing explicit override.
226	
227	**Why not a subclassable host app?** The issue mentions this as a
228	possibility, but it would be a much larger change with significant API
229	surface implications. Configuration-based identity covers the concrete
230	use cases (Sentry version, CTCP, display strings) without requiring
231	downstream projects to subclass anything.
232
