#152026-06-06T00:41:41.197Z

Add another change spec - plugins need a way to compare strings according to the network's casemapping

3 bash · 3 read · 2 edit · 1 write

So the infrastructure exists (CaseMapping static class with AreEqual, Fold, GetComparer) but it's in Marv.Core.Protocol — internal plumbing. Plugins can access IServerInfo.CaseMapping (the enum) but have no way to get a comparer or do comparisons without depending on the Protocol namespace directly. And CaseMapping.GetComparer() is used heavily inside IrcBot but never exposed to plugins.

Created CS-010: Expose Case Mapping to Plugins. The proposal is minimal — one new property on IBot:

IEqualityComparer<string> CaseComparer { get; }

The comparer already exists internally (CaseMapping.GetComparer() is called throughout IrcBot). This just exposes it so plugins can do Bot.CaseComparer.Equals(nick1, nick2) or use it with dictionaries/hashsets instead of incorrectly using OrdinalIgnoreCase (which misses rfc1459's []\ ↔ {}| equivalence).

#162026-06-06T00:47:46.949Z

Regarding CS-010, how should CaseComparer be handled when the bot is not yet connected? Should it error or fall back to the default? How should plugins which use collections handle that; they'd have to recreate their dictionaries et al on each connection

Good questions. The collection problem is the thornier one — a mutable-delegate comparer sounds appealing but would silently corrupt hash tables if the mapping changes.

My recommendation: default to rfc1459 pre-connection (it's the IRC spec default), and don't try to make it transparent — case mapping changes are a state reset just like everything else on disconnect.

In practice: - Case mapping almost never changes between connections to the same network - OnDisconnectedAsync already documents that IChannel/IUser refs are stale — collections keyed by nick/channel are equally stale - Plugins that maintain nick/channel dictionaries already need to rebuild them in OnConnectedAsync (since the user/channel objects are new)

So the lifecycle is: build your Dictionary<string, T>(Bot.CaseComparer) in OnConnectedAsync, tear it down in OnDisconnectedAsync. That's the same pattern plugins already follow for any connection-scoped state. The spec should call this out explicitly rather than trying to paper over it with a clever wrapper.

Want me to update CS-010 with this guidance?
