Good questions. The collection problem is the thornier one — a mutable-delegate comparer sounds appealing but would silently corrupt hash tables if the mapping changes.

My recommendation: default to rfc1459 pre-connection (it's the IRC spec default), and don't try to make it transparent — case mapping changes are a state reset just like everything else on disconnect.

In practice: - Case mapping almost never changes between connections to the same network - OnDisconnectedAsync already documents that IChannel/IUser refs are stale — collections keyed by nick/channel are equally stale - Plugins that maintain nick/channel dictionaries already need to rebuild them in OnConnectedAsync (since the user/channel objects are new)

So the lifecycle is: build your Dictionary<string, T>(Bot.CaseComparer) in OnConnectedAsync, tear it down in OnDisconnectedAsync. That's the same pattern plugins already follow for any connection-scoped state. The spec should call this out explicitly rather than trying to paper over it with a clever wrapper.

1	# CS-010: Expose Case Mapping to Plugins
2	
3	**Source:** Plugin DX feedback
4	**Scope:** Core (IBot / IServerInfo interface)
5	**Complexity:** Small
6	**Breaking changes:** Additive only
7	
8	---
9	
10	## Problem
11	
12	IRC nick and channel comparisons are case-insensitive, but the rules are
13	server-specific — the `CASEMAPPING` ISUPPORT token selects between `rfc1459`
14	(where `[]\` equal `{}|`), `strict-rfc1459` (also `^` equals `~`), and
15	`ascii` (A-Z only). The bot uses this internally for its `Channels` and
16	`Users` dictionaries, but plugins have no convenient way to perform the
17	same comparisons.
18	
19	Currently a plugin that wants to compare two nicks or check channel
20	membership must either:
21	
22	- Use `string.Equals(..., OrdinalIgnoreCase)` — **wrong** on rfc1459
23	  servers where `nick[away]` and `nick{away}` are the same user.
24	- Reach into `Marv.Core.Protocol.CaseMapping` — an internal namespace
25	  that plugin authors shouldn't need to know about.
26	- Use `IBot.Users` / `IBot.Channels` dictionary lookups as a workaround,
27	  which only works for exact-match lookups on known entities.
28	
29	## Changes
30	
31	### 1. Add a case-mapping comparer to `IBot`
32	
33	```csharp
34	// On IBot:
35	IEqualityComparer<string> CaseComparer { get; }
36	```
37	
38	Returns an `IEqualityComparer<string>` that uses the server's current
39	case mapping. Plugins use it for:
40	
41	- **Equality checks:** `Bot.CaseComparer.Equals(nick1, nick2)`
42	- **Dictionaries:** `new Dictionary<string, T>(Bot.CaseComparer)`
43	- **HashSets:** `new HashSet<string>(Bot.CaseComparer)`
44	
45	The comparer is already created internally by `IrcBot` (via
46	`CaseMapping.GetComparer`). This change simply exposes it.
47	
48	### 2. Implement in `IrcBot`
49	
50	`IrcBot` already calls `CaseMapping.GetComparer(_serverInfo.CaseMapping)`
51	in many places. Store the result and expose it via the `CaseComparer`
52	property. Update it when the server sends a new `CASEMAPPING` token
53	(rare but possible with some bouncers).
54	
55	### 3. Update MockBot (Marv.Testing)
56	
57	`MockBot.Create()` should set `CaseComparer` to return
58	`StringComparer.OrdinalIgnoreCase` (close enough for tests, and what
59	most servers approximate).
60	
61	### 4. Update PLUGIN_API.md
62	
63	Add `CaseComparer` to the IBot table in §5.
64	
65	## Design decisions
66	
67	**Why on `IBot` instead of `IServerInfo`?** `IBot` is the primary plugin
68	interface and already has `Channels`/`Users` dictionaries that use the
69	comparer. Exposing it alongside those is the natural location. Plugins
70	shouldn't need to think about where the comparer comes from — it's "the
71	way this bot compares IRC identifiers."
72	
73	**Why `IEqualityComparer<string>` instead of helper methods like
74	`NickEquals(a, b)`?** The comparer is more general — plugins can use it
75	with standard .NET collections and LINQ. It's also the type the bot
76	already uses internally, so no new abstraction is needed.
77	
78	**Why not also expose `CaseMapping.Fold()`?** Folding to lowercase is
79	occasionally useful, but it's less commonly needed than comparison, and
80	the comparer covers the primary use case. If demand arises, `Fold` can
81	be added later without breaking changes.
82	
83	## Impact
84	
85	- **Correctness:** Plugins that compare nicks/channels will use the
86	  right case mapping instead of guessing.
87	- **Simplicity:** One property, zero new types.
88	- **API surface:** 1 new property on `IBot`.

## Impact
+
**Why not also expose `CaseMapping.Fold()`?** Folding to lowercase is
occasionally useful, but it's less commonly needed than comparison, and
the comparer covers the primary use case. If demand arises, `Fold` can
be added later without breaking changes.

**Why not a mutable-delegate comparer that tracks the current mapping
automatically?** A wrapper comparer that internally follows the current
`CaseMappingType` would let plugins create collections once and have
them "just work" across reconnections. But this is dangerous: changing
the equality semantics of a `Dictionary` or `HashSet` after items are
inserted corrupts the hash table (items end up in wrong buckets, lookups
silently fail). A comparer that mutates under you is worse than one that
goes stale, because stale is at least detectable.

## Plugin lifecycle guidance

Plugins that maintain nick- or channel-keyed collections should treat
them as connection-scoped state — the same pattern they already follow
for `IChannel` and `IUser` references, which go stale on disconnect:

```csharp
private Dictionary<string, MyData>? _channelData;

public override Task OnConnectedAsync(CancellationToken ct)
{
    _channelData = new Dictionary<string, MyData>(Bot.CaseComparer);
    return base.OnConnectedAsync(ct);
}

public override Task OnDisconnectedAsync()
{
    _channelData = null;
    return base.OnDisconnectedAsync();
}
```

For one-off comparisons (e.g. inside a handler), call
`Bot.CaseComparer.Equals(a, b)` directly — no collection needed.
